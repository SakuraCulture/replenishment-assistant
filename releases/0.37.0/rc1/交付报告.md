## 已实现的使用流程

首页/准备数据 → 定时补货 → 选预案与开始时间 → 检查运行条件 → 保存并启用。可选每周或单次，默认同时计算 2 店，上限 4 店。电脑不休眠且软件保持运行，到点自动开始；错过超过 60 秒记为错过，不批量补跑历史日期。

任务使用持久化门店设置及预案，固定预算、主从仓、参数、必卖清单、关注清单、分类映射与准入依据。缺预算/路线或依据变化时等待人工处理，不从当前界面缓存猜值。

翱象按原任务取得门店建议，所需仓各获取一次资料，采用原检查、匹配及计算服务。逐店结果安全保存后标记可核对。完成后从首页两次点击进入原第四步，人工签发；不自动采购或确认付款。

默认资料发布与本次资料分开：全部门店计算完成、工作台空闲且无载入资料/未保存变更时自动更新；有工作进行则等待。原默认被其他操作更新时拒绝覆盖，保留任务计算结果供核对。发布复用仓锁和版本校验，逐仓留回执；不宣称跨多个文件系统写入原子。

暂停、继续原任务、单店重试、结束本次、停用未来安排、删除安排、删除已结束记录为独立动作。已成功门店不重算，平台状态不明不重发。关闭详情继续工作；退出软件先安全暂停。自动结果独立于每日草稿，打开/保存仍走原确认及历史只读流程。

## 性能

Windows 11、Python 3.12.14、24 个逻辑处理器；同机同环境，原基线手工服务与新编排交替串行各 3 次。下表全为明确合成数据，每店 200 SKU；包括读入、计算和结果保存，新编排包括任务记录与默认资料发布；不含真实网络等待。操作系统文件缓存未清空，不能作为冷磁盘或真实多店耗时承诺。

| 1 / 200 | 0.96（0.93～1.13） | 1.59（1.54～1.59） | +0.63 | 76.01→80.91 |

包含 Python 进程启动的外部端到端中位数依次为：1.92→2.44、3.76→5.09、6.42→7.82 秒。所有原始值、读入/准备、计算及保存阶段计时见 `performance.json`；阶段计时不机械相加代替总耗时。

- 新增开销均低于方案的 `max(2秒, 原耗时10%)` 上限。目标是提前完成准备、减少人员搬表，不是提高模型运算速度。
- RSS 每 250ms 采样主进程与全部子进程之和；共享内存页可能重复计入，峰值只是采样峰值。20 次固定活跃规模运行，最后 5 次稳态中位数较前 5 次增加 1.37 MiB，没有持续线性增长证据。
- 1 万条合成运行摘要、每页 50 条，20 次热查询 P95 约 3.59ms；这里只证明仓储查询，不冒充万条数据的实际 EXE 可见首屏耗时。
- 实际 EXE 定时流程 50ms 心跳 P95 约 78ms、最大约 109ms。样本为 2 店合成界面流程；夹具准备和验证脚本直接调用导出/保存不计入实际界面响应。这不证明真实网络等待期间所有界面都达到同样指标。

“青岛线”6 店、山东单仓、无限预算只写入隔离 QA。最后一次 Edge `connectOverCDP` 在 180,000ms 超时；仍未完成浏览器控制身份核验。用户点击允许是已收到的操作反馈，不能代替连接成功证据。未创建取数 run-id、未创建平台导出，没有签发或采购。

本次完成 A/B 核心及 C 主要界面，D 本地联合验收和打包通过，真实平台部分未完成。以下明确保留为未完成：

1. 青岛线真实“取数→仓资料→计算”整链路；真实跨模块授权保持、断网后的平台回执恢复；整夜/休眠唤醒实测。
2. 5 分钟空闲 CPU 对照、万条任务实际可见首屏、高缩放窄屏系统性验收；现有结果不冒充这些目标通过。
3. 在同一任务内改参数后重算没有单独入口；更换依据需新建任务，原任务可结束。参数预览和原依据继续/失败重试已有。
4. 运行记录已有搜索、状态及 50 条分页，尚无单独日期区间控件；大量生产任务的检索体验仍需业务试用。
