# 0.47.3 rc1 分析供货设置与名称显示交付报告

日期：2026-11-07。基线为0.47.2 rc2证据提交 `a163a46`。本次修复缺货率板块读取门店供货设置的来源，补齐门店/商品名称和编码，并修复验收中复现的子进程结果漏收时序。真实资料仅只读诊断，修改和测试均在源码或隔离QA目录；未修改真实业务数据库、未调用真实平台、未自动重算原日报，未推送或合并。

## 使用入口

退出旧版后完整解压[0.47.3运行包](../../../交付_0.47.3_rc1/补货助手_0.47.3_rc1_分析供货设置与名称显示.zip)，运行[补货助手.exe](../../../交付_0.47.3_rc1/补货助手/补货助手.exe)。保留整个目录和旧版包。

先在参数设置保存各店主从仓，再到“门店缺货率 → 选门店 / 采用补货侧设置”，用“查看已采用供货设置”逐店核对。新的分析采集使用新设置；历史日报与原任务的设置不自动改变。继续旧任务仍沿用其原依据，不可将今天仓资料补成此前日期的资料。[具体用法与供货规则](../../../docs/0.47.3分析供货设置与名称显示.md)

## 截图问题的真实原因

已通过SQLite只读连接核对截图对应原任务，未通过打开业务仓库对象触发初始化或迁移。

- 参数页的已保存门店供货关系在 `workbench.sqlite3` 的 `stores.ui`，分析采用入口却只读旧 `store_supply.json`。原任务选了15家店，采用供货路线0条、仓资料0份，导致全部49,786条有销记录的仓与标签依据待核。这不是参数页的主从仓算法失效，而是分析根本未取得配置。[只读诊断](readonly-diagnosis.json)
- 原任务选择的15家店中，诊断时8家有已保存默认供货关系，7家没有。截图顶部显示后来采用的10家新任务设置，其中3家有已保存关系、7家未保存；查询区显示的是已发布历史结果，两个范围不能混为一谈。保存“本次作业”临时设置不等于保存门店默认。
- 原任务14家留存成功、1家因查询与导出行数不一致未采信；实际原件观测日在11月5日和11月7日。图中完成14/30门店日是实际覆盖，不是30天齐备，不补缺采为0。
- 已识别缺货7,083、有销49,786；另有61条有销记录的门店库存为负数。按现有规则它们是指标异常，相关范围的率保持待核；“标签待核”和“指标待核”是两种问题。此版未把负库存当0，也未将公式改为库存≤0。

## 改动与隔离

1. 采用设置时只读取所选门店保存的主从仓，与参数页同一来源；前后复核路线摘要，设置并发变化则拒绝采用。必卖清单仍按原流程明确采用，原参数库和原文件不回写。
2. 单仓只使用本仓商品资料；本仓无该商品按本次地采。双仓保留原主从顺序、主仓状态判断及缺从仓商品时保留主仓资料的规则。类目、供应商、虚拟分类取最终归属仓，未选仓不干扰。缺整份资料与无该商品仍区分。
3. 增加已采用供货设置查看、路线覆盖数和未配置说明。没有默认的门店保留待核，不猜地域归属，不复活旧缓存中已清除的设置。
4. 门店与商品切面、组合切面、筛选提示、商品明细、口径查看及分析Excel同时显示编码与名称。汇总与筛选仍用编码；同名不同编码不合并，同编码名称不一致有提示。名称取分析快照，不用当前主数据覆盖历史。
5. 子进程完成消息漏收修复：进程可能在一次管道等待结束后发送结果并退出，原先直接判异常，现退出后再检查并收取已经返回的消息；没有结果或明确失败仍失败，不重放外部任务、不强杀进程。

主改动限定在 `stockout_settings.py`、分析采用/查询/页面/导出和分析工作进程的结果接收。模型 `0.3.4-rules`、仓归属 `0.5.2`、参数/作业/存储版本 `3/1/2` 保持。分析数据库格式不变，统计分子分母、剔除和取消回滚规则不变；未进入分析板块仍不加载其数据与业务能力。

## 限制

- 本版不会自动改写截图中的旧任务、旧日报；旧快照缺失的仓资料不会凭空出现。更新参数后需明确采用并创建新分析任务。
- 未保存默认供货关系的门店仍须在参数页明确设置；地采缺虚拟分类时仍为标签待核。负库存的统计口径没有修改。
- EXE通过封闭模拟平台和隔离原件验收，没有真实平台重新采集或真实账号操作。组件源码未变，本轮不重复宣称完成真实平台联调。
- 没有大历史库性能对照、低配置业务机或连续无人值守验收。原件按原流程分段处理；名称补充不新增历史全量预载，查询和页面预算保持。
