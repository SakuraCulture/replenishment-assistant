# 0.53.7 rc1 生命周期性能与聚水潭锁单恢复交付报告

已完成授权的前三项优化及锁单短读锁修复。数量、金额、币种、SKU与仓单顺序、原有校验、默认并发均保持。新旧完整业务计划、保存回执、逐表有序数据签名和进度边界零差异。

## 已确认的耗时与改动

1. 付款、收货提交仍重复解析及验算预览时已完整核对的上游和旧版本大单据。本轮沿用0.53.6回传使用的进程认证证据，扩展到付款与收货；提交仍完整读取当前行并哈希原文，只在身份、版本、时间、原摘要、全文字节完全相同时复用紧凑投影。证据缺失、编辑、变更或跨进程时回到完整解码，证据不落库。
2. 共用批量核对对大量SKU行重复解析相同补货单号，并复制已经归本次核对独占的输入。按精确单号复用一次查询内解析，data_version变化即失效；内部复用自己的隔离副本，公共入口仍保护调用方数据。每行来源、门店、仓、修订、重复事实及后续完整校验继续保留。
3. 聚水潭分配逐仓单事务重复编码同一整批计划、再次编码计算摘要。本轮只保留一份规范文本与摘要；每次事务仍读取最新删除范围，相关范围变化按原规则重新编码。6单无变化场景整批编码由14次降至2次。分配仍逐单提交6次，既有更正批原子范围、库存扣减、部分完成/继续与顺序均不改变。
4. 单独修复锁单：短暂读取可使最终COMMIT返回SQLITE_BUSY，旧链路直接报错。现在只有事务明确未提交、且安全回滚成功，才在统一10秒截止时间内重新核对并尝试。最终提交不强行中断；安全回滚后重新可取消。提交结果不明、非BUSY错误或回滚失败均不自动重放。解锁仍执行原原因与付款/收货保护。

生产功能改动集中于src/order_lifecycle.py、src/lifecycle_batch.py、src/jst_orders.py。src/app.py仅增加隔离验收入口，src/version.json更新应用版号。新增tests/test_lifecycle_performance.py、性能对照/EXE验收工具及专用验收模块；说明文档和打包文档清单同步更新。

补货计算模型、箱规、预算、归属、最低持有、准入规则、付款匹配规则、平台上传代码和并发默认值没有改动。存储格式、secure_delete、同步持久性、原件留存、首次备份均未削弱。前轮0.53.6未提交成果保留并纳入本次冻结快照，没有覆盖丢弃其他会话的成果。

付款首次保存内存改善很小；分配预览RSS略增，无占用锁单耗时1.291→1.398秒、RSS259.0→259.4 MiB，已生成批次重复提交0.187→0.195秒，不宣称所有阶段都提速或省内存。进程读写量基本不变，本次主要减少CPU解析、复制、编码及持锁内工作。锁单改动的目标是短占用后安全恢复，不是无占用速度提升。

内存为20毫秒采样的测试工作进程RSS峰值，不是整机、整个应用树或理论瞬时峰值；进程I/O含系统缓存，不等于物理磁盘吞吐/占用率。原件初次读取、测试库复制在计时外；计时为后端入口，不包括Qt渲染、保存后列表刷新或网络/平台等待。只在本机合成数据上测量，未在低配置业务电脑测量，不能直接外推业务等待时间。
