## 业务口径与实现范围

**门店缺货率 = 月销 > 0 且门店可用库存 = 0 的店品数 ÷ 月销 > 0 的店品数。** 在途不抵扣缺货。多店分子、分母分别加总，多日按店品日加权；不平均百分比。零分母显示“—”。月销缺失、负值、非法值及有销商品的异常库存保留待核，不填成 0。

- 包含中心仓 / 地采、必采 / 非必采、门店、仓、原商品类目、仓内上游供货商切面及组合筛选、商品明细和独立 Excel。资料不足仍可出现待核组，不强行归入非必采或已知供应商。
- 全量、剔除淘汰、剔除考核、同时剔除四种视角，共用同一事实；分子和分母同步调整，双标只剔除一次。精确识别聚水潭原生“虚拟分类”的“标杆淘汰”系列和“淘便考核”；标签未知保留并单列。
- 沿用 0.46.5 单仓归属：所选单仓没有对应商品时可归地采，不借未选另一仓的身份、类目、供应商或淘汰标签。禁用或停采商品只要有月销仍进入缺货率基数，不套用下单过滤。
- 以实际取得原件的观察日期形成日报，不拿今天库存补历史缺采。部分成功显示实际覆盖；恢复失败项形成可追溯修订。一天一次观察不能代表全天缺货时长。
- 只有明确“采用补货侧设置”时才只读复制已保存路线和必卖清单。分析资料有独立用途，禁止发布为原补货默认仓资料；原业务采集页面也不把分析任务作为业务可采用资料。
- 原任务身份和已确认原件可恢复；平台受理未知先核对原任务，不生成新编号盲目重试。手动采集离开页面默认安全暂停，只有明确勾选后台继续才保留；每日后台计划须单独开启。
- 原业务任务优先。分析一次一个工作进程，逐店解析、有界批次与分页；取消等待安全边界，不强杀提交。清理只作用于预览日期范围内的分析数据，不删除原订单或平台任务。

主要新增代码是 `src/stockout_*`。共享改动包括小型导航入口、独立用途及任务互斥、公共纯仓选择函数 `warehouse_routing.py` 和原有淘汰枚举 `virtual_categories.py`。原业务归属规则未改变；仓选择组合和原字段结果已有回归覆盖。rc2 另修正 PyInstaller 工作进程入口，确保后台进程在 Qt 标准钩子之前进入 `freeze_support`。

## 容量调查与优化

初次容量检查发现，供应商与类目交叉汇总、明细计数及排序会反复扫描大量事实；导出汇总也重复承担这一成本。实现改为按内容保存公共维度，按快照预汇总实际出现的维度组合，普通切面读取这些计数；明细先定位快照再按索引翻页。没有生成全维度笛卡尔积，也没有省略原件或字段完整性校验。商品编码等高基数切面仍可能扫描事实，可取消。

容量输入为 20 店 × 每店 10,000 商品 × 30 / 90 天。真实 XLSX 解析后在隔离库扩展历史，维度固定为合成数据；它不是平台连续采集 90 天。以下是优化前后各一次调查运行，**不是新旧交替三轮性能基准，也不代表低配置业务机表现**。原始记录：[优化前](capacity-before.json)、[优化后](capacity-after.json)。

| 查询 / 输出 | 30 天 600 万行：前 → 后 | 90 天 1800 万行：前 → 后 |
| --- | ---: | ---: |
| 总览 | 0.0064 → 0.0032 秒 | 0.0118 → 0.0110 秒 |
| 逐日趋势 | 0.0696 → 0.0382 秒 | 0.2197 → 0.2145 秒 |
| 供应商 × 类目 | 19.121 → 0.020 秒 | 60.332 → 0.083 秒 |
| 首 200 行明细 | 6.390 → 0.010 秒 | 19.356 → 0.032 秒 |
| 汇总 Excel 导出 | 43.482 → 0.316 秒 | 137.682 → 0.820 秒 |
| 查询取消响应 | 0.108 → 0.105 秒 | 0.115 → 0.109 秒 |
| 查询进程峰值 RSS | 67.96 → 64.94 MiB | 68.43 → 62.02 MiB |
| 查询组进程读取量 | 15,720,320,791 → 68,819,919 字节 | 47,127,349,571 → 138,539,427 字节 |
| 查询组进程写入量 | 2,304,065,584 → 614,951 字节 | 6,912,109,196 → 1,763,432 字节 |
| 分析数据库大小 | 1753.10 → 1754.83 MiB | 5256.48 → 5265.33 MiB |

代价是保留汇总后数据库稍有增加，测得差值也包含 B 树页面布局影响。90 天库约 5.14 GiB；历史、下载原件和平台组件缓存都会继续占磁盘。这里的进程 I/O 包含系统缓存，不是物理磁盘占用率；RSS 是独立查询进程，不是整个应用或整机。写入量是所测查询与汇总导出组，不是每日原件采集的写入量。

优化前后两组总量逐字段一致；同时剔除时，30 天分母 4,800,000、分子 1,200,000，90 天分母 14,400,000、分子 3,600,000，均为 25%。单元场景另对比原事实和预汇总的四视角、组合筛选及分页结果。容量检查未执行 1800 万行完整商品明细 Excel 导出，也未涵盖任意高基数维度或真实最大仓 Excel 解析峰值。

## 未使用时的资源隔离

以 0.46.5 基线和候选代码交替串行各三轮，对空分析目录、30 天库、90 天库分别测量；共 18 次。两版均保持分析页未进入、每日计划关闭。通过 Python 文件 / SQLite 审计及生命周期状态检查，候选的分析数据访问、重型模块、分析页面、进程及定时器均为 0。以下为中位数，见 [idle-comparison.json](idle-comparison.json)。

| 独立分析数据规模 | 启动：基线 → 候选 | 主进程 RSS：基线 → 候选 | 原业务元数据读取 100 次：基线 → 候选 |
| --- | ---: | ---: | ---: |
| 空目录 | 3.387 → 2.968 秒 | 199.37 → 198.35 MiB | 0.566 → 0.553 秒 |
| 30 天库 | 2.862 → 2.812 秒 | 199.22 → 198.84 MiB | 0.404 → 0.430 秒 |
| 90 天库 | 2.786 → 2.777 秒 | 199.03 → 198.46 MiB | 0.374 → 0.360 秒 |

这一结果支持“未使用时不随分析历史规模加载”的边界，不能把缓存与启动次序造成的差值宣称为原应用提速。元数据读取使用隔离默认业务库，不代表所有原业务重型流程的性能。开启每日计划后会按授权启动后台分析，不适用未使用零任务结论。

## 保留的失败与已知限制

1. 首次源码窗口验收遇到 Windows `WinError 109` 管道已结束：子进程已返回最终结果，父线程再次读取管道时报错。已改为收到最终成功 / 失败后停止继续读管道，后续通过。[原失败](retained-failures/source-ui-01.json)
2. 一次源码验收在原件投影阶段收到取消，原日志不足以还原取消触发方。增加取消来源诊断后，两个独立源码复验及 rc2 EXE 通过，未再复现；**没有足够证据把这次取消的根因写成已修复**。[原失败](retained-failures/source-ui-final.json)
3. rc1 EXE 在“后台进程不加载 Qt”检查失败。已定位到 PyInstaller 标准 Qt 钩子早于应用 `freeze_support`；rc2 自定义早期分发修正后，本项及原业务子进程链路通过。rc1 构建、失败报告和日志保留。[原失败](retained-failures/exe-rc1.json)
4. 全量回归仍有既有 `browser_status_ui` 的 QLabel 销毁后回调警告，测试最终通过；本轮没有修复该警告。
5. 未做真实平台连续每日采集、低配置业务电脑、全新电脑部署或整夜无人值守验收。平台协议用离线场景验证，不能因此声称真实平台端到端已通过。
6. 仓资料继续使用原生校验器，真实最大仓 Excel 的解析中间峰值尚未测量。预检内存 / 磁盘阈值不能保证 RSS 硬上限。共享浏览器、平台任务台账及下载缓存也占资源，页面分析库及自有原件占用不代表整机总量。
7. 地采缺少对应仓资料时，类目、供应商或虚拟分类可能未知；剔除视角保留未知记录并显示覆盖，不能声称淘汰 / 考核已全部剔除。备份需要正常退出后复制完整分析目录，单独数据库不含原件。

本次交付提供可独立使用的首版及可复核的隔离证据；未改变模型、预算、箱规或原订单删除范围。后续真实采集验收可从少量门店、手动采集开始，核对原件、覆盖和缺货商品后，再由业务决定是否开启每日计划。
