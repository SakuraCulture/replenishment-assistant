## 业务流程与代码索引

| 环节 | 代码 | 当前行为 |
|---|---|---|
| 窗口、后台任务、筛选和结果失效 | `src/app.py` | 两份 Excel 导入；修改文件、门店、参数、预算或清单后重新计算 |
| 四步向导及多店状态 | `src/batch_app.py` | 多文件、冲突处理、独立预算、单店失效、部分完成导出 |
| 多店编排 | `src/batch_service.py` | 私有临时归集表；按门店进程并发；原计算引擎不变 |
| 分仓资料与需求归属 | `src/warehouse_catalog.py`、`src/warehouse_ui.py` | 外部分别标记河北/山东资料，保存快照，门店主从仓选择；无库存扣减或需求限量 |
| 版本信息 | `src/version.json`、`src/version_info.py` | 应用/模型版本统一来源；构建时注入提交与构建编号 |
| 字段读取与精确关联 | `src/input_adapter.py` | 商品编码关联，保留异常与源行 |
| 门店/仓参数、计算编排、执行状态、导出 | `src/engine.py` | 河北仓8+4、山东仓8+5；未知仓需填参数；缺失箱规补1；未知分类用快销权重 |
| 原模型 | `src/model.py` | 销量校正、预测、库存额度、最低恢复与单商品资金约束 |
| 一箱例外 | `src/one_box_exception.py` | 原模型结果之后，对符合条件且原建议为0的商品放行一箱 |
| 门店预算分配 | `src/allocation.py` | 必卖先于普通；按最小出库单位分配，不超预算或候选数量 |
| 必卖清单和本机配置 | `src/priority_list.py` | 导入、备份与持久化；预算按门店记忆 |
| 内置业务配置 | `src/default_config.json`、`src/default_must_sell.json` | 随源码追踪；必卖默认清单含2142款，属于业务资料 |
| 构建与归档 | `build.ps1`、`prepare_delivery.py`、`assemble.py` | 构建运行包、附说明与许可、核验后归档 |
| 验证 | `verify_budget.py`、`verify_exe.py`、`src/smoke.py` | 0.3预算与界面验收；依赖本机输入和历史对照文件 |

计算顺序：选择需求归属仓及对应商品资料 → 原模型 → 一箱例外 → 禁用/停采排除 → 门店总预算分配。主仓禁用、可用数≤0或无商品时转从仓；从仓无货仍保留从仓需求，不新增“仓库暂不可供”类别。细则、字段映射和交互图见`docs/0.5.0分仓需求归属.md`。兼容模式保留0.4混合资料计算入口。
AS/BV 保留计算口径；执行数量/金额受排除和预算影响。启用预算后最低持有可能暂缓，不能沿用早期脚本“有销量必定执行补货”的结论。
当前版没有改成3.5+5天，没有应用两套日均统一或安全余量2/3/4天试验。

## 运行和构建

已有本地环境可运行 `.venv\Scripts\python.exe src\app.py`。
打包入口：`powershell -File build.ps1 -BuildId rc1`。只接受干净且已提交的源码；新建`交付_<版本>_<构建编号>`及`build_<版本>_<构建编号>`，目标存在则拒绝。不再覆盖同版本目录。
完整流程及命令见`docs/版本管理流程.md`。`assemble.py --help`列出本次发行所需明确路径；拒绝混用其他提交的验收报告。
`requirements-build.txt` 记录本机观察到的应用与构建依赖；尚未验证全新电脑能完整复现构建。

## 版本控制

源码、默认配置、图标、构建/验证脚本、第三方许可、历史源码快照、选定发行证据进入 Git。
虚拟环境、运行包、构建目录、业务输入/导出 Excel、日志、本机配置、QA临时产物不进入 Git。
发行包继续保存在各自交付目录，校验清单和版本说明保存在 `releases/<版本>/<构建编号>`；0.3历史基线直接保存在`releases/0.3.0/`。
Git 记录不能代替发行包备份；已忽略的 EXE/ZIP 不会随 Git 恢复。

基线标签采用 `v0.3.0-baseline`，表示本次接管时的源码状态与交付包校验记录，不声称进行了同环境重打包或证明源码与EXE逐字节可复现。
历史 `versions/0.1`、`versions/0.2` 保留为收到的快照，不虚构历史提交时间。
下一次修改先建立分支，例如 `git switch -c feature/holding-policy`；每次提交一个可说明的变化。
后续修复递增补丁号，新增功能递增次版本号。新版本记录规则差异、验证结果和发行包SHA256后再打标签。
本流程不修改远程配置、不自动上传；当前远程状态以`git remote`为准。默认必卖清单及验收记录含业务数据，日后共享时须确定受众。

## 验收依据与局限

0.3.0基线说明及验收以 `releases/0.3.0/使用说明.txt`、`验收记录.txt` 为准；0.4.0以自身发行目录记录为准。
根目录旧 `验收记录.txt` 实际标题为0.1.0，仅保留历史原件。
`verify_backend.py`现仅提示使用新入口；旧实现保存在`versions/0.2`。0.3旧UI smoke保留历史参考，不再作为当前入口。
`verify_budget.py`（固定真实样本回归）、`verify_batch.py`（多店与并发）、`verify_exe.py`（当前打包程序）均要求明确输入和新输出目录，用`--help`查看。
每次发行的实际验证以`releases/<版本>/<构建编号>`为准。0.3基线核验不代表新版本业务/UI验收，也不证明可复现构建。
