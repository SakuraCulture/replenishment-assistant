# 补货助手

面向多门店、山东仓与河北仓的 Windows 补货工作台。把补货数据准备、模型计算、门店确认、分仓执行和单据跟踪放在一个应用内，逐步替代原影刀流程中的重复搬表与浏览器操作。

## 业务流程

新人请先看 [业务流程版上手手册](docs/manual/index.html)（HTML 适用 0.50.3，2026-11-10 修订；PDF 为 0.49.3 归档）：按一批补货从参数准备到实收交接引导使用，另有每日缺货分析路线。[第 17 章：第一次配参数](docs/manual/index.html#c17)逐步讲解主从仓、预算、三种生效范围、V3 导入、权重错误和生效复核；[第 18 章：28 项参数速查](docs/manual/index.html#c18)列出当前标准、边界与易错点；[第 19 章：维护三种单号](docs/manual/index.html#c19)区分原采购任务继续核验、已有翱象单核对关联和聚水潭内部号维护。HTML 可搜索、放大原图并练习权重，PDF 可检索、按章节跳转。独立更新包位于 `交付_0.49.3_新人教程详解_20261109`，原应用封版包与旧 PDF 保留；截图版本、模拟状态与现场验证限制逐图标注。

正式单据链：**签发单 → 门店回传单 → 门店付款单 → 门店实际收货单**。

1. **准备数据**：从翱象获取指定门店补货建议，或手动导入；分别准备山东仓、河北仓的聚水潭商品资料与库存。
2. **计算与核对**：选择门店、主从仓、预算和有效参数，计算后查看理由，按需人工改量或安排新品，确认签发。
3. **回传与分配**：采用门店确认回传数量，明确选择分配批次、仓资料及门店顺序，核对分配结果并导出聚水潭执行文件。
4. **付款与采购**：导入实际付款明细，或明确采用聚水潭导入单作为付款依据，核对后确认；以确认的付款资料准备翱象采购。
5. **收货与复查**：跟踪采购状态，核对实收、差异与完成时间；历史保留各环节依据。

手动入口继续保留。生成文件、导出文件、平台实际下单、付款确认和实收是不同事实，不能用本地生成成功代替平台接收成功。

## 主要能力与边界

| 业务 | 已有能力 | 使用边界 |
| --- | --- | --- |
| 数据准备 | Excel 检查、字段匹配、分仓资料、翱象建议获取、聚水潭两仓商品资料同步 | 两仓账号和资料隔离；浏览器需正常登录及连接核验 |
| 定时补货 | 按预案定时取数、更新所需仓、计算并保存独立结果，支持暂停/继续/失败重试 | 软件保持打开；不签发、不采购；修复后源码已通过5店单仓真实链路，原rc1及整夜无人值守不据此宣称通过 |
| 补货计算 | 多门店计算、预算分配、箱规、必卖清单、新品安排、人工改量、理由复查 | 按所选参数与资料计算；业务准入和最终执行数量需核对 |
| 参数维护 | 分仓周期、门店分类参数、独立通用参数、全局分类映射、补货预案；单店/批量/Excel 维护 | 保存默认与应用本次分开；仅更新明确选择的字段，历史快照不回写 |
| 批次执行 | 按回传需求分配、冻结库存、暂停恢复、撤销、重复导出 | 本地占用限本批；资料适用性由业务判断，不按文件时间或哈希判断新旧 |
| 单据管理 | 签发、回传、付款、实收的版本关联、历史查询与差异导出 | 原始记录与当前状态分开；保持签发、回传和付款确认 |
| 翱象自动化 | 建议采集、采购准备与任务恢复、采购观察及实收适配 | 局部真实验证不等于完整连续闭环验收；未知受理先核对原任务 |
| 聚水潭自动化 | 两仓资料原生导出、下载和隔离采用已有真实验证记录 | 自动填地址下单、外部订单关联及实际配货回拉仍是后续主链工作 |
| AI 协助 | Codex / WorkBuddy 本机连接；查询、独立试算、对比、解释、重试和明确采用 | 正式保存、签发、删除、采购和生命周期导入仍在原页面完成 |
| 经营分析 | 独立五段看板、必采/非必采、多轮复盘、原生与AI同口径导出 | 签发业务日筛选；缺失不当0，缺历史依据待核，离散库存观察不等于连续回测 |
| 门店缺货率 | 独立每日快照、淘汰/考核剔除、供货来源/必采/类目/上游供货商等切面、明细及Excel | 按实际观测日期；无历史回填，标签未知保留，每日计划默认关闭，未使用不加载历史 |

此前版本用一张真实已完成采购单补验主子单原件、实收解析和隔离库重复入账；隔离库上游依据由原件重建，不代表该历史订单已与正式付款关联。0.46.3 的采购恢复仅做隔离验证，没有重传或修改真实采购单。联合换机、创建至实收连续闭环及全链路真实规模性能仍未完成，详见[项目进度](docs/项目意图与实施进度.md)。

## 开始使用

**业务使用**：完整解压 `交付_0.49.1_rc1/补货助手_0.49.1_rc1_付款自动认单.zip`，正常退出旧版后运行其中补货助手.exe。保留 `_internal`、`AI接口`、`AI入口`、`使用手册` 等整个目录。“显示与帮助”可调整字号、打开手册和恢复导出。启动自动检查连接与登录，不自动刷新业务资料或启用计划；连接未完成时点击底部“连接检查 / 修复”。业务模块共享已保存配置，无须分别重新配置；真正断线、切换账号或重启后仍可能需要 Edge 许可。此前交付包仍在原目录。发行包与业务资料不随Git下载，源码仓库不等于完整运行包。含旧快照的资料库请继续使用保留的0.46.0版本。

**AI / CLI 使用**：保持补货助手打开，在顶部“AI 协助”选择客户端，点击“配置/修复本机连接”，核对后写入；在客户端重新加载并完成首次信任，再点击“检查本机连接”。从“AI 常用业务”复制当前作业提示词到客户端发送，复制本身不执行任务，采用试算仍需明确确认。配置仍有本机路径，由软件维护；新电脑须重新配置一次，连接密钥和浏览器登录态不迁移。已登记的同一资料环境升级后会更新接口位置，客户端需重新加载。CLI说明和手动配置入口保留，定时任务只读。详见[当前用法及边界](docs/0.40.0AI口径与本机连接.md)。

0.40.0 重新完成真实 Codex/WorkBuddy 调用：数值与导出一致，Codex本轮三项解释通过；WorkBuddy仍混用每店与合计缺口，并有历史时间关系和明细展示不完整的问题，**自然语言未全部通过**。原生结果应作为业务核对依据，不能把一次工具成功当成AI回答可靠。各版本证据分别保留，详见本轮报告。

**源码运行**：在仓库根目录、已有本地 Python 环境中运行：

```powershell
.\.venv\Scripts\python.exe src/app.py
```

主应用使用 Python / PySide6 / openpyxl，业务与作业记录使用 SQLite，浏览器组件使用 Node / Edge。当前交付使用 Windows x64、CPython 3.12.14 的[锁定依赖](requirements-win-amd64.lock)，浏览器组件还需按自身锁文件收集。独立锁定环境构建成功不等于全新电脑逐字节可复现构建。

测试及开发使用独立资料目录：启动前可设置 `REPLENISHMENT_DATA_DIR` 指向专用 QA 路径。不要将日常资料目录作为测试输出位置，也不要将登录态、账号凭据或真实业务原件提交到仓库。

## 验证与构建

常规 Python 回归入口：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

真实样本对照、浏览器组件验证与实际 EXE 验收另按对应发行报告执行；一次单元测试通过不能替代这些验收。不要把旧版测试数量或性能数据当成当前版本结果。

0.43.1 的完整回归和EXE验收见[本轮报告](releases/0.43.1/rc1/交付报告.md)，批量解除包含取消、并发拒绝、失败回滚及7000条隔离规模验证。AI真实客户端结果另以[0.40.0报告](releases/0.40.0/rc2/交付报告.md)为准，不能把本轮桌面测试当作新的AI或平台联调。

构建前先提交并固定源码，准备锁定依赖及组件运行时，选择未使用的构建编号：

```powershell
# 仅为命令示例；docdemo1 必须尚未使用。
.\.venv\Scripts\python.exe tools/build_from_commit.py --commit HEAD --build-id docdemo1
```

当前构建器从固定 Git 归档生成主程序、AI 接口及浏览器组件，不纳入工作区未提交文件；生成独立的 `交付_<版本>_<构建编号>` 和 `build_<版本>_<构建编号>`，已有目录时拒绝覆盖。构建后仍需独立 EXE 验收、清单与 SHA256 记录，不能借用旧报告证明新包。早期 `build.ps1` / `assemble.py` 命令仅按其适用版本使用，参见[版本管理流程](docs/版本管理流程.md)。
