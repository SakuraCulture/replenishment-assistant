# 商品资料实际保存链路（0.16.0代码核对）

本轮没有修改商品资料存储实现。以下说明来自当前调用链，不把设计愿望当作已实现。

## 1. 导入校验后：先留存原Excel

工作页选择“导入河北仓资料/导入山东仓资料”，`WarehouseUi.import_catalog_path`启动后台`warehouse_catalog.import_catalog`。读取商品资料并校验编码、重复、必需字段和读取前后文件哈希。

校验成功后，`ui_tasks.Worker.run`在发送成功信号、界面采用新资料之前调用`source_archive.retained_import`。`source_archive.capture`把原Excel完整字节写入`workbench.sqlite3`的`source_files`表，以SHA256为主键，保存原文件名、留存时间和文件内容。相同内容只存一份。这里保存的是原文件，不是商品字段加工表，也不是仅保存一个本机路径。

注意：这个原文件留存发生在界面“确认更新并保存仓资料”弹框之前。用户取消后，当前生效仓资料没有更新，但原Excel可能已经作为未被采用的附件留存。本轮没有改变这个行为。

## 2. 确认更新后：保存当前生效的仓资料

`WarehouseUi.catalog_imported`显示原/新版本及商品数量，确认后才调用`warehouse_catalog.Repository.save`，通过`atomic_json`写入配置目录下：

- `warehouse_catalogs/河北仓.json`
- `warehouse_catalogs/山东仓.json`

JSON包含用于计算的商品字段、精确编码、原行号、仓库标记、资料版本、导入时间、源工作表、原文件路径和SHA256。它不是完整原Excel；未纳入解析字段的原始内容仍在`source_files`原附件中。

每仓JSON保留当前生效版本，新导入完整替换该仓，不追加累积另一份表。程序下次启动会读取这两份JSON复用。已有计算结果会要求重新检查，不自动把仓资料变化塞进旧结果。

## 3. 保存每日作业：保存本次使用的资料快照

`Workbench.snapshot`把本次内存中使用的`catalogs`与输入、参数、结果放入作业快照，存入`workbench.sqlite3`中的作业数据。当前物理存储为分块格式2，不等于每次复制所有原Excel。

恢复作业时使用作业里的资料快照，而不是用今天最新的仓资料替换昨天的资料。源文件后来在磁盘上被改名、移动或覆盖，也不等于应用里的快照自动改变。

## 4. 确认归档/签发：固定订单使用的资料版本

`normal_orders.Repository`保存正常单修订时，将对应作业版本固定到`normal_work_revisions`，签发快照记录`work_revision`。再次保存每日作业或同日重新签发后，旧签发仍可找到自己的工作快照；同日新签发是新修订，不覆盖旧修订内容。

历史读取链为：签发修订 → `work_revision` → 当时作业中的`catalogs` → 对应仓`source_sha256` → `source_files`原Excel。`history_forms.work_parts`读取当时快照，`archive_batch`用该仓哈希定位原附件。不会用当前仓JSON补写历史原资料。

历史没有留存原Excel时，只能明确提示缺失；加工核对表不能冒充原表。回传、付款、收货引用同一签发修订，不重新导入商品资料，也不改写签发时快照。

## 实际位置与边界

默认用户目录为`%LOCALAPPDATA%/YoutuanTools/补货助手/settings`；源码和EXE验收使用`REPLENISHMENT_DATA_DIR`指定的独立QA目录。默认导出目录设置只改变导出文件落点，不迁移上述资料或数据库。

代码入口：`src/warehouse_ui.py`、`src/warehouse_catalog.py`、`src/ui_tasks.py`、`src/source_archive.py`、`src/workbench.py`、`src/normal_orders.py`、`src/history_forms.py`、`src/archive_batch.py`。

当前并不是一个独立的“所有仓资料导入版本管理库”：每仓JSON只保存当前版本，已签发单保留当时快照，原文件按内容留存。导入但取消采用的原附件，以及未用于签发的资料版本是否需要可见管理，是后续可讨论的功能，本轮未扩展。
