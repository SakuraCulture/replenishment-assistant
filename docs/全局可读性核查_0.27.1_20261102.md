## 3. 根因

1. **几个地方各自维护名称映射。** `history_forms.LABELS`、`archive_exports.LETTER_LABELS`、`parameter_schema.HELP`、`parameter_view.display_path`、`display_fields` 各管一段，名称和覆盖范围不一致。
2. **展示结构经常等于存储结构。** 通用递归展开适合取证，不适合作为业务默认界面。换成中文路径仍会产生 200 多行重复参数。
3. **缺少按场景分层。** 完整性、安全提示、来源追溯、业务动作都在同一层，靠长段说明弥补入口和范围不清晰。
4. **缺少统一的字段格式约定。** 数量、金额、概率、时间、无预算、缺失和未确认没有统一按含义展示。

代码扫描还找到 74 个直接传递异常字符串的候选调用点。这个数字不等于 74 个问题：部分异常本身已经是可用的中文业务提示，需要逐条分类；已确认的典型情况归入 R31。

## 4. 优先怎样改

先围绕“为什么签发这个数”建立三层阅读顺序：

| 层级 | 默认展示内容 | 进入方式 |
| --- | --- | --- |
| 结果 | 门店、仓、商品；最终签发数量及库存单位、金额；主要原因；人工改量与自动安排的差额 | 打开商品即见 |
| 数量依据 | 当时销量库存、实际生效参数；常规计算、恢复/一箱例外、执行排除、预算、人工调整中已留存的数量及实际变化 | 点击“查看数量形成过程” |
| 完整证据 | 原字母字段、内部审计、完整方案、原始商品资料、文件路径、哈希和构建信息 | 点击“查看完整依据”或下载原件 |

每一步都应标注“应用后的数量”与“相对上一步变化”；没有留存足够信息的历史单显示“历史未留存该阶段，无法确定”，不能凭 BQ>0 等条件补编原因。阶段顺序按真实实现和快照证据核实，不能把并列参考值直接画成严格计算链。

建议实施顺序：

1. 决策复查与历史参数：R01—R08、R32。先解决用户当前最直接的困难。
2. 参数维护、预算和签发确认：R09—R13、R17—R19、R26。用户做决定时看到准确的人话与差异。
3. 工作表、导入、日志、错误和导出结果提示：其余项目。复用统一的名称、格式和“业务摘要＋技术详情”组件。

不要通过删证据、减少计算字段或改业务规则实现“简洁”。优先复用现有模块，建立轻量的展示字段定义，不需要大规模结构重构或存储迁移。
