# 本地版本管理

0.3.0基线：main / 7b8da6b / v0.3.0-baseline。保留既有标签、历史提交和交付包；无远程发布。
根目录验收记录.txt为0.1.0历史，当前基线证据只在releases/0.3.0。

## 日常流程

1. `git status --short --branch` 检查用户改动；`git switch -c feature/功能名`。
2. 修改后更新src/version.json、使用说明和变更说明。应用版本和模型版本分别管理；更改计算规则才更新模型版本。
3. 使用明确输入路径及新的QA目录验证；不得覆盖旧QA证据、业务Excel或本机用户配置。
4. `git diff --check`，提交本次源码。打包脚本只接受干净工作区。
5. `powershell -File build.ps1 -BuildId 候选编号` 从已提交源码构建。版本读自src/version.json，每次构建目录和交付目录独立，已存在即拒绝。
6. 对该EXE运行打包界面验证，核对业务回归、并发等价、输入文件和0.3基线未变。
7. 用assemble.py传入本次构建目录及本次验收报告。工具核对源码提交/版本，生成独立发行记录及ZIP，不借用旧验收结论。
8. 提交发行证据后创建新的带注释标签，例如 `git tag -a v0.4.0 -m "0.4.0 release"`。不覆盖已有标签。记录中保留打包源码提交；标签指向包含发行记录的提交。

## 证据含义

文件清单及ZIP哈希只证明文件完整性。业务回归、EXE交互、可复现构建分别报告；本机成功不等于已验证全新电脑或逐字节可复现。
虚拟环境、build目录、交付目录、QA临时文件及本机配置不进入Git。默认必卖清单是获准随应用交付的业务配置；日后共享仓库需另行确认受众。
