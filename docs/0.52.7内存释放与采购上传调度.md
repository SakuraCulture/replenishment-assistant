# 0.52.7 内存释放与采购上传调度

本轮实施已确认内存方案的前三项，并按用户新要求解除翱象采购上传的本地待完成任务数量上限。旧0.52.6交付保留，独立构建；不更改模型0.3.6-rules、数量、预算、箱规、归属或补货计算默认并发2。不操作真实业务库，不调用平台，不自动替换现用软件。

## 三项内存修改

1. 聚水潭`receiveBoundFile`在单次响应结束后`finally dispose`，覆盖成功、HTTP错误、正文错误、取消与写文件失败。只释放本次响应，不关共享浏览器或请求context，不改变下载字节、SHA、原任务身份、文件名和回执；清理自身失败保留首异常或成功事实，技术诊断不泄露地址凭据。
2. 历史缓存用分段UTF8增量hash替代`join+encode`整份副本。保持原schema、三列文本、原checksum，读取仍完整校验未请求显示的投影；旧缓存无需升级或重建，不减少完整性校验。
3. 恢复仓资料窗口仍按原文件mtime倒序、逐份读取并完整校验，但下拉框只持有日期/条数/修订及文件身份，不保留所有商品正文。选定后读取该原文件，核对身份、原字节SHA和目录元数据，再沿原恢复确认和保存流程。空目录、损坏原件照常报告；文件替换或移除时拒绝自动换版本。仓资料和历史文件格式不变，原`history`全文接口保留其他调用方兼容。

文件身份是仅在当前窗口使用的临时标记；Windows卷和文件ID可超过Qt有符号64位整数，转成不丢精度的字符串。Windows `stat/fstat`的旧`ctime`含义不同，各自前后核对，仅交叉比较同义的文件身份/大小/mtime。实际文件内容SHA和原仓资料revision完整校验同时保留。

## 翱象采购上传

原本本机窗口默认2、可调1–4个待完成任务。新版按勾选顺序连续提交全部订单，每项取得唯一受理回执后即可提交下一项，不等待前一项平台导入、创建采购单或完整核验完成；本地待核对受理项不设数量上限。旧批次保存的上限恢复后也不再限流。

共享浏览器的短操作仍统一调度，避免同一页面并发改表单造成串单；没有为每张单新增浏览器或无限线程。已受理平台任务可并行处理，结果按稳定item_id、订单身份及执行令牌回写，完成先后不能改变提交/展示顺序。仅勾选范围派发，单项失败独立处理，取消、重试、删除失效屏障和未知受理不重传仍保留。平台自身响应时间与限速不由本机解除。

## 验证方式与边界

固定冻结0.52.6为基线，新旧AB BA AB独立进程各三次：实际缓存get/put、两仓多版历史目录与选中读取、实际下载入口的本地HTTP反复响应、实际Runner慢平台模拟。内存分别报告工作进程RSS、Node/driver及自有进程树，Buffer保留不是整机RSS；冷/热或不同阶段不混用。上传调度对照比较原始订单结果和顺序；受理时间及最大待核对受理项是刻意改变的行为，不能声称真实平台吞吐已实测。

完整结果、文件字节、摘要、顺序和必要错误预期先验证，再比较资源。实际打包EXE另验缓存兼容/损坏、恢复取消/被替换/完整保存、包内Node及组件、采购9单连续提交与稳定回写，以及既有签发/导出和搬迁后重开。仅使用隔离合成资料和本地HTTP，无真实浏览器/平台调用。

完整实测数字、失败证据、构建身份及已知限制见本版独立交付报告。计算worker副本、导出旧快照、经营分析流式输出等其余候选本轮不实施。既有高缩放布局挤压和旧browser_status_ui销毁回调不在本轮修复范围。
