# 0.52.5 签发反馈与原修订导出修复

## 业务现象与已确认问题

0.52.3现场“签发并导出”停在“签发结果待核，0/20”，完整详情只有路径和空白原因。任务a4089c78c6e14d029029bd6f23e0e7e8、ecba7f88d6184d8ea57d2e46ebf37311未在本机执行，现场库尚未读取。用户确认单独签发也未显示“已自动归档：BH… V…”；不能据此宣称订单已成功落库后又丢失。

冻结源码确认：原签发异常只保留str(exc)，空MemoryError、AssertionError等会失声，跨进程又丢失类型及堆栈。旧通用导出提示把归档异常也描述成文件占用。单独签发在后台忙、只读、输入失效或非今日等条件直接返回，保留旧错误。提交后完整读回全部所选门店，再开始导出，会额外保留多店完整结果。

上述是已确认的代码问题。没有现场异常类型、堆栈或内存采样，不能认定原始故障就是内存不足，也不能认定0/20表示全部未签发。新旧合成规模对照及最终EXE结果见独立交付报告，不把合成试验当业务原单复现。

## 本次修改

- 显示“失败阶段、原因、提交状态”，原始异常无文字时仍保留类型。独立诊断写入当前资料位置settings/diagnostics/work-io-任务号.json，含异常堆栈、操作阶段及已准备的确切修订身份，不包含商品结果或浏览器凭据。诊断写入失败不代替原错误；回执暂被数据库占用也不掩盖首异常。
- 区分未开始最终提交、最终提交结果待核、已提交。提交后按确切oid、日期、门店、修订和摘要核对数据库记录，再反馈成功。列表刷新或展示失败单独说明，不改称签发失败。
- 单独签发入口明确说明未开始原因；取消选择或确认会更新本次状态。历史已签发原修订重导继续保留，不新增审批条件。
- 首次签发提交前保存本批确切修订身份。身份准备不是签发成功，恢复仍逐项检查数据库原修订，不猜号码或替换当前版本。
- 导出只同时读回一店完整原修订，完成后释放，再处理下一店；同店两仓复用这次读取。保留完整快照与业务指纹校验、原文件顺序、事务原子性、并发修订检查、取消及失败回滚。模型、数量、预算、箱规和业务单据规则不改。

## 使用与处理

正常签发完成应明确显示BH签发单号及V修订号，订单跟踪查询同一主库。点击后仅有旧错误不代表本次成功。

如新版仍失败，复制弹窗前面的阶段、原因、提交状态，以及“诊断记录”对应文件。0/20是本次生成文件数量，不能替代签发状态。已提交的任务在“导出任务与恢复”核对确切原修订后补导出，不重新签发。

旧版没有留存确切修订的失败回执继续保守阻止自动恢复；本版不把旧空白原因补成推测，也不会自动重放现场任务。此前0.52.4搬迁修复仍保留，软件包和资料目录分开；不自动替换正在使用的软件。

## 验证范围

仅新建隔离数据库、合成门店和私有应用资料验收，不调用真实平台。覆盖空异常、原始堆栈跨进程、回执占锁、提交前整批回滚、提交后失败按原修订恢复、逐店完整读取、单独签发成功和订单跟踪、取消及原修订重导。实际项目定向回归、同输入规模对照和独立EXE验收以交付报告最终结果为准。
