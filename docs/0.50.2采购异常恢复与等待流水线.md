# 0.50.2 采购异常恢复与等待流水线

本版处理两件事：异常任务能明确结束并重新做；平台等待期间能继续提交后续订单。签发、付款、模型计算和供货归属保持。

## 卡住的采购怎样重做

在“翱象批次作业”选择原采购预览或上传批次，勾选准确门店、仓与补货单号，点击“结束所选任务并重建预览”。阅读所选范围、旧任务与原采购号后确认。新预览采用当前有效签发与付款，完成后仍需核对并单独确认上传。

未取得回执、平台处理中、部分失败及已成功任务均能主动重建，不要求先核清旧任务结果。原平台采购单不会撤销；确需重做时，业务负责在平台核对并处理重复部分。取消确认不改变任何任务。

正在执行的动作先点“停止本批剩余动作”，等待安全结束。不能强杀提交中的请求。其他批次有动作时，重建按钮暂不可用；空闲后可操作。

只处理勾选的原仓单；同批未选订单保持。旧采购记录、冻结文件、受理回执、原采购单号及新旧关系保留，旧任务不再占用新预览。旧回执晚到只记录在旧任务，不覆盖后继。已删原单不能按同名或同号新单重建。重建失败可继续同一新预览准备，不会因应答丢失反复产生后继。

“继续核对原采购任务”仍沿用原身份，不再次上传；“结束本批并新建”仅迁移原任务执行，不等同于主动重建采购。需要重新导入时使用新增的完整名称按钮。

## 平台等待怎样重叠

确认批量上传前，可设置“本批平台同时处理上限”，默认 2，允许 1–4。设为 1 时按单顺序等待。该设置只影响下一次确认上传的批次，属于应用调度上限，不是平台吞吐承诺。

上传仍逐单使用共享浏览器；A 取得唯一受理回执并保存后，先提交 B，再核对 A 的平台任务、采购主单与商品明细。核验成功释放一个位置后，优先提交下一单。数量、金额与归属的完整核验保持。

“平台处理中”不是失败。已受理任务等待一轮仍未完成时，保存确切任务号并释放共享会话，稍后再查；其他作业可以获得会话。暂停、关闭和重启后继续读原状态。单项业务异常挂起该项，其他项继续；连接、登录异常仍暂停本轮，以免在错误身份下派发。

无回执和多回执不会自动猜成“未上传”，也不自动重传。此类任务不再永久挡住业务主动重建的出口；已受理上限只统计本轮有唯一回执的等待项，未知平台结果不等于没有在途请求。

重建暂停所选旧采购的本地周期收货计划及待执行收货任务。旧已确认实收、付款和签发事实不自动清空。新采购获得自身采购号后，业务按正常入口配置新同步。不同执行批次有各自上限，不是跨全部批次的平台全局配额。

## 已验证与现场限制

验证使用隔离 SQLite、合成原生文件和封闭平台替身；真实本地 Node 组件验证重建登记及恢复，实际 EXE 验证界面到组件的链路。未调用真实平台，也未清空正在使用的资料。

尚未测量真实翱象平台的连续导入吞吐、限流及低配置电脑表现；不能据隔离调度通过承诺倍速。建议业务先沿用默认 2 单观察。原 0.50.1 rc3、此前全部交付及失败验收记录保留，源码与包分别独立封存，不自动推送或合并。
