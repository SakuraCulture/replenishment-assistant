# 0.51.5 聚水潭仓绑定纠错修复

本轮修复山东仓、河北仓账号或浏览器绑反后的恢复链路。计算模型仍为0.3.6-rules，沿用0.51.4的断货双零、首铺量、经营分析和同步启停规则。本轮不调整订单、计算参数、仓归属或翱象配置。

## 原因及原行为

`components/jst_catalog/src/service.mjs` 的账号保存原先先检查未完成任务，再比较核验后的新绑定。即使实际账号与浏览器没有变化，也会被旧任务拦截。停止采集只请求安全停止当前动作，正确保留平台受理号和待采用文件；这些记录却继续占用旧绑定。恢复旧任务又必须核验旧账号。两仓互换还会被另一仓仍保存的账号或浏览器占用，形成业务上的循环阻塞，并非SQLite写锁死锁。

禁止旧账号文件被用作新仓资料、两仓不能共用同一账号或浏览器的保护有必要；缺陷是没有与这些保护配套的明确纠错出口。

## 修改范围

- `service.mjs`：有效核验后的原样保存直接返回原绑定；仍保留真实变更的检查。增加预览/确认纠错命令，旧任务所有恢复、回写和采用路径检查本地结束标记。
- 新增 `binding-recovery.mjs`：只按已确认的一仓或两仓范围处理；核对指纹并自动持久备份、回读校验后，在一次任务状态原子写入中结束未采用项、解除对应绑定。原件、平台受理状态、已采用项和未选仓保留。
- 绑定版本单独保留失效代次；旧核验、旧命令重放和旧回调不能在解除后重新生效。已完成纠错的同编号重试只返回原结果，不能清除后来保存的新绑定。
- 新增 `catalog_binding_guard.py`，在默认仓资料、分配库存、定时补货及独立门店缺货分析的采用入口使用同一跨进程SQLite互斥锁。正在采用时不解除绑定；解除后旧内存项先读取当前任务与绑定身份，不会写回旧资料。
- 在采用互斥锁内向原采集服务读取最新状态，不跨进程打开后台正在原子替换的Windows任务文件；服务读取失败则拒绝采用，仍完整检查当前任务、退役状态和账号。
- 启动连接遇到纠错中标记时等待明确确认；纠错后的自动准备只核验浏览器，不猜测物理仓对应关系。首次正常自动配置行为保留。
- `catalog_sync_ui.py` 新增“纠正本仓绑定”“纠正两仓错绑”，确认框列出原公司和未完成项数量。取消不变更，确认后提示备份位置并要求重新获取资料/检查计算；历史记录明确显示“本地已结束”。

## 业务操作

在“聚水潭商品资料 → 手动配置与启停（高级）”中，两个仓互换时使用“纠正两仓错绑”。等待当前任务安全停止后核对确认范围，再逐仓选择正确专用浏览器、核验公司、勾选物理仓确认并保存。最后获取并采用正确仓资料，重新检查和计算未签发结果。只有一仓错了则选择该仓使用“纠正本仓绑定”。

停用仍只控制后续自动同步，不等同于纠正账号。纠错不撤销平台导出；原任务可能继续在平台生成文件。本地已结束项不再自动接回，已采用的旧资料也不自动清空。不能把完成绑定当成已经刷新资料。

## 验证及限制

隔离验证覆盖原样保存、两仓交换、单仓范围、取消、旧文件与平台回执保留、采用互斥、备份失败、状态写入失败重试、旧核验失效、重启及旧命令重放。真实Qt窗口调用真实本地Node组件；平台身份核验使用模拟结果，没有调用真实聚水潭或翱象。

全量回归、实际EXE验收及交付哈希以 `releases/0.51.5/rc2/交付报告.md` 为准。旧失败日志保留；未在业务电脑实测。本轮不提交、打标签、推送或合并，使用带完整SHA256清单的独立未提交源码快照构建，旧交付保留。
