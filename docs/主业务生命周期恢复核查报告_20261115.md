# 主业务生命周期恢复核查报告

第一轮已在0.53.8当前主线中确认4项恢复与状态衔接问题。其中两项用隔离队列和真实源码Qt控件复现，另两项用隔离库存数据及故障注入复现。另有1项可复现的旧入口范围问题，当前正常主界面已不走该入口，单独记录，不当作业务现场已经发生的故障。

这些问题主要是取消后的状态没有正确衔接、失败后留下其他批次暂停，以及成功提交后的结果没有完整反馈给调用方；本轮未证明它们是SQLite物理死锁，也不能将其认定为业务电脑所有既往异常的共同原因。

## 已确认的问题

### F01 取消未开始任务同时封住已受理任务的继续核对入口

批次中一单已经被平台受理，另一单尚未开始时，业务点击“取消本批未开始的剩余任务”，应停止未开始部分，并保留已经受理单据的原结果核对路径。

当前`src/aoxiang_workflows.py:374`的`cancel_queued`直接把整个批次设为CANCELLED，成员仍分别是ACCEPTED和PENDING。原平台任务号没有丢失，但`next_queued`不再读取这个批次；`resume`、`execute_selected`、`retry_items`也不能继续该已取消批次。界面中继续原批、重试原批及仅执行勾选入口均不可用，ACCEPTED行没有继续核对按钮。

隔离复现保留了唯一原受理任务号，关闭后重新打开队列仍不能排入原任务核对。再使用现有“结束本批并新建”，只能把尚未开始的一单转走，已经受理的一单仍留在已取消旧批。这不是要求重新上传的理由。

代码依据：`src/aoxiang_workflows.py:80`、`:292`、`:303`、`:374`、`:407`；当前按钮和取消说明位于`src/aoxiang_workflow_ui.py:279`、`:331`及`:537`。探针见`ax-cancel-accepted-upload/observation.json`及`source-ui-report.json`。

建议优先修复：取消范围落实到未开始成员，保留已受理项可继续核对的状态和原任务身份。若用户明确停止等待，仍保留只查询原结果的恢复入口，不能把“取消未开始部分”变成终止已受理项的所有后续核对。

### F02 取消上传后再次确认同一预览返回已取消旧任务

业务已生成采购预览，确认上传后在真正上传前取消，再回到同一预览重新确认。这时预览仍为READY，确认上传按钮仍可点击。

当前`src/aoxiang_workflows.py:139`按原预览和相同订单范围查重，找到相同历史上传批次即直接返回，没有区分它是否已经CANCELLED。`src/aoxiang_workflow_ui.py:457`随后切换到这个旧批次并检查调度队列，结果没有任何新任务可执行，也没有说明为什么本次确认没有生效。

已通过真实源码Qt控件、真实确认弹窗和生产队列方法复现：点击确认后返回同一个CANCELLED任务，下一排队任务为空。

已有绕行方式是在已取消上传批次内使用“结束本批并新建”，可保留原采购包身份并重新排入尚未上传部分；本轮在独立合成副本中验证了这条路径。但是当前确认按钮不会引导到它，也不会给出具体提示。

建议修复：幂等查重区分执行状态。未开始即取消的原任务应明确衔接现有恢复路线；仍在运行、已经受理或结果未知的任务继续使用原身份核对，不能统一另建采购或重发。重复确认不应无声返回一个永远不会被调度的批次。

### F03 新批首次分配前失败没有恢复另一仓原批的运行状态

隔离案例先登记一个河北仓原批，状态为active且尚有待处理成员；随后建立山东仓新批，在新批已登记、首次分配尚未开始时注入异常。

`src/jst_batches.py:209`登记新批时调用`_pause_other`，把其他active批次持久改成paused，并增加其控制代次。后续失败时，`execute`的异常路径仅暂停新批，没有恢复由本次切换暂停的原批。

结果是河北原批由active变成paused，山东新批也变成paused，自动分配检查找不到active批次。两边都没有发生库存分配，河北原批成员和数量未改，但它不会自行继续。

代码依据：`src/jst_batches.py:171`、`:209`、`:302`、`:318`及`:354`。探针见`jst-new-batch-failure-pauses-peer/observation.json`。

当前可以手动选择河北原批再继续，本轮已在合成副本验证它仍能正常生成。问题是新动作失败后，没有回到此前可继续的状态，影响扩大到了另一仓；这不是原订单丢失，也不是整个软件都无法查询。

正常切换批次时暂停旧批，是当前调度规则。本问题限定在失败后的恢复缺口，不把正常切换规则本身视为缺陷。建议记录本次切换前的批次与控制代次，在尚未发生分配等新事实的失败场景中，按并发校验恢复仅由本次动作暂停的原批；存在后续人工决策时保留其新状态，不能无条件激活所有历史批次。

### F04 分配已保存但批次收尾失败时成功回执未交给界面

`src/jst_batches.py:337`调用库存生成服务完成订单、库存预留与步骤记录提交，随后在另一事务更新批次最终状态。若后一个写入失败，函数抛出异常，没有将已生成结果清单作为结构化结果交给调用方。

隔离故障只注入在最后的批次状态写入：数据库已存在1张有效生成单、1条步骤记录及对应库存预留，业务事件也已发出，但对调用者返回的是异常。再走“继续原批”，会得到“本批没有可继续的任务；已生成单可直接导出”。

代码依据：`src/jst_batches.py:337`及`:338`、`src/jst_ui.py:236`、`:264`及`:271`。探针见`jst-post-commit-finalization-failure/observation.json`。

当前窗口可能已经通过业务事件显示生成单，结果页也能查到并导出；本轮验证了结果页仍显示该单ready。因此不能把此问题描述为生成单丢失。缺口在于收尾异常没有带回“业务已保存”的准确批次身份与清单，界面缺少就地恢复状态的衔接，容易让业务误以为需要重新分配。

建议修复：区分业务提交和批次收尾，保留已生成清单、批次ID及明确提交状态。收尾失败时展示“已保存，批次状态待恢复”，根据持久成员和步骤修复控制状态，直接打开原结果；不重新生成或重复预留库存。实际提交结果未知的情况仍先核实，不能一概报成功。

## 旧入口问题与功能缺口

### L01 旧版勾选重试入口会扩大为整批执行

`src/jst_tasks.py:44`的`retry(path, heads)`使用所选heads定位一个原批，但调用`preview_existing`时未带入所选范围，随后激活整批。后台`drain`再处理所有未完成成员。

隔离案例只传入第一张仓单，随后两张仓单都被生成。`src/lifecycle_home_ui.py:98`仍有“重试勾选未完成生成”的调用，但当前`StageDialog`在`:274`针对jst改用新的ResultsPage并提前返回，因此本轮没有证明正常当前主界面能走到旧按钮。

它属于可调用旧代码的潜在范围问题，不计入上面4项当前链路问题。应封住旧入口或改接有明确范围的现有流程；仅向预览函数补传heads仍不足以保证后台不会扩大执行范围，必须同时检查调度范围和原库存顺序。

### G01 统一恢复入口尚未覆盖所有环节

现有历史版本、原批继续和签发导出恢复能解决部分情况，但不是用户要求的统一“恢复并继续”。例如F01缺少已受理项的原批恢复入口，F03没有本次切换前的完整恢复关系，F04缺少提交成功与收尾失败之间的回执衔接。

这是一项明确功能缺口，不能只增加一个按钮就宣称完成。需先补足相关操作身份、恢复依据与成功事实读取，再把既有恢复能力集中到当前业务页。

### G02 原执行批次直接追加订单当前不支持

`src/jst_batches.py:156`检查原批成员集合，拒绝加入其他订单。这符合当前冻结执行计划的规则，不是本轮新发现的回归。要支持同一业务批次追加，需设计关联追加执行或续批，并明确使用原批剩余库存还是新一轮库存，不宜直接放宽成员校验。

## 修复顺序建议

先处理F01和F02，贯通取消剩余、继续原任务及再次确认之间的状态，保留已受理身份。再处理F03和F04，补齐切换失败的范围恢复和提交后的结构化结果反馈。这四项都可以先围绕现有入口作小范围修复，无须改变计算、数量、金额、箱规、默认并发或库存分配顺序。

统一恢复入口以这些准确结果为基础实施，不能用清空队列、删锁文件、重新下单或初始化充当恢复。原批追加订单与已收货更正规则单列设计，不与上述修复混在一起放宽。

本轮没有进行这些修复。实施后应先把本次探针改为正式回归，验证故障不再出现；原保护168项继续保持，并补实际EXE中的取消后恢复、混合受理批次、分配失败恢复、退出重开和其他独立业务可继续的验证。
