# 0.45.2 删除性能优化

本轮接续 0.45.1，基线为 1c020e1。候选分支为 perf/deletion-load-0.45.2。

## 实际瓶颈

冻结历史共有 39 个父单、4 个业务日及 16,218 个内容块。删除最新一天一个父单时，需要清理该天的共享签发作业与当前草稿。两条记录保存完全相同的分块清单，每条逻辑内容约 1,351 MiB。原流程对两条记录分别完成完整摘要核验、逐行过滤和输出摘要计算，重复读取、解压和解析同一份内容。

函数级剖析与文件格式核对表明，本次选中日期的作业已采用分块格式。历史库中仍有旧格式快照，但不能将本次主要耗时统称为旧格式转换。剖析包含分析器开销，仅用于定位。正式对照单独计时。

删除少量订单仍有全库工作，是因为同步回收必须确认其他订单、历史作业、草稿、计划值和资料目录是否继续引用共享内容与原件。当前引用缓存仍需要核对对应原始压缩字节。索引保留原有全文匹配语义，因此仍需扫描索引文本。

## 本轮实现

准备阶段按业务日和原始快照 SHA256 复用已经完整核验的重写结果。相同日期使用同一组待删门店。缓存只存在于本次操作，保留小型描述和输出树引用。不同业务日分别计算，草稿自己的索引摘要仍逐条核验。

提交前继续在写锁内比较完整源记录集合与内容摘要。准备期间有其他连接提交时，现有 data_version 机制继续使内容块引用复用失效，转为重新核验。取消、异常、回滚及提交边界沿用原入口。

临时编辑器中同一个内容块再次出现时，先查本次已写入的哈希集合，避免重新压缩和重复 INSERT。内容编码、哈希及后续读取校验仍执行。

生产逻辑涉及 data_maintenance.py、maintenance_storage.py。删除对象、同店同日双仓父单范围、共享原件归属与单事务回收语义沿用现有规则。应用版本为 0.45.2，模型仍为 0.3.4-rules，存储格式仍为 2。

## 验证方法

所有测试使用新的 QA 目录与隔离数据库。以 0.45.1 验收提交归档作为对照，使用同一 Python 环境，AB/BA 交替串行运行。正式场景包括大库已有引用缓存三轮、大库首次无缓存两轮、三日各一父单两轮、合成首次引用核验三轮。

已有缓存来自旧 QA 验收库，只复制两张维护引用缓存表。完整冻结历史作为各次删除输入，旧缓存缺少的条目仍走完整核验。首次无缓存场景直接复制没有维护缓存表的冻结历史。“无缓存”指业务引用缓存，操作系统文件缓存没有清空。

计时包括预览、准备、执行与提交，排除副本复制和业务签名生成。RSS 每 30ms 采样删除工作进程。Windows 进程读写计数包括系统缓存服务的字节。临时库体积记录准备结束时文件长度，未声称覆盖全部日志文件峰值。

对照比较预览 token、删除结果及逐表有序业务签名。仅沿用既有 jobs.revision/saved 动态字段豁免，内容块和维护缓存的物理布局由专项验证覆盖。删除事件采用两端相同固定时钟。

四项新增回归覆盖相同签发/草稿内容的旧格式与分块格式等价、重复内容对应错误草稿摘要时拒绝、相同内容跨日按各自门店范围处理，以及重复临时块只压缩一次。原有并发、取消、共享资料和跨库回滚测试继续执行。
