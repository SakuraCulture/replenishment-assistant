# 0.22.0：回传后生成与付款来源

订单生命周期保持：签发 → 回传 → 付款 → 收货。聚水潭导入单是执行附件，生成、导出、锁单均不自动确认付款。

## 如何使用

1. 回传处理或批量导入中确认完整回传单，系统先保存回传，再后台自动生成聚水潭导入单。订单跟踪下方显示生成进度及停止／继续按钮；重启恢复未完成任务。
2. 当前仓库存基准优先，没有基准时采用已保存的对应仓资料。需要最新库存时，在回传处理／订单跟踪的“聚水潭导入单 · 生成与导出”面板更新资料。已生成单不因资料更新自动重分配。
3. 聚水潭面板勾选订单可导出、看分配明细、下单后锁定。缺资料或商品异常会显示待处理原因，可修正后重试；普通库存不足按箱规向下分配。不足一箱分配0。
4. 文件为商品编码、单价、数量、订单号四列；最后一列是本应用分仓补货单号。每店每仓一份，同名安全覆盖。前三列及分配规则保持。
5. 外部导入及下单无异常，且确认已付款：进入付款核对，勾选一单，点击“使用聚水潭导入单作为付款来源”；或者用“导入门店付款单”拖入四列文件。两条路径进入同一付款确认表单。
6. 有实际调整或需外部单号：导入原13列聚水潭付款文件。文件没有补货单号时明确选择目标仓单。相同订单的两份付款来源必须选一份，不自动相加或覆盖。
7. 聚水潭内部单号可以在直接回拉时缺少，提示未提供；不能用补货单号冒充。以后导入实际付款单可校准，页面展示原／新数量、金额和外部单号。旧原件保留，不改变仓占用、锁或已保存收货数；已有下游须重新核对。

付款仍与回传要货量大于0的行比较，收货与付款正数量比较。0、空白、缺行最终均为0，来源提示分别保留。原计算、预算、签发和原有导出不变。

## 使用边界

- 自动生成异常不会撤销已经保存的回传。停止后当前安全提交完成，已生成单保留；可继续或修正后重试。
- 已锁单跳过重新分配；新仓资料已扣减这些订单，不能重复扣。付款导入本身不操作库存。
- 未锁已有生成需要重分配时，继续使用明确的全仓未锁范围核对；不在后台默默改动其他单。
- 默认资料的库存准确性依赖业务及时维护。生成文件不代表已在外部下单或付款。
- 旧历史文件不回写；新增任务表为增量保存。回退需旧包和升级前备份，不用旧EXE写新版资料。
- 四列文件在真实聚水潭接收端尚需核验，不能把本地通过当成外部接收成功。

## 人工试用重点

- 新回传确认后待付款，后台有生成进度；生成后仍待付款。
- 两仓订单分别输出，末列补货单号正确，长编码无丢失。
- 直接采用生成明细和四列文件回拉的数量金额一致；没有虚构外部单号。
- 实际付款改量后能看到原／新差异，确认后原签发和收货数不变。
- 锁单后刷新仓资料、再次生成，不重复扣锁单；付款校准不重新分配。
- 取消、关闭后重开，可继续未完成任务，不重复生成。

## 代码查找与复跑

`order_lifecycle.commit → jst_tasks.enqueue`在同一回传事务记录任务；`jst_task_ui.Generator → jst_tasks.drain → jst_orders.prepare/commit`后台恢复执行。已准备操作先保存再提交，崩溃重试复用原操作ID。分配核心`jst_allocation.py`未改。

`jst_exports.export`添加最后一列；`lifecycle_io.payment_specs/scan`识别四列及原13列；`lifecycle_batch`保留整单来源选择；`jst_orders.payment_plan`和文件适配共用`order_lifecycle.make_plan/commit`。
