# 0.49.0 付款单识别与采购状态

本轮接续0.48.7，实施[已确认方案](plans/付款单分层识别与采购状态同步修正方案_20261108.md)。不改变计算模型、预算、箱规、仓归属、分配算法、默认参数或删除事务。

## 我拿到聚水潭付款明细，怎样导入？

1. 在订单跟踪进入付款核对，勾选需要处理的仓单，再导入付款文件；也可从批量导入进入。先限定原订单范围更方便，但不能把范围内的一张误判为全局唯一。
2. 原表至少包含“内部订单号、商品编码、数量、商品金额”。店铺名称、下单时间、买家帐号和辅助码可保留；“买家帐号／买家账号”都支持。不要求补写签发号或猜仓。数量仍按现有库存单位约定读取，不擅自乘箱规。
3. 选择“本批付款表来自”的真实聚水潭企业。此项来自已有已核验连接的企业身份，不以山东／河北仓、手机号或买家帐号猜账套。同批文件来自不同企业时应分批处理。无核验企业身份，仍可逐单人工确认付款，但不能记住一个虚构来源范围。
4. 查看自动带出的门店、仓、日期和签发单。先用已确认内部号原关系；否则用门店对应、生命周期、日期及汇总筛选，最后逐商品对照实际生成单。日期和首次付款／更正仅排候选顺序，唯一性仍核对相关全部日期。
5. 无唯一结果时，选中完整来源组，点“查看识别依据与候选”。看到多候选、缺行、额外商品或混仓，应核对原业务；需要拆组时由人明确选择行和签发单，不默认第一张，也不丢行凑匹配。店名只有空格、全半角差异可归一；业务别名首次需要确认。
6. 点“核对并准备保存”，查看整批明细和差异。此表确为已付款明细、金额确为实付时，再勾选完整范围确认并保存。付款事实与需要记住的内部号／门店对应一起成功、一起回滚。

## 店名对应确认错了怎么办？

展开“更多候选筛选”，进入“维护已确认门店对应”，选中该条名称对应并确认解除。解除前备份对应记录；签发、付款和内部订单号的原关联不删除。新来源单重新确认名称即可。已存在内部订单号不能通过解除名称对应改绑别的订单。

“筛选候选日期”仅缩小显示；“扩大到全部日期”恢复全部候选。“刷新索引并重新识别”只读变更快照。读取或识别取消后，需重新完成识别才能保存；取消不产生付款或对应关系。

## 翱象平台已经作废，为什么本地还有付款和订单？

平台状态和本地事实分开保存。已作废且主子单身份一致、没有冲突实收时，停止常规查询，不产生最终实收待办；保留签发、付款、采购号和原件，不记收货0、不自动退款或删除另一仓。

若已作废但有部分实收、原已完成／保存实收，或主子状态冲突，则显示“平台已作废，但存在实收或状态冲突”，保留已有事实，需核对后续业务处理。查询失败不会替换上次已核验的平台状态。

## 为什么收货同步中不会再拉出已删的旧订单？

从采购批次进入“本批收货同步”，只带当前批次或勾选范围；全局管理在“全部有效采购单同步”。正常池校验本地原OID、签发修订、仓单可见性、付款版本和平台终态。旧任务缺原身份时，读取原冻结依据复核，不能只凭单号关联同号新订单。

“显示历史及失效关联”是只读审计；失效、作废和完成项不能勾选执行。启用周期、排队、派发和轮询中都重查本地依据。删除后的调度投影另行退役；即使投影尚未更新，执行校验仍拦截。运行任务请求协作暂停，不强杀或重传原受理任务。

## 已有采购单号，还要填日期和店名吗？

正常精查只填准确采购单号，捕获并校验实际查询请求，拒绝隐藏日期或门店筛选；返回主子单仍必须逐项核对原身份和明细。若网页日期控件无法安全清空，只有在尚未提交任何导出意图、且原件证明制单日时自动降级。无可信日期会明确停止，不按今天猜测。已受理／受理未知的任务不会换查询重提。

本轮仅在本地离线Edge页面和协议夹具验收。真实翱象网页是否支持清空全部日期仍待现场验证；本轮没有登录真实平台或创建采购单。

## 资源与证据边界

付款识别模块在实际导入相应付款表时才加载。首次索引逐份解码当前签发和有效生成快照，保存名称、范围、汇总和版本引用；不复制商品大文本或扫描全部旧修订。已有索引只重读元数据及必要完整候选；缓存损坏可重建，原损坏文件留存，不代替正式复核。取消可能留下已校验的缓存进度，但不写业务事实。

5／25／100店合成基准分别测首次、已有索引、扩大检索及取消；数值见交付报告。数据SKU少、单轮、同机缓存未清，不能作为业务电脑性能承诺。Windows进程I/O含系统缓存，内存是实际工作进程，不代表物理磁盘或整机。

现有QLabel销毁后的回调警告不在本轮修复范围。旧交付保留；使用新完整应用目录启动，关闭旧版后替换入口。证据与包路径见[交付报告](../../releases/0.49.0/rc1/交付报告.md)。
