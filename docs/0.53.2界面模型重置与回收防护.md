# 0.53.2 界面模型重置与回收防护

2026-11-14 11:04:38，实际0.53.1 rc1发生原生崩溃。系统事件与转储确认：Qt对象析构链中触发`_purecall → abort`；当时运行阶段为RUNNING。转储缺少相关堆对象，未还原具体控件或最初的Python回调，不能把11:04:37存在草稿保存记录当成保存逻辑导致闪退的证明，也不能将此次问题归为旧迁移退出弹窗。

## 本轮修改

1. **修复已复现的表格模型缺陷。** GoodsModel在手动beginResetModel/endResetModel范围内调用QStandardItemModel.clear，而clear自身还会重置。Qt明确报告嵌套与不配对。改为在原有单次重置内清空行，保留数据、顺序、排序和筛选。相同4项真实Qt测试，旧版4失败，新版4通过；没有放宽预期。
2. **约束循环回收线程。** 普通引用计数继续执行；停止由任意分配线程触发自动循环GC，在GUI线程按原阈值分代调度，不降低工作并发。退出先等待后台结束，在QApplication仍存在时回收与处理延迟删除，再恢复原GC开启状态。不全局替换gc.collect，显式后台回收只记录诊断。
3. **保留首个错误线索。** Qt警告、致命消息及其Python调用栈写持久日志；尝试启用faulthandler，故障栈文件位于不可移动的本机控制诊断目录，不占用业务资料目录句柄。诊断回调不创建任何窗口，正常运行的业务错误提示保留。

## 验收边界

使用新建合成资料，验证实际准备、默认并发2计算、取消准备、循环保存与表单重建、排序筛选、正常退出和重开，并验证计算结果和SKU顺序。独立EXE的具体结果见本轮交付报告。未读取或重放真实业务操作，未修改真实资料；旧包和失败证据保留。

本轮没有复现原始`_purecall`，不能声称已找到并修复其唯一根因。官方Shiboken实现与合成探针证明，后台释放GUI包装会进入主线程延迟删除队列；循环GC是入口之一，后台释放最后引用也是入口。GC调度防护不覆盖所有末引用释放或既有内存损坏。Windows fail-fast也可能绕过故障处理器，新增日志不保证每次都能还原全部调用栈。
