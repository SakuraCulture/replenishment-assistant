### 1. 冷索引为什么还会等

`history_tasks.py:6–46`：HistoryReader 使用 Windows spawn；20ms轮询消息；同一时刻一个运行请求和最新一个待处理请求；generation确保旧结果不会刷新新查询。关闭时退出自有只读进程，未把这套强制退出策略用于归档写事务。

`history_read.py:98–139`：决策复查 `list` 先取 `repo.headers()`，逐个 `cached(...)` 后才检查日期、门店、仓和搜索。因此“只查今天”也不能保证首次只解码今天的数据。进度在每单完成后回报；整单解码是大块等待点。

`lifecycle_home.py:12–75`：订单跟踪已先按日期筛选，再读取所选单；每页50是显示分页，不等于仅处理50单。不能把两个页面的查询路径混为一谈。

建议顺序：先把廉价日期/订单身份条件推到昂贵快照读取之前，保持原顺序与商品搜索语义；显示“准备索引/读取第n单/完成”、处理计数和最近更新时间；增加安全停止读取入口；确认等待热点后再做分块检查点。验收必须覆盖冷/热缓存、窄日期/不限日期、大单、取消后重查，不能只看小包演练。

### 2. 增长不是“每次把一切复制一遍”，也不是已经解决

`source_archive.py:10–23` 用内容哈希键和 `INSERT OR IGNORE` 留存原件；`storage_chunks.py` 用不可变内容块复用。同日更新仍可能保留历史修订和新块；不同内容原件、生命周期原件、导出文件会继续增长。

`storage_maintenance.py:10` 起只生成经校验的新数据库副本；旧格式副本中的清理/VACUUM不能被描述为日常自动回收。当前未发现可安全删除“所有无用块”的用户功能。

先补只读统计：数据库/原件/块/索引/备份/导出目录分别占多少，按月新增多少，备份耗时多少。索引是可重建缓存，签发/原件是证据，不能同一保留策略。备份至少验证能在新目录恢复并对照哈希后，才考虑按业务日期封存。不要先做不可恢复的历史删除。

### 3. 版本与回归应当怎样管

`version_info.py` 从 version.json 和 build_info.json 合并诊断身份；发行包保留构建提交与校验值。下一步先用一份“机器/使用人/应用版本/构建短哈希/更新日期”登记表和唯一推荐版本说明；无需立即建自动升级服务。

`dev.ps1:51–54` 当前运行所有单元测试。0.17.1原发行证据记录195条常规单测19.335秒（不是本次重跑），与此前“38项回归”不是同一统计单位。本次38条是新建的人工业务用例，也不是自动回归总数。

建议三层，保留原预期：

1. 快速冒烟：输入识别→两店双仓→签发→三环节关系→历史取证→参数非法与试算隔离。改动时跑，目标耗时需实测后确定。
2. 相关专项：按改动模块选择路由×预算×一箱×在途、存储取消/冲突、导出类型/顺序、并行有序等组合。不要只按单文件名挑测。
3. 发行全量：真实数据严格逐项对照、全部单元、兼容恢复、实际EXE、交付哈希。只在候选发行和跨层改动执行；性能测试与功能快测分开统计。

不建议为“减少测试数”删除真实事故回归；可以合并重复初始化、共享只读样本和去除没有新增断言的重复跑法。

### 4. 参数治理现状

`work_repository.py:37–58`：方案保存为不可变的新版本；标准方案只读；门店默认支持比较原值后保存，防止并发覆盖。`parameter_schema.py:33–53` 校验完整键、权重和、概率范围、仓周期及开关。

`parameter_ui.py:28/127–135/197–201`：生效核对展示标准/方案/打开时门店/当前编辑层，应用前逐店列变化；试算完成明确不修改正式结果。`parameter_scene.py` 明确保存默认只供以后作业带入，不自动改当前工作。

`workbench.selected_settings`、`batch_service.calculate_store`、`normal_orders.confirm` 保存实际配置和签发快照；`history_forms.py:35–57` 可查询当时参数与单SKU当时事实。因此“历史单没有参数版本、一年后只能猜”不符合当前实现。仍需区分“存了最终值”和“记录了每一次谁改了什么”：后者不完整。

“为什么按5%补”也要纠正：当前5%是 `allocation.py` 的固定有限超支政策，不是可随意编辑的参数，也不是每单都按预算多补5%。预算按设定数分配后，最多追加一个最小出库单位，总金额不超过105%，0预算不追加，不超过模型候选。预算报告保存 ratio/ceiling/max_units，触发商品保留 `_budget_overrun`。历史解释应同时看模型规则版本和实际触发审计，不只看参数方案名字。

下一次字段格式变化前，单独加入参数格式版本、显式转换函数、缺省来源说明、老新快照同参数对照；迁移在副本运行并保留旧文件。当前不擅自给旧历史补写不存在的参数来源。
