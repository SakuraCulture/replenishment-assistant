# 0.10.0 分仓确认单与门店默认

基线：0.9.2 / 6894be792e99f9aa179c1fc5ac8a8e24ffe134b4。独立分支 feature/warehouse-confirmations-0.10.0。模型仍为 0.3.3-rules，仓归属仍为 0.5.0；JSON/SQLite/每日作业格式不迁移。保留 0.9.2，不合并、不推送。

## 使用流程

1. 检查文件后设置各店主仓、从仓和完整参数。点击“保存主从仓与参数为门店默认”，下次检查相同门店编码时自动带入。预算单独勾选保存，默认不把临时预算写成长期默认。参数编辑内的主按钮为“保存为门店默认并应用”；“仅用于本次”不会写默认。
2. 按现有方式计算、选新品和预览预算。选择“导出加盟商确认单”后，逐店列出河北/山东两仓，显示动销款数、新品款数和金额，默认全选，可只勾选所需仓。
3. 首次或修改后导出仍需确认签发，保存完整门店正常单。每个店每天一个正常单、一个修订；选择一仓不代表只归档一仓。两仓共享同一次门店预算，不再分别分配资金。
4. 两仓分别生成 `日期门店名称（精简版·河北仓）.xlsx` 和 `日期门店名称（精简版·山东仓）.xlsx`。超过一份选择文件夹；一份可另存。已有文件拒绝覆盖，不自动加 `(1)`。
5. 保留往期新品、本月新品、中心仓动销补货清单三张表及原22列。只按已签发的 AU 归属分仓；地采、禁用、停采继续排除。新品未选择/未安排仍写0；某仓只有零数量新品也会出表，无可导出商品的仓不生成文件。
6. 门店正常单号不变，河北子单为原号 `-HB`，山东为 `-SD`。U列、页眉、批注和工作簿属性使用子单号，同时属性保留门店正常单号、供货仓和确切修订；不追加用户已删除的审计列。
7. 加盟商修改Q列后可分别或批量回传。子单号解析到原门店、仓和修订，每个商品必须属于该修订的该仓；错误仓拒绝整批保存。两仓回传合并保存为一个门店修订下的回传版本，不清除另一仓数据。回传页增加所属仓和每仓状态。0表示明确不补，空白不抹掉已有回传。
8. 旧总单号仍兼容。缺少修订的表必须明确选择原签发修订，不猜测日期/名称/当前仓。原签发建议不会被回传覆盖。
9. 历史页可按仓重导原修订。取消/失败保留已经提交的归档及成功文件，提示未完成文件；从历史页只选失败仓重试，不重新计算或签发。

## 数据和边界

- 仓库采用固定名称身份，不按主仓/从仓位置保存周期。换主从仓不交换两仓周期；停用从仓不清除其配置。超参、权重仍按门店，不新增每仓预测模型。
- 保存包含实际有效配置（含各仓周期覆盖），按精确门店编码写现有 stores 表；可选保存默认预算。保存时间与“已保存默认 / 仅本次”状态可见。失败仍显示未保存，不假装成功。
- 同次重新检查保留当前临时设置；新建作业、重新启动后导入才自动载入门店默认。恢复旧作业使用该作业快照，历史签发不取新默认重算。
- 未知/缺失归属仓不能拆单，阻止受影响门店并列出商品；其他有效门店可继续。历史数据也不使用当前仓资料猜测。
- 未新增子单数据库表：子单是父单确切修订的只读仓投影，身份为父号+仓后缀；导出事件和回传来源保留子号与仓。正常单每日唯一及多店签发原子事务不变。
- `normal_exports.export(..., warehouse=None)` 保留旧总单内部兼容入口，历史工具和对照可调用；所有用户加盟商导出入口均按仓。内部批次明细导出不受此次分仓影响。

## 模块与调用链

工作页 → merchant_selection（店仓选择）→ work_io_process（后台进程）→ normal_delivery（一次归档、按店仓顺序写文件）→ normal_exports（原表样式、仓过滤）→ warehouse_orders（仓划分/子号）。

回传 → merchant_feedback.scan/choices/prepare → warehouse_orders.resolve（先精确旧父号，再子号）→ 原归档修订商品归属核验 → 合并父修订回传快照 → 原事务提交。反馈UI展示仓来源，历史老回传按当时签发行的AU显示。

门店参数 → parameter_ui/store_defaults → work_repository.stores → workbench.populate_stores。原 restore_job 路径继续使用 `_restoring` 隔离默认加载。
