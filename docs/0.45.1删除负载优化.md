# 0.45.1 删除负载优化

## 使用

仍从“订单跟踪”或“决策复查”勾选订单，再“彻底删除”。删除范围、确认和取消方式不变；同一门店当天两仓共享正常单，仍按确认弹窗列出的父单范围删除。未选门店、平台订单、原Excel和旧交付包不变。

不增加维护开关，不要求业务人员选缓存、数据库格式或电脑性能等级。删除进度继续显示当前阶段、已处理数量、用时和最近进展；最终提交前可取消并回滚，最终提交中等待安全完成。删除不会自动执行全库压缩，因此数据库文件不一定立即变小，已释放页可供后续数据复用。

## 已确认的负载来源与处理

1. 预览与提交前校验把关联记录集中到列表，再生成一整份JSON和UTF-8副本。改为逐条按同一JSON格式累计SHA256，token保持一致，不保留全部历史任务文本。
2. 同一天的多个旧格式作业被一起读入并留到提交结束。改为逐份读取，准备结果只保留32字节的原压缩内容摘要、原逻辑摘要和重写描述。写锁内核对完整记录集合及原内容摘要，防止覆盖准备期间的新变更。
3. 同一个写事务内重复核对原作业内容、再次解压求摘要。一次完整比较已足以锁定原数据，复用准备时验证过的原逻辑摘要，取消多余的读取、解压。
4. 准备阶段检查过所有历史内容块，回收阶段又读一遍。将本次检查得到的引用放在临时SQLite；只有同一连接的main.data_version在准备开始到取得写锁期间未变，才复用。任何并发提交都会让该捷径失效，按原方式读原字节核验。新增块仍单独校验。缓存只在本次操作有效，不仅凭旧缓存跳过内容检查。
5. 每次把历史引用缓存整表重新写入，即使完全没变。改为仅新增或更新实际变化的行，减少回滚日志和磁盘写入。
6. 清理生成任务逐条读取payload；索引明细用SQLite只读BLOB分段扫描，跨段Unicode匹配和完整UTF-8验证与原规则一致，即使前面已匹配也继续验证剩余文本。减少Python整段大文本及副本。
7. 编辑器知道本次新写了哪些临时内容块，原有块直接读取源库，减少逐块空查临时库。临时引用查询放在一个只读事务内，避免每次查询重新获取文件锁；不会延长主库写锁以外的读事务。

涉及代码：data_maintenance.py、maintenance_storage.py。没有更换业务数据库格式、解除安全删除设置、改为分批提交或把回收延后。临时准备文件仍由操作结束时清理，失败回滚不改变业务记录。

## 验证范围

固定基线bfad263。同一冻结输入，新旧版本独立副本交替串行执行；对比删除预览token、结果、逐表有序且带类型的业务签名、未选订单和共享资料。仅每日草稿新修订标识/保存时刻作为精确动态字段；分块与引用缓存的物理布局不作为业务结果，但完整性、引用、并发变化和回滚另有专项测试。

专项涵盖：旧格式/分块、取消重试、写锁等待、最终提交边界、并发修改作业、并发修改内容块、共享原表保留、未选门店与队列保留、任务状态拦截、双仓父单范围，以及相同缓存不重复写入。

性能区分准备/执行阶段，记录三次原始耗时、30ms采样的工作进程峰值RSS和Windows进程I/O字节。I/O计数包括被系统缓存服务的读写，不能等同机械硬盘实际读写量或任务管理器磁盘占用率；测试机器也不能代替低配置业务机。合成样本首次引用核验、真实冻结历史已有引用缓存分别报告；本轮没有重新测量大历史库首次无缓存的完整耗时，不能借用旧报告作为本次结论。

大历史库首次核对全部存活引用仍可能耗时。SQLite安全删除和回滚日志仍有必要写入，不能承诺磁盘占用始终低于某个百分比。本轮没有对业务电脑做诊断或删除真实数据。

全量回归日志仍有浏览器状态栏控件销毁后回调的QLabel警告；0.44.0原始验收日志已有同一堆栈，本轮未修改该模块。测试通过不表示这项旧警告已修复，作为独立遗留项记录。

本次独立交付0.45.1 rc1，保留0.45.0 rc1；最终数据、EXE验收、构建提交及哈希以releases/0.45.1/rc1/交付报告.md为准。本轮不推送、不合并。
