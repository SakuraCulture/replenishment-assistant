# 0.47.1 缺货率批量导出与原件读取修复

缺货率采集接入原补货业务已经使用的翱象批量导出流程：同一批选择的门店先依次提交导出，平台同时生成多家文件，再轮询收取原任务结果。新建采集不再等待一家完全下载、解析后才提交下一家。

同时修复原生表头误拦截和空队列轮询导致的误取消。翱象“商品补货建议V2”的第43、45、47列本来都叫“毛利”；分析不使用这些列，现在与补货业务一样忽略未使用的重名列。月销、可用库存、商品编码及分析使用的其他字段重名时仍拦截，提示具体列名、位置和工作表，不猜第一列或最后一列，不修改原件。

## 使用方式

正常退出旧版，完整解压 0.47.1 运行包，打开“门店缺货率”，核对已采用的门店及供货设置，点击“采集今日分析资料”。无需打开新的并行开关，所选门店自动使用一个批次。界面显示本批门店数、平台已受理数、已取得文件数和待处理数。

之前报“原件存在重复表头”的任务，请在“采集与快照”选择原记录，点击“继续原任务 / 补失败项”。已下载且校验通过的文件会继续读取，无需删除任务或重新向平台导出。原补货分配队列没有任务时的周期检查不会再打断分析；确有分配工作时仍优先让行。

这里并行的是平台生成文件的等待时间。浏览器查询和提交沿用原补货组件的顺序操作，下载和本地文件校验、解析仍逐份执行；不会同时打开多份大表增加内存负担。单店任务没有多店等待可重叠，不能期待同样提速；实际耗时也取决于平台和网络。

## 原任务与隔离边界

- 升级前已经产生的逐店任务按原编号恢复，不合并、不取消重建。**旧的未完成任务可能仍逐店接续；本版新建的采集使用批量流程。**
- 每家门店先关联同一不可变批次再派发；响应丢失保留同一命令，继续时核对原结果。暂停不会撤销平台已接受的导出；已通过校验的原件保留。
- 补失败项继续原批次，只重试组件允许重试的失败门店；成功门店不重新发起平台导出。受理未知仍需核对，不能绕过防重。
- 原补货未完成任务只拦截冲突门店，其余所选门店仍可组成分析批次；不接管或取消原补货任务。分析进度中的待处理项保留具体原因。
- 本地逐店投影失败仍可保留其他完整快照。批次原件身份、范围或哈希校验不通过时拒绝采用，不用跳过校验换速度。
- 独立分析资料、默认关闭的每日计划、按需加载、原业务优先及安全暂停均保留。仓资料采集方式、缺货率公式、淘汰/考核识别、模型与订单业务不变。

其余使用方式见 [0.47.0 板块说明](0.47.0门店缺货率分析.md)。本轮新旧对照使用隔离平台模拟、同一原件、新旧交替各三次；实际 EXE 验收也使用隔离输入，不访问真实平台。数据和未验证范围见 [0.47.1 交付报告](../releases/0.47.1/rc1/交付报告.md)，不能把模拟等待时间当成实际平台提速承诺。
