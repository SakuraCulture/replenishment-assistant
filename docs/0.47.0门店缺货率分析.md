# 0.47.0 门店缺货率分析

新增顶部“门店缺货率”入口。它使用独立资料和日快照，不要求先计算、签发或创建采购单。模型仍为0.3.4-rules，仓归属仍为0.5.2；原补货参数、作业和存储格式不变。

## 使用顺序

1. 打开“门店缺货率”，点击“选门店 / 采用补货侧设置”。选择已经在翱象核验过的门店，复制原业务已保存的供货路线及必卖清单。以后更新要再次明确采用，两边不会互相自动覆盖。原业务没有保存必卖清单时，可明确勾选采用内置清单，否则必采属性显示待核。
2. 点击“采集今日分析资料”。按所选路线的仓并集逐仓获取聚水潭原生资料，再逐店获取翱象全部商品补货建议；任务、身份、范围、条数、编码和原件哈希校验后发布分析日报。需要原有平台正常登录及连接核验。
3. 选择日期和剔除视角，查询总览、逐日趋势和切面。支持门店、中心仓/地采、必采属性、仓、原商品类目、仓内上游供货商、仓商品状态、翱象补货状态、在途情况、标签依据和商品编码。两个切面可交叉；选中多组后筛选，同维度为“或”，不同维度为“且”。
4. “商品与待核”查看具体商品；“明细只看缺货”不改变上方统计分母。标签待核可通过“标签依据”切面下钻。明细每页最多200行，超长内容按4 MiB结果预算减少本页行数，下一页继续，原文不截断。
5. “导出本视角Excel”独立生成报表，可选择逐行导出商品明细。报表包括口径与覆盖、总体、剔除与标签待核、每日趋势、门店汇总、四类分层、当前切面和可选明细。文件已存在时要求另选名称；取消不会留下残缺正式报表。

## 统计口径

**门店缺货率 = 月销 > 0 且门店可用库存 = 0 的店品数 / 月销 > 0 的店品数。**

- 在途不抵扣门店缺货。无月销商品不进入基数；零基数显示“—”。
- 月销缺失、负值或非法值，以及有销商品的库存缺失、负值，不当作0。该范围的率显示待核，并保留已识别的分子、分母和待核数。
- 多店按分子、分母分别加总；多日按店品日加权，不平均百分比。每天采一次表示观察时点，不代表全天缺货时长。
- 仓、类目和供货商都是门店缺货的切面，不能据此自动认定供货责任。
- 禁用、停采商品只要有月销也进入基数，不沿用下单过滤。单仓范围无对应商品时按地采处理，不借未选另一仓的身份、类目、供应商或淘汰标签。
- 中心仓的类目、供应商和虚拟分类取本次归属仓原件；本次地采无仓商品资料时，供应商不适用，虚拟分类未取得。未知标签仍保留并单列，不能声称已全部剔除。

四种视角为全量、剔除淘汰品、剔除考核品、同时剔除两者。淘汰品按精确“标杆淘汰”系列，考核品按“淘便考核”，均取聚水潭原生“虚拟分类”。从分子和分母同步剔除，双标只减一次；缺列与已取得的空标签有区别。

## 采集、暂停及每日计划

- 进入页面只读取本板块的记录，不自动采集。每日计划默认关闭，本轮交付不会给业务资料启用计划。
- 需要连续每日数据时，单独打开“每日采集计划”，设北京时间。应用须保持运行、平台可用。软件关闭或跨日错过时保留缺采，不拿今天库存补昨天。
- 手动采集离开页面默认安全暂停；只有勾选“离开后本次继续采集”才继续。已明确启用的每日任务到时可在后台运行，完成后工作进程退出。
- 原补货计算、采集、删除等任务优先，分析在安全边界让行。“安全暂停”保留已确认原件及原任务编号，不撤销平台已接受的导出，也不强杀提交任务。
- 失败或中断后到“采集与快照”选择原记录，点击“继续原任务 / 补失败项”。已成功文件不重复取得；平台受理未知先核对原任务，不换任务号盲目重新导出。
- 部分门店成功可发布部分范围，覆盖显示“已完成 / 所选门店”。补失败项会形成新修订，原日报保持可追溯；跨午夜原件按实际观测日记录。完整重采才采用新的仓资料依据。
- “结束本地准备”只结束已核对清楚的本地意图。尚有未知平台受理时仍要求继续原任务，避免解除关联后重复提交。

## 独立资料和资源边界

资料位于用户资料目录的 `analysis/stockout/`；计划小标记位于 `analysis/stockout-schedule.json`。主库是 `stockout.sqlite3`，原件在 `originals/`，任务临时文件在 `temporary/`。共享平台台账会增加带“缺货率分析”用途的记录，原补货采集页面不会把它当作可采用资料；分析回执禁止发布为补货默认仓资料。

未进入且计划关闭时，只保留入口并检查小型计划标记，不打开分析库，不初始化重型分析模块或启动分析轮询。任务按需启动独立进程，逐店解析；1000行或4 MiB一批，长文本维度按内容归一存放，四视角共用事实。仅预汇总实际出现的维度组合，不生成全组合；商品编码等高基数切面仍按原事实查询，可安全取消。页面持有有界汇总及当前页；离开丢弃页面和结果，等待短事务正常结束。

写入前检查磁盘至少保留256 MiB加本次原件复制余量；可用系统内存低于128 MiB时安全暂停。它们是保守的提前检查，不是进程RSS硬上限；Excel解析、共享浏览器和系统缓存仍会消耗资源。低配置业务机尚需实际测量。

本版单次查询最多366天；趋势是逐日表，缺采日期不补0。占用展示读取文件大小及已记账原件大小，不在启动时扫描整个目录。分析历史清理先预览明确日期，作用于这些日期全部门店及视角，不按当前商品切面暗中缩小范围；不删除原订单或平台任务。清理提交后仅回收不再引用的分析自有原件，失败文件可重试；数据库空闲页复用，不自动VACUUM。仍被资料版本和原任务引用的仓原件保留。

备份需正常退出应用后，单独复制整个 `analysis` 目录；只复制数据库会丢失原件。原补货备份不会因此扩展为分析全量备份。分析库损坏时保留故障文件后恢复分析备份，原补货可继续使用。共享平台组件另有任务台账、下载和缓存文件，它们仍由组件管理，也会占用空间；页面所示“分析库/自有原件”不代表整应用或平台缓存的总占用。

## 实施与验证入口

功能代码为 `stockout_*` 模块；公共纯仓选择函数为 `warehouse_routing.py`，淘汰标签枚举为 `virtual_categories.py`。没有调用补货计算核心来生成分析分母。

- 单元与协议场景：`tests/test_stockout_analysis.py`、`tests/test_stockout_acquisition.py`。
- 实际窗口/EXE：`tools/verify_stockout.py --output <全新隔离目录> [--exe <EXE>]`。
- 30/90天合成容量：`tools/stockout_capacity.py --output <全新隔离目录>`。
- 原版本与候选未使用成本：`tools/verify_stockout_idle.py --output <全新隔离目录> --capacity <容量证据目录> --baseline <基线提交>`。

参数、输出和隔离标记必须先核对；所有验证只使用隔离输入，不调用真实平台。最终结果、失败记录、固定源码提交与包哈希见发行验收报告。实际平台连续每日采集、低配置电脑、跨机器部署不因隔离验收通过而视为已验证。既有 `browser_status_ui` 的 QLabel 销毁后回调警告不属于本轮修复范围。
