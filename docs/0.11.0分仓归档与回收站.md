# 0.11.0 分仓归档与回收站

固定基线 main / dd76b57cc00a038b0fb3d15973e68fd1c712c137。开发分支 feature/warehouse-archive-0.11.0。模型保持 0.3.3-rules；业务快照、JSON、SQLite 内容块格式不迁移。保留 0.10.0，独立打包，不自动合并或推送。

## 操作

历史归档每行代表“日期＋门店＋仓”，使用原有 HB / SD 子单号。同一门店仍共享原计算和总预算，不重新计算分仓预算。可按日期、门店、仓、商品关键词查询，正常归档和回收站分开。

选中仓单可打开修订、查看商品及当时参数、导出归档三表、移入回收站。历史详情的加盟商确认单只导出当前仓。回传对照也只展示该仓，原签发建议保持只读。操作记录按仓关联；从操作记录导出也绑定当时仓及确切修订，不导出文件路径清单。

删除默认取消，确认后把该仓全部修订移入回收站。另一仓仍可查看和导出；回收站可查看原快照，恢复后才能签发、导出确认单或导入回传。不增加永久删除按钮，不释放共享内容块、原始资料或回传记录，也不删除已发出的 Excel。恢复需要明确确认。每日草稿不因回收站操作变化。

同一门店确认归档是整体原子事务：任一仓在回收站时，重新签发该门店需先恢复。不会通过重算偷偷恢复已删除仓。删除、恢复、回传提交与签发均复核当前状态；过期修订或旧回收站令牌被拒绝，刷新后重试。取得写锁并核对后短事务完成，界面不允许强制中断提交。操作前保留安全备份，因此数据库文件或备份目录可能变化，不能宣称文件字节完全不变。

## 三张归档表

文件名：`日期门店（归档·河北仓·V001）.xlsx`，山东仓单独文件。

1. 完整计算建议表：所选仓的全部计算记录，包括零建议、禁用/停采、待核；每行带签发身份、完整有效配置、仓周期、原输入、字母中间字段、预算前后数量金额与审计。嵌套数据展开为列，不要求业务阅读 JSON。参数列来自原快照，SKU 的 AB/AC/AD/AG/AH 等才是该 SKU 实际代入值。全店预算明确标为共享，不能按重复行累加。
2. 制单时商品资料原表：读取签发关联的原文件哈希与原工作表，保留全部原行、列及重复表头。原表中公式作为公式文本展示，防止导出重算；数字、编码、日期保留类型。此表是数据快照，不复制原 Excel 的宏、图片、合并样式；完整原文件仍可下载。旧单没有留存原文件时明确写“历史未留存”，不以当前资料或选取字段冒充。
3. 模型建议签发表：沿用当前加盟商确认单的选品范围、数量和金额，将往期新品、本月新品、动销三组按原顺序纵向放入一表，增加推荐类型。仅中心仓可执行范围；未安排新品仍为 0。

三表不重新运行模型。归档导出不受商品搜索框过滤影响。不覆盖已有输出，取消不发布半成品。原加盟商确认单的三组工作表、字段、格式和规则不变。

旧版没有仓身份的匹配记录显示“旧版未标仓”，不按当前主从仓猜测；地采不伪装成第三张中心仓订单。全部原记录仍在旧签发快照与每日作业中。

## 模块与兼容

- `archive_orders.py`：只负责仓身份和回收站可见状态。首次删除增加独立 archive_visibility 表；不改 normal_revisions、jobs、源文件或内容块。老程序不认识回收站状态，因此不要用旧版并行管理同一个资料库。
- `archive_exports.py`：读取确切修订、展开全部字段、写三张表；无模型重算、无实时配置读取。
- `history_read.py`：派生索引升级为 2，旧索引自然失效重建；原数据库不迁移。按仓搜索和汇总保持原商品顺序。
- `history_ui.py`、`application_window.py`：按仓筛选、确认、回收站、三表入口。
- `normal_orders.py`、`normal_delivery.py`、`merchant_feedback.py`：只增加回收站状态门禁；无数量/金额修改。

## 五项质疑核查

1. main 已于本次前合并至 dd76b57，0.10.0 的代码树与合并前已验收树一致。历史分支自验不能代替组合回归。本轮用该 main 冻结源码独立执行旧/新 38 项对照，并新增 64 组主从仓×预算×一箱开关×在途×两店组合，必须证明真正触发一箱、在途限制、预算不足及转从仓，不只统计测试数量。
2. 旧 NotRequired 确实要求 Python 3.11+；本轮改为等价的 TypedDict 必填/可选继承。conflict_ui.proposals 原先因顶层 Qt 导入无法无界面测试，现抽到 conflict_choices 并保留兼容导入。parameter_view 当前本就没有 Qt 导入，质疑的这一部分不成立。依赖见 requirements-test.txt；本轮独立 Python 3.10/3.12 无 Qt 环境实测，完整 GUI/EXE 构建仍固定 Python 3.12。
3. 确实没有逐次配置编辑的完整历史轨迹；不能根据值相等猜测来源。分仓确认只是已有结果的仓范围，不是新增参数覆盖层。当前可回答“按当时哪些输入、有效参数和中间值得出数量”，不能声称恢复没有保存的每次编辑人和覆盖时间。本轮完整导出有效配置和 SKU 参数，并保留这个限制，历史不补造来源。
4. z=0 冲突目前保持待核及诊断，不私自把未知预测变成 0 或新算法。新的退化预测/人工确认策略属于独立业务规则任务，需单独确认、试算；本轮不改变计算。
5. 当前 engine.py 的例外隔离已经是显式 RuntimeError，不是 assert。本轮注入错误例外实现并在正常及 -O 模式验证均被拒绝。验收脚本中的 assert 不等于生产校验，生产模型/分配/一箱算法保持原文件。
