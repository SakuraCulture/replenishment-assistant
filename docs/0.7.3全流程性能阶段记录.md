商品表使用一行一个原生排序/过滤项，完整业务字段延迟格式化；排序仍使用原比较键并保留 Qt 同值顺序。新品表改为按需显示的表模型，筛选后的原始行映射保持，隐藏选择不丢失。已计算结果复用原有全行汇总，筛选汇总独立计算。

根据本轮补充要求，商品资料禁用、补货建议停采在工作商品列表和新品列表中排除，商品 Excel 导出也排除。原始计算/归档保留完整行，模型输入、中间值、预算和执行金额不改。内部工作簿保留原工作表、字段与样式，已排除明细页保留表头。已知排除商品对应的必卖匹配和冲突明细同步过滤，真实文件检查数/去重数不伪造为过滤后的计数；JSON 原始审计仍完整。

## 阶段二：大快照 I/O 协调（源码验证通过）

每日作业 SQLite、JSON/zlib 格式及 work_repository.py 不改。读取、保存前核对和签发导出由独立进程处理，分块传输完整数据，Qt 线程只更新进度；恢复已独占的数据树避免重复复制。保存/签发事务中不强杀，读取允许取消并回收进程，旧修订检查由原事务负责。

完整差异不丢弃：过长内容在确认框中明确提示截断，可导出完整 JSON；归档快照不截断。最终回归、压力与 EXE 结果以发行记录为准，当前记录不声明交付完成。

源码验证：work_io_source/work_io_report.json 在真实五店完整作业副本上通过取消、重试、恢复、配置复制、保存、覆盖取消、签发、五店导出、重读和关闭回收。io_controls/report.json 通过进程边界修订冲突、失败回滚、签发后取消导出、重试沿用修订。完整快照读取 SHA256 与原数据库一致。内存、总耗时与 UI 响应分别报告，不将后台等待描述为瞬间完成。

既有差异记录：首次 33 场景对照中两个 loaded.config.category_profiles 的字典插入顺序不同，所有逐商品结果相同。原因是原 engine.py 对 set 中未知分类补默认映射时受 Python 随机哈希种子影响；新旧引擎字节未变。本次不修改该业务代码，QA 将固定相同 PYTHONHASHSEED 后独立重跑双方，仍严格比较字典/列表顺序，不新增忽略字段。
