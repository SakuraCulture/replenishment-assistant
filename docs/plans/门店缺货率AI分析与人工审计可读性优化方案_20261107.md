# 门店缺货率 AI 分析、审计可读性、签发回传与图文新人手册方案

日期：2026-11-07。状态：**方案已编写，尚未实施。**

核对基线：main，f481cbe31a2ec82be97d8df83303aae64dd17bcc；应用 0.47.7，模型 0.3.4-rules，仓归属 0.5.2。本轮只检查源码、已有说明和设计依据，并编写本文；没有修改运行代码、业务参数、数据或客户端配置，没有调用真实平台，也没有重新执行 EXE 验收。

本文包含四项可以分别交付的工作；沿用原文件路径，便于已有链接继续访问：

- **缺货率 AI 分析**：沿用现有统计服务，让 AI 查询、比较、定位问题、说明证据、生成报表，并为后续门店自动配参提供依据。
- **人工审计可读性**：优先解决核对表、最终清单和风险表的字体、行列尺寸及窗口适配，保证业务人员能够看清完整内容并正确操作。
- **签发、回传与归档导出**：核实并复用已有隐藏关联页，补强回传识别失败说明、明确绑定和导出恢复，解决“文件属于谁、是否已经签发、失败后怎么办”的问题。
- **图文新人手册**：按业务目标组织完整操作路径，配同版本真实界面截图、编号标注、成功结果和报错恢复说明；提供离线阅读与打印版本。

建议优先定位签发 / 导出失败并改善人工审计，再接入 AI 基础分析，最后补齐跨日复盘和履约证据联查。手册目录和错误索引先编写，截图随对应功能验收完成，避免把旧界面写成新版说明。四项工作均不改变现有模型、预算、箱规、供货归属和确认范围。

**本轮新增核实结论：**当前门店签发文件已经写入 `系统关联信息` 隐藏 Sheet，含补货单号、门店、仓、日期、签发修订和摘要；回传读取也已接入。用户反馈的实际失败文件、日志和操作入口尚未取得，因此“标记丢失”“旧修订”“目录不可写”等只能作为排查分支，不能写成已查明原因。详见第 14 节。

## 2. 缺货率 AI 的使用方式

### 2.1 两个入口

1. 在“门店缺货率”完成门店、日期、剔除视角和维度筛选后，提供“用 AI 分析当前范围”。它生成包含精确范围的提示词；沿用现有“复制到客户端发送”方式，复制本身不执行任务。
2. 在“AI 常用业务”增加“缺货率总览”“连续缺货商品”“类目 / 仓 / 供应商定位”“履约证据核对”“导出分析报表”等场景。

AI 也可接受直接问句，例如：“查看最近 7 个自然日所选门店的必采缺货，按供货仓和上游供应商找集中问题。”此类问句只确定分析意图，实际查询先解析日期和精确门店编码，再返回采用的范围。

“最近 7 天”默认指自然日区间；不擅自向更早日期扩展成“凑足 7 个有记录日”。“最近一次”指实际留存的最近观测，不把它改称今天。范围不明确时优先继承页面明确选定的范围；没有可继承范围时再询问必要信息。

### 2.2 每次分析的固定输出

| 顺序 | 用户应看到的内容 |
|---|---|
| 范围 | 门店编码及名称、自然日区间、实际观测日期、剔除条件、所用修订 |
| 数据覆盖 | 已取得 / 应核对的门店日、未采日期、失败或待核项目；未采不补 0 |
| 总体 | 缺货数、有销基数、缺货率，待核与剔除数量 |
| 主要问题 | 门店、必采、中心仓 / 地采、类目、供货仓、上游供货商的集中情况 |
| 重点商品 | 商品编码及名称、可用库存原值、月销、在途、观察次数和相关日期 |
| 证据与建议 | 已证实的环节差异、待验证假设、缺失资料、可以执行的下一步 |
| 追溯 | 对应快照、观测时间、原件行号；涉及履约时附原补货单号及关联环节 |

用户只问一个问题时按需缩短回答，但不能省略会改变结论的范围和覆盖限制。排行同时展示缺货率与分子、分母，避免小基数高比例被误读为最大问题。

## 3. 统一统计口径

### 3.1 基础指标

统计对象为“观测日期 × 门店编码 × 商品编码”，每个日期读取明确选定的有效日报修订。一店一商品不因两仓同时有资料而重复计数。

- **有销基数 B**：当前视角内月销大于 0 的门店商品数。
- **缺货数 O**：B 中门店可用库存小于或等于 0 的商品数。合法负库存按 0 判缺货，保留原始负值供追溯。
- **缺货率 R**：O / B。B 为 0 时显示“无有销商品”，不显示 0% 或 100%。
- 多门店、多日期：分别加总 O 和 B 后求比值，不平均各店、各天百分比。跨日期明确标为店品日加权率。

库存采用翱象门店可用库存。仓库存、在途和拟补数量不能替代门店现货，也不能从缺货分子中抵扣。

### 3.2 排除与待核

1. 默认剔除门店停采 / 禁采以及实际供货仓禁用，同时从分子、分母剔除，重叠只计一次。备用保留；未知状态不猜成禁用。未参与供货的另一仓状态不决定本店排除。
2. 淘汰品、考核品按已冻结的聚水潭“虚拟分类”识别，保留全量、剔除淘汰、剔除考核、同时剔除四种视角；名称系列沿用现有规则，不新增模糊匹配。
3. 地采供货仓显示“地采”；上游仓供应商显示“不适用（地采）”，不生成虚构的地采供应商。
4. 月销缺失 / 非法 / 负数，或有销商品库存缺失 / 非法，保持指标待核；不把缺失解释成 0。供应商、类目、标签缺项进入对应待核分组，不因此删除有效店品。
5. 标签未知时如实展示“含标签待核”；剔除视角只排除已经确认命中的记录，不能声称未知标签已排除干净。
6. 旧日报仍有负库存旧口径影响时，提示使用留存原件重算；AI 查询不自动重算、不重标统计版本。

**实现注意：**现有页面的停采、禁用剔除默认勾选；底层查询参数省略这些字段时并不等价。新增 AI 契约必须显式携带这两个布尔开关，并与页面共用范围构建方式，不能因漏传参数改变基数。

### 3.3 维度、筛选与汇总

复用门店、供货来源、必采属性、供货仓、商品类目、仓库上游供货商、观测日期、仓商品状态、翱象补货状态、在途情况、标签依据、商品共 12 维。

- 同维多选为“或”，跨维为“且”；门店和商品以编码作为身份，名称用于展示和查找。同名多编码不能自动合并。
- 供应商沿用当前“供货仓＋原供应商名称”口径；不能只凭同名认定两仓为同一主体。类目按现有单列资料展示，不凭名称构造多级类目。
- 跨天维度采用当日冻结值。仓、标签、类目等发生变化时展示变化，不能拿今天资料悄悄重分历史。
- 只看缺货商品的明细开关只改变明细浏览，不把总率分母改成缺货商品集合。
- 不同切面是同一批记录的不同观察方式，不跨切面加总；“贡献占比”明确分母是该范围缺货数，不等于缺货率。

## 4. 趋势、持续缺货与原因分析

### 4.1 时间比较

原有总览和趋势继续由统计服务给出。新增对比保留两个层次：

- **各期实际范围**：如实展示当期有销基数、缺货数、比例和采集覆盖，包含商品增减造成的结构变化。
- **可比商品观察**：仅对两端均有有效依据、符合约定纳入条件的同店同商品比较；单列新出现、移出范围、转停采和维度改变，不把这些变化当成库存恢复。

默认作最近两个有记录日期对照时，明确两天日期及间隔；区间比较采用长度和覆盖可解释的窗口。比较时同时给出比例变化的百分点、分子变化和分母变化，不能只给一个“改善百分比”。

“重复观察到缺货”记录缺货观察次数 / 有效有销观察次数；“连续日观察到缺货”要求自然日连续且每天依据有效。缺采、指标待核或退出有销范围时，中断连续日判定，并说明原因。隔日采集可以报告多次观察缺货，不能称为连续缺货若干天。

每天一次快照只证明观测时点状态，不证明全天缺货时长。月销是滚动窗口，不能相减冒充实际日销或直接估算丢失销售额。

### 4.2 原因分层

| 类型 | 可以给出的结论 | 不足时如何处理 |
|---|---|---|
| 观察事实 | 某店某商品在指定日期月销 > 0、可用库存 ≤ 0 | 字段无效则待核 |
| 履约差异 | 原单从建议到签发、回传、付款、实收的明确增减量 | 缺单据或未确认环节不填 0 |
| 供应观察 | 当时冻结资料显示供货仓可用数、商品状态或在途情况 | 不把现时仓库存用于证明过去缺供 |
| 参数疑点 | 在履约依据较完整时，将保护期或安全库存列为待试算因素 | 不以缺货率高直接认定参数错 |
| 行动建议 | 核对在途到店时间、追查配货差异、检查资料、进入参数诊断 | 区分查询建议与已经执行的动作 |

门店减量、仓库少供、到货偏晚可以同时存在，不把重叠标签相加成“原因贡献 100%”。“实收不足”需要可靠上下游关联；“迟到”还需要约定到货时间与实际到货时间，单有导入时间或实收数量不能判定。

### 4.3 联查规则

按门店编码、商品编码、原订单、供货仓、库存单位和时间读取业务证据。先限定日期、门店和重点商品，再加载相关单据。多单、跨仓、单位不一致或时间关系不清时，列出候选依据并停止自动归因，不能默认取“最近创建的一单”充当来源。

观察之后创建或确认的单据不能用于声称观察之前已到货。保留业务日期、观测时间、导入时间、实际收货时间的区别。五段漏斗与缺货率的排除规则并不完全相同，关联证据不能通过内连接悄悄删掉缺货率总体中的商品；应明确“找到依据 / 未找到 / 多份待核”。

## 5. 数据、MCP 与资源设计

### 5.1 拟新增接口

以下为设计名称，当前程序尚未提供。复用现有任务状态、取消、错误结构和本地连接，不开放任意 SQL 或脚本执行。

| 接口 | 用途 | 对业务数据的作用 |
|---|---|---|
| stockout_context | 读取留存日期、可用门店、当前范围、规则版本与完整性状态 | 只读，未建分析库时返回“尚无分析资料” |
| query_stockout_analysis | 固定范围和已发布修订，提交后台分析，返回 task_id / snapshot_id | 不采集、不重算、不更新资料 |
| stockout_analysis_results | 分页读取总览、趋势、切面、商品与待核；较重的持续缺货和对比可作为后台子任务 | 只读固定分析依据 |
| stockout_filter_values | 按其他筛选条件查询候选编码 / 名称 | 只读分页 |
| stockout_evidence | 联查精确店品的快照与履约依据 | 只读，不自动补建单据关联 |
| export_stockout_analysis | 用户明确要求后，将核对过的范围导出到新的本地文件 | 仅写报表，不发送文件、不改业务记录 |

页面和 AI 对同一范围共用统计服务。新增对比和持续缺货逻辑放在共享分析服务，不让语言模型自行汇总明细。AI 给出结论时引用服务返回的数值、证据编号和状态，不根据名称或描述猜编码、销量和原因。

### 5.2 快照一致性

现有查询入口通过 current_days 读取当前发布结果。AI 分多轮调用时，期间可能发生重算或删除，因此不能只固定日期而每页重新读取“当前日报”。

查询创建时固定日报修订、门店快照清单、规则版本、筛选、排序及其摘要。分页、联查和导出都使用同一清单；需要给共享查询服务增加内部的明确修订读取能力。未指定修订的原页面行为保持。

不在等待 AI 回复时保持长 SQLite 读事务。使用短查询和有期限的任务引用；清理 / 删除开始前协调在途任务，取消读取或将会话标为过期。底层快照被删后返回“原分析依据已删除，请重新查询”，不能自动换到另一修订，也不能无限阻塞用户清理。

分析派生缓存随任务过期或范围删除失效，不另存长期整库副本。此前已导出的报表和已发到 AI 客户端的回答属于独立产物，应保留其原范围与生成时间，不冒充实时结果。

### 5.3 模块独立与低资源运行

- 普通启动、打开 MCP 工具列表、读取补货参数不加载缺货率历史，也不自动创建分析数据库。
- 仅在用户进入分析或明确调用分析工具时按需加载；结束或过期释放任务数据。普通查询不加载 Excel 原件，追溯必要时才按需读取。
- 缺货率资料、供货设置和必卖清单继续使用本板块已采用的独立版本。AI 不能为了补标签擅自刷新补货侧仓资料，也不把新参数反写旧日报。
- 优先读取汇总；商品分页沿用 MCP 单页最多 100 项及消息大小限制。报告默认展示重点项并标明“展示 / 总数”，完整结果可继续分页或导出。
- 范围沿用最多 366 天、12 维、32 套导出组合、每维最多 1000 个筛选值。超范围要求缩小或明确拆分，不静默截断。
- 重查询、导出和履约读取后台执行，支持安全取消；与采集、重算、清理协调，避免多任务同时扫描同一批大文件。查询缓存必须包含修订、统计版本、全部排除开关和筛选。
- 读取业务单据使用只读路径，不为了查询调用会初始化或迁移业务库的构造过程。

### 5.4 业务提示

报错至少说清“发生了什么、影响哪些店 / 日期、保留了什么、下一步在哪里处理”。例如：

- “所选日期中有门店未取得资料，当前结果只覆盖已完成门店；可到采集与快照查看缺项。”
- “当前范围含旧口径负库存结果，尚未自动重算；请在采集与快照选择对应作业核对。”
- “这笔实收无法唯一关联到原采购，暂不能判定是否少收；请查看列出的关联候选。”
- “日报已经更新，本次结果仍对应原修订；重新查询后才能分析新结果。”

技术错误码和调用详情提供复制入口，不作为唯一的用户说明。AI 自然语言核验与工具调用核验分别记录；旧版本客户端成功记录不代替新接口验收。

## 6. 如何衔接门店自动配参

本期为每店输出“建议保持 / 优先处理履约 / 可进入参数试算 / 证据不足”及对应依据，形成配参候选清单。地采缺货不通过中心仓参数试算假装解决；实际供货范围、主从仓、资料优先级仍以门店配置为准。

后续自动配参按以下闭环开发：

1. 用户选择门店、目标和允许调整的字段范围。
2. 读取本期分析证据与当前有效参数，区分新店模板初始化和有历史门店优化。
3. 自动生成逐店候选，先覆盖分类库存目标分位概率及有业务依据的分仓备货天数；到货天数需可靠记录，趋势权重和资金阈值另行扩展验证。
4. 冻结输入、原参数、预算、供货、箱规、准入和清单，用原模型完整重算整店预算，展示原值、新值、影响和风险。
5. 用户核对后选择“仅本次”或“保存以后默认”；逐店保存版本和原因，不修改未选门店，也不直接编辑可能被其他店共用的命名预案。
6. 后续观察实际缺货与库存表现；经明确授权后，才增加限定门店、字段、幅度和频次的自动调整模式。

参数试算只能证明相同输入下建议数量、金额和覆盖的变化。历史缺货率不会因改参数而改善；真实效果需后续观测验证。库存目标分位概率也不是实际不断货率承诺。

完整自动配参此前初估 13–20 人日，其中部分分析基础与本期重叠，不能把两个估算直接相加。授权范围内持续自动调整此前初估另需 8–15 人日，并需覆盖多个完整补货与收货周期；这些属于后续工作，不计入本文首期排期。

## 8. 显示改造方案

### 8.1 字体与尺寸统一调整

增加本机“显示设置”：正文 10 / 11 / 12pt，以及紧凑 / 标准 / 宽松行距。默认保留当前 10pt 起点；密度调整改变留白，不偷偷缩小字体。提供恢复默认和按页面恢复布局。

行高、表头、编辑器、复选框和按钮使用实际字体尺寸与 Qt 样式度量。字体、屏幕 DPI、窗口尺寸变化后一起重新布局；不叠加一套手工倍数导致二次缩放。标题、汇总卡和长说明在小窗口收敛占用，不用压缩正文换空间。

本节字号、行数、断点是待验证的设计初值，不是已经验收的尺寸。布局按实际可用工作区和字体度量确定，不能仅按物理分辨率硬编码。

### 8.2 表格按字段类型分配空间

| 字段类型 | 显示策略 |
|---|---|
| 门店 / 商品身份 | 同时提供编码与名称；按任务固定必要身份列。名称最多两行预览，完整值可直接查看和复制 |
| 金额、数量、比例 | 右对齐，符号与单位清楚；保证常见值完整，极长值可完整查看，不擅自改单位或数值精度 |
| 状态 | 简短中文状态，保留文字，不只用颜色 |
| 修改原因、风险、来源说明 | 主表显示可读摘要，完整原文进入常驻详情区；不只靠悬浮提示 |
| 长表头 | 支持按语义换行，表头高度随字体调整；完整中文含义与单位可查 |

默认宽度由字段重要性、表头和有上限的可见样本计算，设置合理上下界；保留手动拖宽、双击适配和恢复默认。不能在每次滚动时对全表做“按内容调整所有行列”。

主表不强行把全部列压进当前宽度。提供按任务的列组和列显隐，例如“核对与改量”“预算与风险”“资料与来源”“全部字段”。固定列占用过大时切换紧凑身份区，始终给当前业务列留出空间。

### 8.3 人工审计改为“清单＋完整详情”

常见宽度下，左侧 / 上部是核对清单，右侧 / 下部是完整详情。用户可拖动分隔线，或将详情独立放大；窄窗口改为上下布局。

详情按业务分段展示：门店和商品、原值与新值、调整原因、风险、计算依据、原件 / 单据来源。支持文本选择与复制；切换条目后始终显示当前身份，避免看错店或商品。

主表默认展示完成核对所必需的信息，长说明保留两至三行预览；详情展示完整原文。提供“展开本行”和“查看完整内容”，不是无限增加每行高度。关键阻断与风险标志必须在主表保留，不能藏到默认关闭的详情里。

已有商品计算依据与列分组继续复用。固定列基于原模型及同一选择模型，不复制业务行；现有固定列实现面向部分 QTableWidget，扩展到可编辑 QTableView 前需单独处理代理模型和编辑器，不可直接套用。

### 8.4 最终清单与风险核对优先改造

- 默认围绕商品身份、自动量、拟签发量、差额、金额、风险组织主表，其余按列组查看；保持单店与多店身份可辨。
- 金额概览压缩为摘要，逐店金额可展开；当前可见范围、全部勾选范围、整店金额的含义继续分别说明。
- 风险区域支持放大 / 独立查看，点击风险定位对应商品；完整风险和原因可读、可复制，不要求拖到很宽的固定内容列。
- 窄窗口将操作分为常用与更多，筛选按区域折叠；当前生效筛选和未处理风险数量常驻。批量操作、当前勾选范围和确认按钮保持可达。
- 改量编辑器、原因输入区随字号调整；切换筛选、排序、列组及窗口尺寸不丢编辑、不串行。字段身份继续绑定业务键和源索引。
- 隐藏列、查看详情、展开文本只改变展示，不改变风险确认状态、最终数量、勾选对象或签发范围。

### 8.5 确认弹窗和窗口适配

大量差异使用可调整尺寸、可最大化的专用核对对话框；小型确认继续使用普通消息框。替换现有嵌入表格的 QMessageBox 时，保留原按钮含义、默认取消、Esc 取消及确认范围。输入区域的回车不能误触确认。

窗口初始尺寸限制在所在屏幕可用区域；多显示器和跨 DPI 移动后重算。允许缩小窗口时，筛选区域滚动或折叠，表格独立滚动，操作区保持可达；不能让整个窗体被固定最小尺寸挤出屏幕。

显示偏好保存在本机独立配置中，按稳定页面 / 字段标识记录字号、列宽、列显隐和分隔比例，不写入业务参数或历史快照。跨版本新增列有默认值；恢复失效窗口位置时移回可见屏幕，不迁移其他电脑的绝对屏幕坐标。

### 8.6 资源约束

维持现有数据模型、分页和按需加载。行高计算优先覆盖可见区域，列宽计算有样本上限；调整字号 / 拖窗采用合并刷新，避免全量重建商品表。详情按选中项加载，退出释放监听、任务和缓存。

特别检查固定列同步：现有实现存在按全表同步行高的路径，大数据表推广前应改为只同步必要变化，不能用读取更多记录换取显示效果。字体切换不重算补货、不重新读取全部原件、不触发平台采集。

| M1 | 完整任务目录、状态词典、错误与恢复索引 | 1–2 人日 |
| M2 | 对应版本真实截图、编号标注、全流程正文与示例 | 3–4 人日 |
| M3 | 离线 HTML / PDF、链接和排版检查、新人演练 | 1–2 人日 |
| I | 四项合并回归、资源检查与独立交付封存 | 2–3 人日 |
| **本期合计** | **显示＋AI 分析＋签发回传与导出＋图文手册** | **21–34 人日** |

其中显示改造 5–8 人日，AI 分析 5–8 人日，签发回传与导出 4–7 人日，手册 5–8 人日，共同集成 2–3 人日。原两项初估为 11–18 人日；本次增加两项交付并扩大集成检查，不能仍沿用原合计。

建议顺序：E1 先确认当前阻塞 → E2 / E3 与 U1 / U2 按相应页面分段完成 → U3 验收并交付第一批恢复说明 → A1 → A2 → 完整集成。M1 可以先做；M2、M3 跟随已验收界面收集素材，最终与同版本安装包一起交付。该顺序不要求同时启动多个开发者，也不要求等待全部 AI 功能完成后才交付导出修复。

上述 AI 估算沿用现有外部客户端、数据服务和导出结构；不包含完整内置聊天、新的数据采集通道、连续库存轨迹回测和自动保存参数。显示改造限上述人工核对重点页面，其他所有业务列表统一改版单列后续范围。手册估算包含图文及 PDF，不包含培训视频、多语言翻译或在线帮助服务器；演练人员安排等待不计入开发人日。

## 12. 实施前应冻结的设计项

以下不阻塞当前方案编写，实施时先用样本与现有设置核实；只有会改变业务要求的部分再请用户决定。

- 人工审计首批页面：优先实际最难阅读的窗口，并记录屏幕缩放与字号；本文列出的页面族作为检查范围。
- 显示初值：保留 10pt 默认，提供更大字号；审计摘要行数、详情位置与字体联动规则通过实际布局验证确定。
- AI 默认范围：继承页面；没有范围时询问，日期与剔除开关必须明确。
- 自动配参目标：后续开发前明确必采保障、库存占用和预算约束的取舍，不从“缺货率高”反推出用户允许增加预算。
- 完整历史是否存在：检查实际可用日期和履约覆盖后再启用相应分析；缺资料只降低结论强度，不伪造记录。
- 故障原件：区分“确认签发并导出”“历史门店签发重导”“内部归档明细 / 原件导出”，留存实际报错和失败原件的只读副本再复现，不能仅凭描述认定同一原因。
- 手册基线：每次发布固定应用版本、构建标识、屏幕缩放和示例资料；待实施功能单列，只有完成验收后才转入正式操作步骤。

## 13. 图文新人使用手册

本节规定下一阶段要交付的完整手册，不表示手册、截图或 PDF 已经制作。本次先把目录、写法、配图和验收范围定全；尚未实施的界面不能用示意图冒充真实操作截图。

### 13.1 阅读入口与单篇结构

首页从“我想做什么”进入，不按源码模块排列。设置“第一次使用”“每天补货”“订单回传与执行”“缺货率分析”“出现问题”“数据维护”六类入口，另提供按钮名、报错原文、业务单号类型的检索。第一次使用有短路径，完整手册保留异常、边界和恢复说明，不能只写正常流程。

每个任务使用统一结构：

| 内容 | 新人需要看到什么 |
|---|---|
| 目标与准备 | 本次要完成什么；需要哪些文件、登录状态、门店和业务日期 |
| 从哪里进入 | 按实际版本写清页面与按钮名称；配有所在页面的全景定位图 |
| 怎样做 | 分步配局部截图，编号与正文一一对应；输入示例明确标为演示数据 |
| 怎样判断成功 | 对应完成画面、保存位置、单号 / 修订、处理范围及应核对数值 |
| 会改变什么 | 本次作业与以后默认的区别；本地文件、归档记录与平台实际操作的区别 |
| 中途停下怎么办 | 能否取消、已完成部分是否保留、从哪里继续；不得引导强杀提交中的进程 |
| 出错怎么办 | 报错画面、业务解释、检查顺序、恢复动作及恢复成功画面 |
| 还不行时提供什么 | 版本、操作时间、入口、门店 / 仓 / 单号、完整报错和脱敏诊断材料 |

例如“把门店回传单导入原订单”必须讲清：选择文件 → 查看识别到的单号、店仓与修订 → 核对数量和范围 → 确认导入 → 查看该原单的回传结果。识别不到时转到原因与候选核对，不能只写“手动选一个订单”。

### 13.3 配图和交付要求

1. **截图来自验收版本的实际 EXE。**使用隔离演示数据；平台相关页面如来自模拟回放或已有证据，图注注明，不宣称新增真实平台验证。用户旧截图可帮助定位问题，不能直接当作新版操作指南。
2. 每条主要路径包含入口定位、关键操作、结果核对；常见错误包含报错与恢复后的结果。以覆盖操作为准，不用固定截图数量充数。
3. 全景图解释“在哪里”，局部图解释“点哪里 / 填什么 / 看哪里”。局部图保留必要页面上下文，序号对应正文，图注说明该步目的；不只在大截图上圈一个红框。
4. 图片在正常阅读尺寸下可辨认正文和按钮，不把数十列表格缩成一张不可读图片。长表拆为身份区、目标字段、详情区等连续图，注明是同一示例及范围。
5. 保留原始截图和标注版，标注不遮挡关键文字；凭据、手机号、实际个人信息等脱敏，不修改数值来伪造成功。图片加标题、替代文字和相应文字步骤，支持检索和复制。
6. 手册首页标注适用应用版本、构建依据和更新时间；图册记录页面、场景、缩放与来源。版本升级时按受影响任务更新，旧说明转历史，不覆盖旧验收证据。
7. 提供同一源稿生成的 **离线 HTML 和可检索 PDF**：HTML 有目录、目标入口、全文检索和报错锚点，不依赖 CDN 或联网；PDF 有书签、页码、清晰图片和完整分页。图片随文件一起交付。
8. 随完整程序包提供“新人从这里开始”入口；应用内帮助按钮如需开发，单独接本地手册，不在普通启动时加载整本手册或所有图片。

### 13.4 报错与状态词典

错误索引按业务现象列出报错原文、含义、已完成部分、下一步和复查位置。至少包含以下类别；实际正文逐项采用当版真实提示，不编造现有按钮。

| 用户看到的现象 | 手册应说明的处理方向 |
|---|---|
| 连接成功但未登录 / 账号不一致 | 区分浏览器可连接、平台已登录、商家 / 仓身份核验；去相应检查入口，不重复采集试运气 |
| 原件存在重复表头、字段不足、公式无缓存 | 指出文件 / 表 / 字段，展示正确模板和保存步骤；不教用户删除不理解的业务字段 |
| 待核很多、缺货率是“—” | 分开解释标签待核与指标待核、覆盖不足；负库存按现行规则计缺货，不作为需要修成正数的错误 |
| 基线重算与当前结果不一致 | 查看具体门店、字段、旧新值及冻结依据；停止依赖该基线的试算，先定位差异，不放宽校验 |
| 已跨日 / 历史只读 / 已有人工安排 | 区分恢复草稿、查看历史和按原修订导出；解释试算限制，不建议重新签发绕过 |
| 回传不知道绑定谁 | 查看关联页是否存在、具体冲突、候选店仓日期修订；缺失时明确人工核对，冲突时不能忽略后硬绑 |
| 签发导出失败 / 归档导出失败 | 先看签发是否已经提交，再看逐文件结果与失败阶段；关闭占用文件或修复目录后按原修订补导出 |
| 平台已创建但本地待核 | 查原任务 / 原采购，解释受理、已创建、已关联分别是什么；禁止通过重复上传核实成功 |
| TASK_NOT_FOUND / 无唯一受理号 | 展示可核对的原任务时间、店仓和已有依据；未找到不等于平台没有创建 |
| 平台已作废，本地仍关联或拦截删除 | 查询并确认原采购最新状态，按原任务恢复流程处理；不能用结束本地准备冒充撤销平台采购 |
| 按钮失能 / 只能执行部分订单 | 分清正在执行、已排队、未勾选、没有可执行项和历史只读；说明勾选范围和原任务入口 |
| 分析不能重算或重跑 | 查看原件、所采用设置和门店覆盖；重新采集只能产生新观测，不能伪造成过去某天资料 |
| 删除后仍占磁盘 / 初始化后配置为空 | 查看删除范围、文件保留、备份和初始化的真实范围；不自行删除数据库文件或浏览器资料 |
| AI 已配置但客户端未连接 | 核对本机服务、客户端配置、实际工具调用和版本；配置文件存在不等于连接成功 |

统一解释“已保存草稿、已签发归档、文件已生成、已上传受理、采购已创建、已关联采购、已作废、已停止、待核、已完成”等状态。“停止”只说明后续动作停止；“文件已生成”不说明平台已经采购；“待核”必须附仍缺什么依据和可执行的下一步。

### 13.5 手册验收

- 对照目录逐项覆盖，正常、取消、错误恢复都能找到；页面名称、按钮、文件格式和实际版本一致。历史说明中的旧列号、旧规则不得混入现行流程。
- 至少安排新人按手册独立完成：首次计算并签发导出、识别回传及缺标记处理、恢复一次导出部分失败、采购结果待核查询演练、缺货率多维导出和重算、仅本次参数与以后默认区分、完整阅读并取消一次审计确认。
- 演练只用隔离数据和模拟平台响应，不提交真实采购、不删除真实数据；记录停顿点、误操作和缺失说明并修订。没有实际新人参与时只能写“内部走查”，不能写“新人验收通过”。
- 离线打开 HTML、检索一个报错并跳到恢复步骤；检查 PDF 文字检索、目录跳转、表格续页、图片清晰度和无裁切。断网不影响手册阅读。
- AI、显示、签发回传分批发布时，手册同步标明当前已支持与后续计划；不要求新人点击尚不存在的按钮。

## 14. 签发文件身份、回传识别和归档导出

### 14.1 已有能力与尚未确认的问题

用户所说的“签发单号”，在这里对应本应用的补货单号及签发修订，不能与翱象平台产生的采购单号混用。当前门店签发文件确实已经有隐藏身份页，并非完全依靠文件名识别。

| 环节 | 源码已确认 | 本次要补查 / 补强 |
|---|---|---|
| 隐藏页 | `系统关联信息` 使用 veryHidden；包含格式版本、文件关联标识、业务工作表、补货单号、门店编码、仓库、业务日期、内部签发引用、原签发摘要、签发保存时间及关联信息校验 | 当前实际文件是否存在、内容是否完整，所有门店签发 / 重导 / 合并入口是否一致携带 |
| 可见内容 | 当前门店签发业务列保留 A:T，U 为决策理由；单号另有文件属性与隐藏页 | 新人说明不能再沿用早期“U 列是隐藏单号”的说法；核查模板及用户收到的文件类型 |
| 回传读取 | 验证隐藏页表头、校验、工作表关联、门店 / 仓 / 单号与修订；已有整单人工绑定及多来源拆分 | 显示具体失败环节，解释候选为什么能绑或不能绑，避免只显示“无法识别” |
| 新签发导出 | 先冻结并确认归档，再逐份导出；单文件先写临时文件再替换目标 | 明确归档状态与每份文件状态；失败恢复沿用原修订，不能重复签发 |
| 历史归档导出 | 已有分别 / 合并导出、不可用项确认、逐文件结果、清单及“重试未完成项（原修订）” | 保留已有能力，补齐最外层失败、清单 / 日志失败和重启后的结果追踪 |

依据：[身份格式与校验](../../src/order_identity.py)、[门店签发文件](../../src/normal_exports.py)、[回传读取](../../src/lifecycle_io.py)、[批量分组与绑定](../../src/lifecycle_batch.py)、[原签发复核](../../src/order_lifecycle.py)、[签发与导出两阶段](../../src/normal_delivery.py)、[归档导出](../../src/archive_batch.py)、[归档导出界面](../../src/archive_batch_ui.py)、[0.32.0 使用与结构](../0.32.0使用与结构.md)。

veryHidden 表示普通工作表标签栏看不到，通常也不能直接用 Excel 的普通“取消隐藏”显示。隐藏和工作簿结构保护主要防误改；关联摘要用于一致性检查，不能把它描述为防伪数字签名。正常改回传数量、排序不应要求用户修改隐藏页。

**已确认入口：**用户说明发生在“核对与签发 → 确认签发并导出”。尚未取得用户本次失败的原 Excel 和失败日志，不能预先认定具体根因；路径、占用、原件或写出阶段失败需分别验证。0.48.0 已实施范围与后续项见[实施说明](../0.48.0AI分析审计与签发恢复.md)。

### 14.2 先分清三种导出

| 入口类型 | 产物与业务效果 | 恢复原则 |
|---|---|---|
| 当前作业“确认签发并导出” | 确认所选范围的签发修订，然后生成门店文件 | 归档提交后，即使写文件失败，也只能按该修订补导出 |
| 历史门店签发重导 | 读取选定的冻结签发修订，生成门店使用的文件 | 不重新计算、不更新归档、不使用今日参数补旧单 |
| 内部归档明细 / 完整计算表 / 商品资料原件 | 导出内部核对表或留存原件，可能包含多个订单 | 不把内部加工表默认当作门店回传模板；缺原件和缺字段如实列出 |

首先记录具体入口、版本、所选订单及仓、修订、目标目录、预期文件数和完整报错。在只读副本 / 隔离库复现，核对“准备 → 读取原件 → 归档提交 → 写 Excel → 发布文件 → 记录回执”哪个阶段失败。业务库不做试错性删除或重签。

当前还发现三个值得优先验证的实现风险，它们都不是用户故障的既定结论：

- 内部归档文件的部分路径使用 `os.link` 发布临时文件；验证用户实际磁盘 / 共享目录是否支持，以及权限和占用条件。若需要兼容替代，仍须保持完整文件才发布、既有目标不被意外覆盖的约束，不能退化为直接向最终文件写半成品。
- 归档批量导出在逐文件完成后写 `导出清单.txt`；清单失败可能让外层报错，掩盖已经生成的文件。结果页应保留真实文件结果，并单列清单失败。
- 当前归档结果计算哈希有整份 `read_bytes()` 路径；大文件时核对额外内存和等待。必要时改成分块计算同一完整摘要，不省略校验、不改摘要语义。

### 14.3 让文件身份可见、可检查

保持现有隐藏 Sheet 格式和商用列结构，本期不新增第二套单号。提供只读“查看文件关联信息”或等价详情入口，展示识别到的业务文件类型、补货单号、门店编码及名称、仓、业务日期、签发修订和校验状态；用户不用解除保护才能确认文件属于谁。

新导出、历史重导、分仓、合并、由回传再次导出的文件分别建立检查清单。写出后对完整文件及关联信息进行校验，结果与本次固定的签发依据对应；合并文件保留每张原单的完整身份，不给整个工作簿随意填一个代表单号。内部归档加工表按自身用途标明，不能混淆为可直接回传的门店文件。

保存及回传方式要用实际 Excel / WPS 检查：只改数量、排序、删商品行、文件重命名、另存为、复制工作表到新文件、工作表改名、转 CSV 等。哪些能完整保留关联，哪些会丢失或冲突，记录实测结果并写入手册；不能承诺任何编辑器及转换方式都保留元信息。

关联信息缺失与关联信息损坏必须区分。缺失时允许沿用现有明确人工绑定；已存在但校验冲突时，不得通过忽略隐藏页、删属性后自动回退为“识别成功”。不自动改写用户回传原件补造身份。

### 14.4 回传识别失败要说清楚，并给出可用路径

保留现有识别顺序与一致性约束，先核对明确行字段、隐藏关联和既有文件属性是否相符，再按精确身份定位有效原单。文件名、SKU 重合、数量接近、创建时间接近只可辅助查找，不能用来自动确定订单。

| 识别结果 | 应展示的具体原因 | 下一步 |
|---|---|---|
| 唯一匹配 | 原单、店仓、日期、修订及采用的关联依据 | 核对完整来源及数量后确认导入 |
| 没有身份标记 | 文件中未找到可用的系统关联信息 / 明确单号 | 列出限定范围内候选，由用户明确选择；标为人工绑定并保留记录 |
| 标记损坏或字段冲突 | 具体文件、工作表、字段和冲突双方值 | 取回正确原件或核对来源；不提供绕过冲突的自动绑定 |
| 原单不在当前资料环境 | 明确单号在当前数据目录没有有效对应仓单 | 核对数据目录、删除记录或备份；导入文件不能自行补造一个原签发 |
| 原签发已更新 | 文件修订及摘要，与当前有效修订及差异提示 | 核对原文件和应回传版本；旧文件不得静默套在新签发上 |
| 同店同仓多个候选 | 日期、单号或修订仍不能唯一确定 | 显示全部相关候选与缺失依据；人工选择完整来源，不按“最近一单”默认绑定 |
| 文件包含多单 | 哪些行已分组，哪些来源尚无法区分 | 沿用明确行选择拆分，剩余行继续待绑定；不能一键把全部行绑到一个订单 |
| 目标在所选范围之外 | 已识别身份，但不在本次允许导入范围 | 显示差异；由用户返回明确调整范围，不后台扩大范围 |
| 重复文件 / 重复整单候选 | 命中的文件摘要或同阶段原单，以及此前导入状态 | 复用已有重复处理与修订规则，不把同一来源再次相加 |

候选列表显示门店编码与名称、仓、业务日期、补货单号、签发修订、当前状态及匹配 / 排除原因。可搜索，但搜索不能绕过店仓约束或把已删除仓单变成可导入。候选为空、不能唯一确认和字段冲突分别提示。

确认前用可读核对页展示：原文件及工作表、来源行范围、原单身份、识别方式、数量差异、空白与缺行按现行规则如何处理。尤其区分“已明确导入的完整订单内空白 / 缺商品”与“整张订单尚未回传”；后者不能自动视为 0。

保留原文件摘要和来源行、绑定依据、确认时间及既有操作者信息（若系统提供），不虚构用户身份。预览后文件、原签发或目标状态变化时重新核对，不在写入前跳过并发检查。

### 14.5 签发状态和导出状态分别显示

归档数据库提交与文件系统写出无法被现有流程视为一次整体事务。沿用现有归档原子性，显示各阶段事实，失败时保留已提交修订和已完成文件。

```mermaid
flowchart LR
  A[核对订单范围与原修订] --> B{需要新签发}
  B -->|是| C[确认并提交归档]
  B -->|否| D[读取已归档的固定修订]
  C --> D
  D --> E[逐文件写出并校验]
  E --> F[显示完成 失败 未执行与回执状态]
  F --> G[按原修订重试未完成项]
```

| 失败发生位置 | 用户应看到的状态 | 恢复动作 |
|---|---|---|
| 准备、范围校验或目录预检失败 | 尚未新增签发；指出失败对象和原因 | 修复输入 / 目录后重新核对 |
| 归档提交报错或进程中断，结果未知 | 正在核查归档是否提交，不能直接称成功或失败 | 按原任务证据查询已提交修订，确认后选择继续；不能盲目重签 |
| 归档已成功，文件尚未生成 | 已签发 Vxxx，导出完成 0 / N | 按这次签发修订补导出 |
| 部分文件完成 | 已完成文件、失败文件、尚未执行文件各自列明 | 修复具体原因，仅重试未完成项 |
| 文件已生成，日志或清单失败 | 文件已生成；记录失败，不把整批文件说成没导出 | 先校验原文件及身份，补写记录；不能因为记录失败重签 |
| 历史原件缺失 / 损坏 | 对应原单与原件不可用；可用部分单列 | 沿用明确部分导出确认，不能自动拿最新资料替换 |
| 用户安全取消 | 提交是否完成、已生成文件及取消未执行项 | 保留已生效部分，按原修订继续；提交或压缩安全步骤中不强杀 |

新增或扩展的导出回执至少保存任务、入口、精确原单 / 仓 / 修订 / 摘要、目标路径、文件摘要、各阶段完成时间、原始错误及对应恢复动作。优先复用现有日志和导出清单；补充结构若涉及业务库格式，先说明迁移与兼容影响。

回执逐份安全更新，重启后能够核对“已提交但未导完”的任务。重试前复核原修订仍可导出和目标文件现状；已成功且未被改动的文件不无故重复生成，已被用户编辑的文件不能默默覆盖。历史内部导出继续新建任务目录；门店签发文件遵循既有目标文件覆盖规则，在新文件完整完成前保留原文件。

若回执本身未保存且现有依据不足以确定任务状态，显示“结果待核”，列出需检查的订单和目录，不能声称自动恢复完成。错误信息含可复制的详细原因，但业务提示先说明是否已签发、已生成多少、失败在哪里、下一步在哪里。

### 14.6 目录与资源检查

导出前核对目标目录、写权限、同名文件、可用空间、路径可用性、所需原件和原件摘要。Excel / WPS 占用、网络目录中断、长路径、空间不足分别报告；预检通过后仍可能发生变化，实际写出时保留失败处理。

大数据导出继续使用已有流式路径和有界缓冲，完整哈希可分块计算。临时文件限于本任务约定位置，取消和失败后按已知任务文件清理，不递归清理任意用户目录。文件发布失败时不给半成品冠以完成状态，也不损坏此前完整文件。

只导出原修订所需资料，不为导出刷新平台、重算补货或加载全部历史。性能记录区分准备、原件读取、Excel 写入 / 压缩、发布、回执，避免只用总耗时掩盖实际瓶颈。

### 14.7 定向验证与完成条件

沿用 [身份测试](../../tests/test_order_identity.py)、[回传批处理测试](../../tests/test_lifecycle_batch.py)、[归档批量导出测试](../../tests/test_archive_batch.py)，针对新增失效路径补充验证，不放宽原有保护预期。

| 验证组 | 关键场景与判断标准 |
|---|---|
| 文件往返 | 单仓 / 双仓、分开 / 合并、修改数量、排序、删商品行、重命名、Excel / WPS 另存；身份保留则准确匹配，丢失或冲突则说明具体原因 |
| 不可猜测身份 | 同 SKU 多店、多日期、同店两仓、同名不同编码、混合来源；不能串单或自动选最近修订 |
| 版本与状态 | 预览后新签发、文件改变、仓单删除、切换数据目录；重新核对或拒绝，旧回传不写新单 |
| 数量语义 | 空白、显式 0、缺商品行、整单未回传、单位换算、重复候选；业务结果与既有规则一致，原始依据保留 |
| 导出失败 | Excel / WPS 占用、只读目录、空间不足、长路径和中文路径、所用文件系统不支持发布方式、原件缺失 / 损坏；指出具体阶段及受影响文件 |
| 部分成功与记录失败 | 多店导出中途失败、文件成功但哈希 / 日志 / 清单失败；成功文件仍能被核实，不误报整批未生成 |
| 安全取消与恢复 | 提交前后、写出过程中、重新打开应用后；不强杀提交，修订不重复、范围不扩大、重试不遗漏未完成项 |
| 实际交付 | 使用同一待交付 EXE 从签发到回传完成一遍，并演练导出失败恢复；成功截图和手册步骤一致 |

全部故障注入、删除和中断场景使用隔离数据库与临时文件。实际低配置业务机、不同文件系统或未安装的 Excel / WPS 版本未覆盖时，在交付报告明确列为限制。

本项完成须同时满足：用户反馈的实际问题已复现并修复，或已经有可核验的具体原因及完整可用的恢复路径；不能只增加一段通用提示就宣称修好了“总是失败”。交付报告列出准确入口、复现条件、改动范围、结果等价性、EXE 与文件往返验证，以及仍未覆盖的环境。
