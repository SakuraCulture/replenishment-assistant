# 采购异常恢复与等待流水线

日期：2026-11-10。用户已要求按方案实施；基线为 0.50.1 rc3。本轮应用版本 0.50.2，不改模型、预算、箱规、默认业务参数或供货归属。

## 业务规则

异常任务必须有恢复出口，不能把本地“曾进入上传边界”永久当成仍在执行。区分继续原任务与主动重建：自动恢复只处理原任务；业务明确选择重建时，允许重新生成并再次确认上传，即使旧上传结果尚未核清。界面须展示旧任务状态、原任务号／采购单号，并说明旧平台单不会自动撤销，可能需业务处理重复单。

1. 未上传或准备失败：能继续原任务，也能结束旧准备、生成新预览。
2. 已受理：原任务可继续核对；其等待不得阻止其他订单提交。
3. 结果未知、部分失败、原任务无法核清、已成功但业务需要重做：提供“结束所选任务并重建预览”，不再要求先把旧任务核验成功。
4. 重建只影响勾选项，保留同批未选项；不能强杀正在提交的请求。只有所选旧动作安全退出后才能重建。
5. 重建不自动上传，仍由业务查看新采购预览并确认。新预览采用当前有效签发与付款依据；源订单已删除时禁止重建和复活。

## 历史与防重占用分离

旧采购记录、冻结文件、回执和已关联采购单保留。组件用一次本地写事务释放旧记录的活动预约并建立新预约；保存旧／新采购身份、操作号和时间。重建请求可按相同操作号恢复，不能因回执丢失重复建立后继。

旧记录转为“已结束并重建”，只保留历史用途，不重新派发上传、关联或自动收货。原回执晚到时写入原记录，不重新占用订单，不覆盖新任务。旧采购的周期同步暂停；新采购取得自身单号后再进入自己的收货链。既有平台单不由本功能作废、提交或撤销。

不新增业务主库格式；利用组件现有 JSON 记录保存重建关系。原活动预约的索引键退役，新预约保留正常唯一键，避免删除历史记录或清空防重库。自动重复调用同一命令仍防重；明确重建形成新命令，允许业务选择的新一轮导入。

## 等待流水线

批次默认最多 2 单同时在平台处理中，界面可调整应用侧上限（不是平台承诺的并行能力）。上传和浏览器操作使用原共享会话，依次执行；一单上传结束并保存唯一受理回执后，先提交下一单，再轮询前面的原任务。各单独立核验，异常只挂起本单，不把平台处理中显示为失败。

完整采购主单／商品明细核验继续保留并使用现有浏览器调度，不通过省略验证提速。暂停停止后续派发，保留全部已受理任务；重启按持久身份恢复，禁止把原受理任务当作未提交重新上传。历史身份、删除屏障、稳定 item_id 与执行令牌继续生效。

## 实施与验收

先实现组件原子重建和晚回执处理，再接通批次恢复入口，然后实现上传受理与结果核验分离及有界流水线。保持旧单单接口兼容。

隔离验证至少覆盖：未上传、未知结果、已受理、已成功、部分失败的主动重建；重建回执丢失重试；旧回执晚到；源订单已删；未选项保留；旧同步停用；A 等待时 B 已提交；单项失败其他项继续；并发上限；暂停／重启；完整数量金额校验。使用模拟平台与隔离数据库，不调用真实平台，不删除真实业务数据。

独立打包并执行实际 EXE 验收，保留旧交付，未经要求不推送或合并。实际平台处理吞吐与低配置业务机效果待现场验证，不承诺倍速。
