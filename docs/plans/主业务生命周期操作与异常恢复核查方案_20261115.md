# 主业务生命周期操作与异常恢复核查方案

业务会补单、改单、撤回、重新分配，也会遇到执行一半失败、平台已成功但本机没有收到结果等情况。主流程需要在这些变化发生后，保留已经发生的事实，让业务知道下一步怎么继续，并把影响限制到实际相关的订单、仓和批次。

本次目标是检查整条流程在各种操作组合下能否继续，重点是批量操作中只调整一单、成功与失败混杂、下游已执行后上游更正，以及退出重开后的恢复。先复用现有实现和测试定位缺口，再决定最小修复，不预设重写生命周期框架或增加审批。

必须满足用户补充的三项要求：一是有明确方式恢复到问题操作前的可继续状态；二是恢复足够简单，业务不需要处理数据库、锁文件或技术状态；三是单个订单或旧任务异常不能让整条主流程完全锁死。恢复本身也必须可重试、可追踪，不能成为第二个无法退出的任务。

核查基线为2026年11月15日本地main，提交`f7d5b701c93d9c7f0f1af855430e6e1f515ed7c0`，应用0.53.8、模型0.3.6-rules。开始时工作区干净。本轮只新增本方案，未运行业务操作、修改业务代码或数据库，未提交、推送、打包。下述验收项目是后续执行要求，不代表本轮已全部验证通过。

## 一 业务范围与检查单位

检查范围覆盖：资料采集与采用、门店参数和计算、草稿与补货签发、门店回传、运营签发、聚水潭库存分配、付款核对、翱象采购准备与上传、收货同步与核对，以及对应的导出、跟踪和经营分析读取。

新流程主链为：准备资料与计算 → 补货签发 → 门店回传 → 运营签发 → 聚水潭分配 → 付款核对 → 翱象采购 → 收货。外部文件导入、一键采用和旧流程订单沿既有分支检查，不要求业务补造本机没有发生的环节。历史订单不统一退回新增环节。

以一张具体仓单为基本操作单位，同时检查商品明细、同店另一仓、其他门店、批次和业务日期。批量是明确选择的仓单集合，不能用当前表格位置、门店同名或父单身份替代实际选择范围。

例如同批A、B、C中，A已完成、B失败、C未开始：业务应能看清A的结果，单独处理B，决定是否继续C，也能追加新的D。每个动作必须说明对共享库存和后续顺序的影响，不能为重做B而抹掉A，或让旧B的回调写进C。

## 三 建立按环节和状态的操作清单

每个环节逐项列出：当前事实、可执行动作、实际影响范围、已有结果如何保留、哪些下游需要重新核对、失败后从哪里继续，以及退出重开后的表现。区分业务单据状态、后台任务状态、库存占用与锁单状态，避免一个“待核”代替所有原因。

| 操作 | 核查重点与目标行为 |
| --- | --- |
| 单个或批量新增 | 新订单、新仓单、首次导入单据、追加商品分别核查。不能把新增另一仓当成更新已有仓，也不能凭同店同日覆盖原单。 |
| 批量中只修改一单 | 只生成该单必要的新版本，保留其他单据内容、版本、外部单号和执行顺序；下游变化限定到真实依赖。 |
| 批量中只补做一单 | 明确继续原结果、补缺失步骤还是以新依据重做；已完成单不重复保存、扣库存或上传。 |
| 查询与筛选 | 区分范围总数、当前筛选、本页、已勾选和实际可执行数；明确未显示原因。翻页或改筛选后不能错选、漏选或扩大范围。 |
| 导入同一文件 | 完全相同不重复新增；内容改变按更正处理，原件与旧版本可追溯。数据迁移的新增去重与生命周期更正导入不混为一谈。 |
| 撤回或撤销 | 区分放弃未保存预览、结束本地任务、撤销生成结果、回收站和彻底删除。操作名称及说明对应实际后果。 |
| 彻底删除单个仓单 | 保留同店另一仓及批次其他成员；旧草稿、旧预览、排队任务和晚到回执不得恢复已删单。外部订单不会被本地删除自动撤销。 |
| 重算和重新分配 | 明确采用原冻结资料还是新资料，展示批次与时间；不能把刷新默认资料等同于旧批已经换用新库存。 |
| 补导出 | 按实际保存的原修订补文件，不重签发、不重新分配、不修改付款或外部采购事实。 |
| 暂停 继续 重启 | 暂停后保留已完成结果，继续仅执行剩余明确范围；重启软件能恢复真实状态，不把残留标志永久当成正在运行。 |
| 批量部分失败 | 每单显示已提交、未提交、结果未确认及下一步。独立范围可继续；存在库存顺序或共同事务依赖时，列出准确受影响集合。 |

新增、修改和删除均包含商品明细层面的场景：加商品、减商品、全部改0、0恢复为正量、数量或金额变化，以及重复行、缺行和清单外商品。数量与金额不一致按原业务规则处理，不借此新增商品编码猜仓或额外审批。

## 四 同批订单单独调整与追加

### 只调整原批中的一单

先核查现有原批更正能否完整到达：改单 → 重新核对运营依据 → 更正原批分配 → 重新核对付款 → 更新采购准备。保留原付款、原分配和平台执行事实，标明其依据是否已经变化，不把历史事实清空成“从未发生”。

共享库存继续遵守既有规则：只改B时，保留A和其他未选订单的占用，在允许范围内为B更正分配；不能把其他订单已经占用的库存拿回来补给B。若业务另行要求重排整批库存，须展示完整影响范围并明确选择，不能由单单修改隐式触发。

没有明确批次的历史更正路径，目前存在选齐相关未锁订单的限制。要检查它是否仅在必要情形生效，是否可转入准确原批处理；不能直接解除后改变库存平衡。

### 给原业务批次增加订单

拟按状态区分处理，而不是允许随时改写已执行批次：

- 尚未执行且未冻结的准备范围，可重新选择后预览，并使旧预览失效。
- 已注册或部分执行的批次，不直接改写原执行计划。优先评估关联追加执行记录或续批，并在界面保持原批与追加部分可一起追踪；成功单不重跑，已有成员不重复加入。
- 追加时明确库存依据：沿用原批时只能使用该批按规则剩余的库存；采用新一轮实际仓资料时建立独立库存批次，不能在旧批中悄悄换库存。
- 不允许运行中的旧工作线程继续按变化后的成员位置回写。是否需要短暂停派、何时重新核验，由具体环节的提交边界决定。

“追加仍归同一业务批次”的界面与现有执行批次如何对应，列为需要核查后确定的功能缺口；本方案不提前承诺当前已有此能力，也不自行修改批次库存规则。

## 五 上游修改后的下游处理

| 发生变化的位置 | 必须核对的后续影响 |
| --- | --- |
| 资料或参数改变，尚未签发 | 只让实际受影响的计算结果失效，展示需要重算的门店；保存默认设置不能静默覆盖历史签发。 |
| 补货签发更正或补签另一仓 | 按仓保留自己的版本与依据；另一仓未变时，其回传、付款及分配不能无故失效。 |
| 门店回传更正 | 原运营数据保留，并指出是否需要重新采用或更正；变化顺着实际依赖传递，不能直接改写运营事实。 |
| 运营签发更正 | 原分配保留可追溯，按原批更正范围处理；不能自动重分配所有门店。 |
| 分配结果更正 | 保留旧付款事实，指出付款需要重新核对的依据；采购预览不能继续使用过期付款或过期分配。 |
| 付款更正或平台采购已建立 | 未上传的旧预览失效；已上传的采购保留外部身份，不自动重发或自动作废。需要执行新的外部动作时明确原任务与新动作关系。 |
| 收货后更正 | 保留已收货事实，核查现有更正路径和限制说明；不得直接回滚成未收货或重新占用同一份库存。 |

相同内容重复导入不应无故产生版本变化和下游待核。真实数量、金额、来源或依赖变化仍按原规则处理，不能只比较版本号而漏掉内容变化。旧预览与并发保存发生冲突时，告诉业务具体哪单、哪个环节变了，并给出刷新或重新核对入口。

## 六 恢复到操作前的简单入口

### 恢复依据先留存

在可能改变业务状态的关键操作前，留存本次操作的恢复依据：明确的仓单范围、有效单据版本、批次成员与顺序、库存基准及占用依据、原任务与外部身份，以及本次操作已经完成到哪一步。优先复用现有历史版本、冻结计划和持久回执，仅补缺少的关联与状态，不为每次点击完整复制整个数据库。

恢复点在退出重开后仍可读取，不能只存于内存。对同一操作的重复点击复用同一份执行和恢复记录。若恢复所需的关键记录尚未可靠保存，不进入不可确认的后续提交或外部发送阶段。

“恢复操作前”按实际提交结果处理，不能用旧快照覆盖后来已经发生的新事实：

| 故障发生的位置 | 恢复目标 |
| --- | --- |
| 尚未提交，或已明确完整回滚 | 恢复到本次操作前的已确认业务状态，释放仅属于此次失败尝试的本地准备和失效占位，允许重新操作。 |
| 已提交，界面读回或提示失败 | 读取已提交结果并恢复正确显示，从已完成节点继续；不撤销成功结果，也不重复提交。 |
| 批次部分已提交 | 成功部分保留；其余部分回到各自最近可继续节点，只补未完成步骤。 |
| 平台已受理或结果未知 | 保留原任务及采购身份，先核对原结果；暂时无法确认的订单单独保留待处理，不假装未上传重发。 |
| 故障后有人更正了单据或删除了订单 | 保留后来生效的更正和删除；旧恢复点不能覆盖新版本、复活已删单或撤销其他操作的库存占用。 |

### 一个入口完成恢复

业务页统一提供“恢复并继续”，发生异常时直接出现在该订单或批次附近，不要求业务先回总览、查日志、结束任务，再绕回原页面。操作顺序设计为：选择问题订单 → 点击恢复并继续 → 查看范围和处理结果 → 继续原业务。

程序自动核对恢复点、实际落库结果和当前执行者，决定应刷新成功结果、恢复未提交部分、继续剩余步骤，还是核对原平台任务。界面只解释具体业务后果，不要求业务选择技术状态码或手动判断是否已经提交。

纯读取核对和成功结果刷新不额外确认。需要撤销本地未完成准备或改变生效状态时，在同一页面一次列清影响范围并确认，不连续弹出多轮审批；保留已完成、未选和外部事实。结果显示已恢复哪些订单、从哪一步继续、哪些订单仍待平台核对及具体原因。

恢复过程有阶段、进度和明确超时反馈；可查看上次结果。取消在安全边界生效，不能强杀提交。恢复中再次退出或异常后，重开仍能按持久记录继续。这个入口属于拟补齐的能力，需核查现有恢复记录与入口后实施，不代表当前版本已经具备统一入口。

### 把阻塞限制在真实依赖范围

同批B异常时，A已完成的结果可查可导出，其他无依赖订单、另一独立仓或新业务批次仍可处理。旧任务的本地状态不能永久占住所有操作入口；能证明已经退出或失效的占位由恢复机制处理，正常业务不依赖人工清库或重启电脑。

对共享库存的真实前后顺序依赖，保留原顺序，明确列出等待集合，并提供继续原批、处理失败前序或结束所选未完成项后的正确后续路线。不能为了放行后序而静默重排库存，也不能把同仓一单的问题扩大到整个应用。

真实运行中的提交、另一个活跃实例或真实数据库写锁仍需保护。等待必须有反馈和恢复出口；不能通过删锁文件、抢占正在提交的事务或绕过实例保护来实现“解锁”。已结束任务的残留标志与真实占用必须分开核实。

## 七 异常恢复与防止流程锁死

重点检查以下情况：

1. 本地保存未开始或已明确回滚：保留原数据，允许在条件恢复后重新核对或重试。
2. 已提交但界面刷新、读回或通知失败：先根据持久结果确认已经完成的部分，不能显示成全失败并要求重复提交。
3. 本地批次部分成功：保留成功部分，恢复剩余步骤；库存顺序有依赖的范围不得越过失败前序擅自执行。
4. 平台已受理或结果未知：先查原任务和已有采购号，恢复关联；连接中断不能当成“平台未创建”。其他独立订单不得因无关待核任务被整体锁死。
5. 本地任务已结束但队列、占用或界面仍显示运行：按实际持久状态核对，修复范围限定到相关任务，不以清空库、删锁文件或初始化作为正常恢复办法。
6. 关闭窗口、取消、退出重开：准确区分关闭显示、暂停后续和取消未开始项。提交中的安全边界保留，不强杀任务；关闭后已完成结果继续可查。
7. 原件丢失、文件变化、损坏、无权限、磁盘不足、数据库锁、网络超时、登录切换和资料版本变化：显示具体来源和阶段，保留原异常及未完成材料，避免一个笼统“待核”覆盖所有原因。

统一反馈至少包含：哪张仓单、正在做哪一步、已保存或已受理什么、尚未完成什么、此次影响哪些订单，以及可以点击的下一步。能继续原任务、只处理勾选项、返回更正或补导出的，应就地可达。灰色按钮也应能说明具体条件。

允许正常业务更正，不增加“必须与上游数量完全一致”“必须逐行审批”等条件。真实身份、单位与数值合法性、完整性、并发修改、库存重复占用和平台重复提交结果识别仍保留；每个拦截点都要能解释必要性与恢复路径。

## 八 核查方法与验收场景

先建立操作矩阵，记录当前支持、缺入口、合理限制、已复现缺陷和待验证情况。矩阵按环节、状态和操作分组，不凭已有测试名称推断通过，也不一开始把所有组合都重写一遍。

测试资料全部新建、隔离：至少包含同仓多店共享SKU、同店两仓、两天业务、未选订单、分页外勾选、重复文件、已付款与已收货订单，以及部分完成批次。固定原始库存、数量、金额和顺序，对未选对象建立保存前后签名。

| 场景组 | 必验内容 |
| --- | --- |
| 正常主链与入口差异 | 单个、批量、文件导入和一键采用到达相同业务结果；旧流程按原路由完成。 |
| 同批单单修改 | 批量完成后只改一单；先改后续单再改前序单；加量、减量、全部0、0恢复正量。 |
| 原批追加 | 未执行、部分完成、全部完成后分别追加；重复追加、另一天同店、同店另一仓，不重复消费旧结果。 |
| 删除 | 删首项、中间项、末项；只删一仓；混合成功与失败时删除；全部删除后晚到回写和软件重启。 |
| 多步更正 | 已运营后更正回传；已分配后更正运营；已付款未收货后更正回传；已锁单和已收货走准确处理路径。 |
| 重复与重做 | 连点、重复文件、重复确认、重复继续、只重试失败项、结束后新建；原结果不重复新增或占库存。 |
| 并发与陈旧预览 | 预览后修改上游、更新仓资料、删除或更正目标；另一窗口先保存；旧回调不能覆盖新版本或其他订单。 |
| 异常时点 | 写前失败、事务内失败、提交后读回失败、通知失败、导出一半失败、平台受理后失去回执。 |
| 取消与恢复 | 提交前取消、部分完成后暂停、关闭窗口、正常退出、测试进程预设中断点、重开后继续。 |
| 查询与结果一致 | 跟踪、阶段页、批次详情、导出和经营分析使用正确有效版本；明确历史与当前，计数和未显示原因一致。 |
| 操作前恢复 | 操作前已有状态可恢复；提交前失败不残留半成品；提交后通知失败恢复正确已完成状态。 |
| 恢复简单且不扩大阻塞 | 从出错页直接恢复，不依赖数据库工具、删锁或重启；本单恢复期间其他独立业务仍可操作。 |
| 恢复本身异常 | 重复点击恢复、恢复途中退出重开、恢复保存失败，均不重复执行，也不破坏原恢复依据。 |
| 恢复点之后发生变化 | 其他窗口更正、删除或提交后，旧恢复点不覆盖新事实、不复活已删订单、不释放其他任务的占用。 |

恢复验证必须走真实持久记录，再退出重开核对，不只在内存里改状态。平台部分使用隔离离线适配器模拟未受理、已受理、成功但无回执、作废、重复回执及延迟回执，不调用真实平台。不得把模拟在线成功写成实际平台验收。

涉及修复时，同一固定输入比较新旧数量、金额、顺序、版本、库存预留、原件和关联身份；未选订单及另一仓应保持原事实。对明确缺陷，以业务要求建立期望，而不是把旧缺陷结果当成必须保持的基线。保留每次失败与最终通过证据。

实际打包EXE至少覆盖：混合状态批次中单改、单删、追加或关联续批、暂停继续、重复点击、提交后异常恢复、补导出和退出重开。使用真实窗口、后台线程、本地文件与隔离数据库；不通过整体替换弹窗或保存入口声称完成验收。

## 九 实施顺序与交付

第一步只读梳理当前所有入口、状态和依赖，形成操作矩阵，区分已有能力与真正缺口。优先核查单仓单独操作、部分完成后续做、已付款后的更正、旧任务锁住新业务，以及结果已提交但界面误报失败。

第二步使用隔离案例复现高风险组合，给出准确原因、影响范围和最小修复清单。每个问题说明是入口缺失、状态未同步、依赖判断过宽、库存边界、并发回写还是保存后反馈问题；不能统一归结为“防重太严”。

第三步经确认后分组修复，先处理可能错单、重复占用、误删、旧回调复活和提交状态误报的问题，并把操作前恢复依据与就地“恢复并继续”入口作为第一轮交付范围，不能把恢复路径留到最后。复用现有公共保存、批次和回写能力，不给各环节再造独立审批流程。

第四步完成定向回归、跨环节连续操作和独立EXE验收，按需比较性能与内存，保证不降低默认并发。测试完成后交付操作矩阵、逐项问题与证据、修复范围、业务恢复说明及独立包；旧版本与失败证据保留。

数量、金额、计算模型、箱规、预算、供货归属、默认并发和既有库存顺序保持。若真正需要改变原子提交范围、追加订单的库存语义、已锁单或已收货的更正规则、外部重提策略，单独列明方案与影响后再决定，不夹在异常修复中实施。

验收完成的标准是：原正常流程能走通；业务发生改单、补单和中断后能在准确范围恢复；每个不能继续的动作都有具体原因和明确下一步；已发生事实与未选订单不被破坏。必须实际验证可回到问题操作前的可继续节点、业务从当前页即可简单恢复、故障不会无故阻断整条主流程这三项。仅有按钮可点、数据库多一条记录或某个单元测试通过，均不足以证明整条恢复链完成。

## 十 修复影响范围与作业量预估

以下依据0.53.8首轮核查的4项确认问题、1项旧入口问题及现有168项定向回归估算。估算按一人复用现有实现、包含编写测试和独立EXE验收的有效工时计算，不是测试脚本运行时间，也不是保证完成时间。若后续发现新的原生崩溃、必要的数据格式变更或额外业务规则，需要重新评估受影响部分。

建议分两阶段交付。第一阶段先解决已复现的卡住点，并在采购和库存分配两处落实操作前恢复依据与就地恢复入口；第二阶段将恢复能力补齐到全部主流程。第一阶段完成不能表述为所有环节已具备统一恢复。

### 第一阶段修复已确认问题

| 项目 | 修改方案 | 直接影响与主要边界 |
| --- | --- | --- |
| F01 取消剩余任务封住已受理项 | 按成员状态取消真正未开始项；已受理、已关联和结果未知项保留原身份，提供继续核对入口。只有确实没有待核对外部结果时，才能将整批作为全部结束处理。 | 影响采购队列取消、暂停、恢复与显示。已受理项只查原任务，不进入重新上传路径；未选单及成功单不变。 |
| F02 重新确认返回已取消旧批 | 查重时区分执行状态，复用可继续的原任务或衔接现有后继执行；再次点击跟随同一恢复结果，不重复新建执行批次。没有明确未上传证据时，先核对原采购状态。 | 影响确认上传及重复点击处理。采购包、平台任务身份和上传前校验保留，不能为了按钮有反应就重建平台单。 |
| F03 新批失败留下另一仓原批暂停 | 在批次切换时持久记录本次暂停的原批和控制代次；新批尚未发生分配而失败时，仅恢复本次造成、且未被后来操作改变的暂停状态。已部分提交时保留结果，从实际完成位置继续。 | 影响新批登记、激活、异常收尾和后台恢复。正常批次切换规则不变，不全局激活历史批次，不覆盖后续人工暂停或其他批次选择。 |
| F04 业务已提交但收尾异常只返回失败 | 保留批次ID、已生成清单、提交状态和原始异常；界面显示“已保存，批次状态待恢复”，读取持久结果修复收尾，再直接进入原结果。 | 影响分配回执、生成窗口和结果页。收尾恢复不能重新生成、重复占库存或把结果未知直接认定成功。 |
| L01 旧重试扩大范围 | 封住旧入口或改接现有明确范围的处理；预览、后台调度和执行范围一并约束。若必须依赖前序，列明前序，不静默扩大勾选。 | 当前主界面不走该旧入口，改动要小；库存原顺序仍保留。 |

第一阶段预计涉及8至10个生产模块，主要为`aoxiang_workflows.py`、`aoxiang_workflow_state.py`、`aoxiang_workflow_ui.py`、`aoxiang_upload_pipeline.py`、`jst_batches.py`、`jst_ui.py`、`jst_results_ui.py`、`jst_tasks.py`，必要时增加一个职责单一的恢复辅助模块。具体以补丁审查为准，不为凑齐文件数修改无关模块。

预计涉及5至8个测试文件，增加约30至50个定向场景。这是计划数量，不作为完成度指标；必须覆盖故障时点、重复操作、未选保护、部分成功、历史任务与重开恢复。

### 第二阶段补齐全主流程恢复

在第一阶段基础上，统一回传、运营签发、付款、收货和签发导出的恢复入口。每个入口都先读取当前持久事实，再决定刷新已成功结果、回到未提交前状态、补未完成步骤，还是继续核对原外部任务。保留原整批原子提交和原库存顺序，不统一改成逐单提交。

复用现有单据版本、冻结计划、任务事件和导出回执。恢复记录优先增加必要技术关联，不重写业务原文、不为每次操作备份整个数据库，也不把网络等待放进数据库写事务。恢复自身的重复点击、保存失败和退出重开必须可处理。

历史任务分情况兼容：已有确切订单、版本、采购号和回执时，从这些事实恢复；缺少操作前状态时不猜测整批回滚。例如历史F03无法确定哪些暂停来自当次切换时，提供选择原批并核对后继续，不能自动激活所有暂停批次。后续新操作必须提前留存准确恢复依据。

第二阶段预计再影响4至6个生产模块，重点是公共生命周期保存及业务页的衔接；新增约20至35个恢复场景。完整主流程合计预计涉及12至16个生产模块、增加约50至85个定向场景，仍以实际必要范围为准。

第二阶段预计追加14至24个有效工时；两阶段合计24至40小时，按每日8小时约3至5人日。此合计已包含第一阶段，不能再重复相加。

### 资源与兼容影响

正常路径会增加少量恢复状态及技术身份的读写，恢复时也会增加范围核对。它们按本次订单和操作定位，避免扫描全部历史。实际内存、读写与延迟变化需要新旧对照，不提前承诺为零；不降低默认并发，也不通过关闭完整性检查换速度。

第一阶段预计可通过现有表、事件和回执兼容扩展完成，不需要搬库或改写历史单据。若最终必须增加技术表，需要同时说明旧数据读取、删除裁剪、迁移与回退影响；如涉及业务存储格式、原子提交范围或库存语义变化，另行说明后再实施。

采购组件协议和网页操作优先保持，目标是修复宿主队列与恢复衔接。确需调整组件时，单独列出协议、登记与防重影响，不默认扩大成浏览器或平台采集重构。

### 验证与交付安排

将已复现探针转为正式回归，先证明修复消除了原问题，再跑现有168项及受影响邻近模块。对正常输入严格比较数量、金额、顺序、版本及库存占用；未选单和另一仓保存前后保持一致。对异常路径核对实际提交事实，不能只比较最终提示文字。

实际独立EXE至少安排12类业务场景：未上传取消再确认、混合已受理批次取消、继续原平台任务、原批切换失败、部分分配后失败、分配收尾失败、仅选一单处理、重复点击、上游更正、单仓删除后晚到结果、恢复途中退出、重开继续。另核对正常主链、原文件及导出可用。平台回执使用明确的离线模拟，不宣称真实在线平台验收。

每阶段独立交付源码差异、回归结果、实际EXE证据、恢复使用说明及新包，保留旧包和失败证据，不自动替换现用软件，不执行真实数据恢复。推送、合并按届时授权执行。

本估算不包含原执行批次任意追加成员、改变已锁或已收货的更正规则、自动作废平台采购单、任意回滚已完成业务事实，也不包含对所有页面重排布局。这些属于单列的业务能力，避免借恢复修复扩大工程范围。
