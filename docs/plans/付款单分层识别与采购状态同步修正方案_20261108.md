# 付款单分层识别与采购状态同步修正方案

日期：2026-11-08，业务时区：Asia/Shanghai。

状态：业务方案已确认，待开发。当前本地交付仍为0.48.6 rc1，固定构建源码为 `b5f77bed4c9e3161e1f14b3c56bbf35c7b26f79a`，验收证据提交为 `19f49f2a1950e234693ec972ea928100bad8e69a`。本文不代表下述新增能力已上线。

## 1 目标与核查依据

聚水潭付款表不天然携带补货助手签发号，也可能没有供货仓，两边门店名称还可能存在细微差异。付款导入应先利用已有关系、生命周期、时间和门店逐层缩小范围，再核对商品明细。能唯一确认时自动带入仓单，存在歧义时展示原因和候选，减少手工找单、填写签发号和反复搬表。

本次一并纳入采购作废状态、已知采购单号查询，以及历史关联记录误入收货同步候选的问题。继续复用已有签发、回传、分配、付款和收货服务，不重新开发整条业务链。

本次会话只读核查确认：

- 收货快照已读到4张采购单为“已作废”，但仍要求实收字段，终态停止标记没有成立。创建关联时状态与最新收货观察状态没有正确联动。
- 采购台账有10条已关联记录，其中6条无法通过本机正式单号解析找到对应订单，另4条属于当前订单。这是核查时点的结果，实现不得写死数量或单号。
- 批量收货候选读取全部已关联记录，从当前作业进入时未带入本批范围，也未统一检查本地业务是否仍有效。
- 已知采购单号的查询仍强制结合门店和时间筛选。
- 用户付款样表使用“买家帐号”，现有适配要求“买家账号”，未自动识别出付款工作表。

样表“580.77柴小囤（琅琊古城店）20261107.xlsx”有155个不同商品，数量合计157、商品金额合计580.77元，内部订单号1314390。不能仅凭这些汇总值推定数量单位或签发归属。原件SHA-256为 `d4fabc6a707653e35823486ea17452bd738b7bab8bf6d53732a0d6a6c2877414`。这是模板核查结果，未实际绑定任何真实签发单。

## 2 文件读取与业务入口

用户仍从现有付款核对或批量单据导入入口选择文件，不增加必经配置页，不要求预先填写签发号、供货仓或技术性的“账套”。识别与商品核对在同一流程内完成。

一份文件有多个内部订单号时，按完整来源订单分组，分别识别。保留文件、工作表、行号、原始字段和原始值，不混单、不累加、不按文件到达顺序覆盖。表格外的合计单元格不当作商品行。

兼容“买家帐号／买家账号”等明确字段别名。内部订单号、商品编码、数量、商品金额为本类模板的核心字段，其他字段按实际用途处理。缺辅助字段不直接判整表不认识，缺关键依据则给具体提示。同义表头同时出现且不唯一时，不擅自选列。

内部订单号是聚水潭订单标识，不是补货助手签发号。不能由线上订单号、文件名或相近日期推算签发号。

## 3 门店和来源身份

### 3.1 门店名称不同

以已确认的统一门店编码为业务身份，显示名称和编码，同时保留翱象、聚水潭各自的原始名称。已核验的跨平台编码对应关系优先使用。

空格、全半角、括号等可做格式归一化；简称、品牌前缀及分店别称仅推荐候选。例如“柴小囤（琅琊古城店）”和“柴小囤便利超市（琅琊古城店）”可以成为对应候选，不能直接通过删除“便利超市”等词语认定同店。

用户在付款核对页首次确认后，记住来源名称与统一编码的对应关系。相同简称对应多店时保留歧义，不默认第一家。尚无确认关系时，也可先用商品明细找候选，但必须展示双方名称、门店编码和“门店对应待确认”，不默默保存永久映射。

### 3.2 内部订单号的使用范围

“聚水潭来源企业或连接范围”用于避免不同企业数据中的内部订单号碰巧相同，不等于山东仓或河北仓。同一企业多个仓可共享数据范围，不要求用户另填“账套”。

首次确认后记录来源身份、聚水潭内部订单号、本地订单身份、签发修订、仓及确认依据。后续同号导入优先读取该关系。

来源身份优先取现有连接中可核验的稳定标识。取不到则待核，不编造企业标识，不用买家账号或手机号码代替。跨连接复用先确认属于同一数据范围。

## 4 分层缩小候选范围

### 4.1 检索顺序

| 层次 | 依据 | 处理方式 |
| --- | --- | --- |
| 已有对应关系 | 来源身份与聚水潭内部订单号 | 定位原仓单，并复核存在性、修订及状态 |
| 生命周期 | 当前入口和业务进度 | 首次付款优先回传已确认、已生成、待付款的有效仓单 |
| 时间 | 付款表下单时间、本地业务及作业时间 | 先同日及附近日期，再按需扩大，不强制同日 |
| 门店 | 统一编码、已确认别名、名称候选 | 确认关系作为约束，名称相似只推荐 |
| 汇总特征 | 款数、数量合计、金额 | 分完全匹配与存在差异的候选，减少明细读取 |
| 商品明细 | 编码或唯一条码对应、逐项数量金额 | 完整核对剩余候选，识别具体供货仓 |

界面示例为：有效仓单120张，待付款18张，日期附近优先候选6张，门店候选2张，明细完整匹配1张。数字仅为模拟，不是实测结果。

每层展示检索范围、剩余数量和排除原因。无候选时说明停在哪层，提供扩大日期、查看该门店其他未完成作业、切换其他生命周期的入口，不只报“识别失败”。

### 4.2 生命周期与时间的边界

首次付款、重复导入、补单和付款更正需要不同范围。首次付款默认优先待付款池；已确认过的内部订单号，即使本地已付款或已结束，也应识别原关系并进入相应核对流程，不能一律排除已付款单。

聚水潭下单时间不等于签发日期。跨日付款、补录、晚到文件可扩大检索。时间窗口在识别页可调整，新增默认范围在开发时结合业务确认，不擅自设成固定“三天”等强制规则，不修改模型日期和归属。

“优先层只有一个”不等于“唯一对应单”。自动带入前，须通过轻量索引检查相关有效候选池有无同内容仓单，不能只找到同日一张，就漏掉跨日未处理的同内容单。无法完成唯一性检查时，显示检索范围和待确认状态。

来源身份、已确认关系和订单有效性不能为了找到结果而静默放宽。日期接近、名称相似、金额接近只用于检索和排序。无签发号的未绑定来源单不得因扩大范围而复活已删除、失效或退役订单；已有关系指向这些记录时，展示原关系和失效原因，不悄悄改绑当前修订或其他订单。

## 5 从明细识别仓单

优先比较当时已保存的聚水潭生成明细，因为实际分配可能少于回传或签发建议。没有生成结果时，可用有效回传或签发提供候选和差异，不能宣称为“生成明细完全匹配”。

付款表没有仓字段时，从匹配的仓单携带供货仓。不能按商品是否存在于某仓现行资料判断仓，也不以当前主从仓顺序代替当时分配结果。

逐项核对规则：

- 商品编码精确匹配。辅助码只能按现有规则唯一对应原签发条码，不模糊猜商品。
- 数量金额按十进制语义比较并保留原值，不用浮点容忍或抹平差额制造一致。
- 不凭箱规乘除数量。单位来源不明确则待核，不能把箱规“／”当换算证明。
- 缺失、空白、明确0和清单外商品分别保留，不通过丢行、补0或忽略额外商品制造完全匹配。
- 总额相同不能代替逐商品一致。摘要只加速检索，带入前仍核对真实明细。

| 识别结果 | 业务行为 |
| --- | --- |
| 门店已确认，且有效范围内唯一完整匹配 | 自动带入仓单，展示仓与依据；用户完成原付款核对后保存 |
| 内容唯一，但门店别名未确认 | 推荐候选，同页确认门店对应后继续，可记住已确认关系 |
| 多候选、数量金额差异或部分内容相符 | 展示候选及逐项差异，允许整单选择一次，不默认第一张 |
| 无候选或依据不足 | 展示缺口和扩大范围入口，不猜仓、不硬绑、不自动创建订单 |

数量、金额有差异不等于不是这张单，不能为了缩小范围丢掉真实差异候选。同店同仓两张内容完全相同的有效单据，必须让用户选择一次。可能混仓或一份付款对应多张签发时，首期提示此情况，不自动拆单或分摊；拆分规则另行确认，不借识别改变付款对象和范围。

## 6 核对与保存

识别页显示内部单号、原店名、统一门店名称和编码、供货仓、签发号及修订、匹配依据、差异和检索范围。当前查看范围与完整保存范围分开，筛选不改变提交范围。

首次确认后保存对应关系。后续同号定位原单，内容变化展示与上次的差异，沿用完整付款单版本及校准规则；不无条件覆盖，不重复增加相同付款版本。付款样表本身不证明已经实际付款，原核对确认要求保留。

预览后订单、修订、生成单、付款版本、门店映射或来源文件变化，旧预览失效并重新核对。保留并发检测、取消、失败回滚、重试和本批原子保存，不改逐行分批提交。

## 7 已知翱象采购单号直接查询

业务定位使用当前商家身份和已核验采购单号，不再要求用户手填店名与日期。门店、供应商和原付款依据由程序自动核验。

实施时先验证平台是否支持仅按单号精查。支持则引入独立查询口径，捕获并核验实际请求中的准确单号，不能只去掉界面输入框、仍保留旧日期筛选而漏单。

平台若强制日期或门店，内部自动使用原生制单日及已确认编码，不拿今天或本机时间猜测。不同模式的查询、下载任务及范围证据不得混用，原日期批量查询保持。

## 8 已作废采购单与收货同步

创建关联时状态、最新平台观察状态和本地业务进度分开。保留原绑定及原件，最新状态通过新观察记录表达，不覆盖旧证据。

| 核验结果 | 自动同步行为 | 本地业务处理 |
| --- | --- | --- |
| 正常未完成 | 按已启用计划查询，不提前记实收 | 保留原生命周期 |
| 已完成且完整实收核验通过 | 停常规轮询，恢复必要的最终实收保存 | 沿用正式收货服务 |
| 已作废，主子单及归属一致，无冲突收货事实 | 记作废终态，停止常规轮询，不产生最终实收待办 | 显示平台已作废，保留签发、付款与关联，不记收货0、不自动退款或删除 |
| 作废伴随部分实收、主子状态冲突或既有终态回退 | 暂停自动处理，保留证据 | 进入作废后待处理，不清空已有实收、不自动关本地业务 |

作废单不再要求空白实收字段必须有值。停止轮询与记正式实收分开，不能把作废套入等待最终实收的逻辑，造成无限待办。

订单跟踪、采购批次、收货同步和周期计划显示同一份最新状态及观察时间。查询失败不能覆盖已核验状态，旧绑定状态不冒充当前状态。单仓作废只处理对应仓单，不连带关闭同店同日另一个仓。

## 9 历史关联记录与同步候选

从付款或采购批次进入同步时，默认带当前批次或勾选仓单。全局管理另设明确入口，正常候选仍只包含本地有效、关联有效且适合执行该动作的订单。

页面候选、立即同步、周期启用、到期排队和执行前统一判断有效性。已删除、退役、失效或平台作废记录不进入正常池。历史在审计视图查看，不能从历史入口绕过执行校验。

业务删除成功后，关联调度应安全退役。保留审计、平台身份和必要防重依据，不以直接清空关联台账隐藏问题。开发前重新核查，不按截图编号或本次6条数量硬编码清理。

尚未开始的失效排队任务安全取消，执行中的任务协作停止并保留已提交结果，不强杀提交。清理动作有对象和影响预览，保持原删除事务原子性。跨库退役不能伪装成单库事务；即使退役投影尚未完成，执行前的本地有效性检查也必须阻止脏任务运行。

## 10 资源约束与实施顺序

识别只在进入付款业务或用户发起时按需执行，不在启动时扫描历史明细。先用订单头、生命周期、时间、门店、仓单摘要和对应关系筛选，最后只读少量候选明细。

索引保留轻量摘要和版本引用，不复制全部签发或压缩快照。缓存可重建，不能作业务证据；写入、映射变更及删除使相关索引失效。缺索引时展示建索引或检索进度，支持取消，不静默全库解析。

开发验证分别记录不同历史规模下的首次、已有索引、扩大范围和取消耗时、工作进程内存与读写。不把合成测试当低配置业务机实测，不承诺固定秒数或整机资源上限。

第一步修作废终态、候选及调度有效性，验证已知采购单号查询方式。第二步做付款模板、门店对应、分层索引、明细比较和首次确认后的内部单号映射。第三步完成跨入口联调、资源对照、实际EXE验收及独立打包，保留旧版本。

不改计算模型、预算、箱规、归属、分配算法和历史留存语义。未经另行确认，不改存储格式，不清理真实数据，不调用真实平台开展测试，不推送或合并。

## 11 验收场景

| 场景 | 通过条件 |
| --- | --- |
| 样表用买家帐号，无签发号和仓 | 正确识别付款来源，原字段保留，不要求用户改表头 |
| 门店名格式或业务别名不同 | 格式可归一化；业务别名未确认不默默保存映射 |
| 同日与跨日有同内容候选 | 不因优先搜到同日一张就认定唯一 |
| 跨日付款、补录、晚到文件 | 可扩大检索，不误报无单 |
| 已付款重复导入或更正 | 找到原关系，进入对应核对，不重复记账 |
| 合计相同但部分SKU不同 | 不判完整匹配 |
| 两仓资料有同SKU | 按历史生成明细识别，不凭现行资料猜仓 |
| 同店同仓两张相同单据 | 展示多个候选，整单确认，不默认第一张 |
| 混仓、部分付款、缺行、空白或额外商品 | 展示具体情况，不擅自拆单、补0或丢行 |
| 内部号相同但来源企业不同 | 不串单，身份取不到则待核 |
| 预览后修订、付款、映射或文件改变 | 拒绝旧预览，保持并发检测和整批回滚 |
| 已知PO号但日期或店名不同 | 不要求手填；准确单号查询，必要条件可信自动带入 |
| 作废且实收为空 | 显示作废、停止轮询，不写0、不留最终实收待办 |
| 作废伴随实收或状态冲突 | 保留证据，进入待处理，不覆盖既有事实 |
| 历史采购找不到本地订单 | 不入正常候选，也不能经后台调度执行 |
| 从本批进入同步 | 只带本批或勾选范围，不默认全部历史 |
| 页面打开后订单被删除 | 执行前重验并阻止启动，不信旧页面缓存 |
| 缺索引、扩大检索、中途取消 | 有范围与进度，取消无业务写入，恢复不重复提交 |
