# 每日门店缺货率分析独立板块方案

日期：2026-11-07。状态：**方案，尚未实施**。

本次补充已由用户明确：指标是**门店缺货率**；支持剔除淘汰品、考核品的视角；两类都依据聚水潭原表“虚拟分类”，分别识别“标杆淘汰”系列和“淘便考核”。商品类目（资料“分类”）及仓库上游供货商切面纳入首版。

用户进一步明确：分析资料与原补货业务保持独立，不能随分析更新而替换原业务资料；未进入分析板块时，不应加载庞大的分析数据和能力。本方案据此增加资料采用边界、按需加载及退出释放，并将每日后台采集设为**默认关闭、单独启用**的选项。数据每天积累、资料更新频繁和低配置电脑资源压力，是这项隔离设计的业务依据。

核对基线：应用0.46.5，提交 `0ae49f9e6bca9f3d69911f0f9a859e8006648546`，模型0.3.4-rules，仓归属能力0.5.2。本轮只编写方案及文档入口，不改运行代码、不升级版本、不启动采集或定时任务、不操作真实平台。实施前重新核对工作区和最新交付。

## 1. 目标与首版范围

新增顶级入口 **“门店缺货率分析”**。每天取得所选门店在翱象“全部商品”范围的补货建议，保存独立日快照；依据同批冻结的聚水潭仓商品资料、门店供货设置和必卖清单，观察有月销商品在门店的缺货情况。所有切面都使用翱象门店可用库存判定缺货，聚水潭仓库存仅参与既有供货归属或辅助观察，不作为缺货率分子。

核心指标按用户指定口径：

> 门店缺货率 = 当前视角内月销大于0且门店可用库存等于0的店品数 ÷ 当前视角内月销大于0的店品数。

主要回答：哪些门店缺货率高；中心仓、地采各缺多少；必采商品是否缺货；缺货集中在哪个供货仓、商品类目、上游供应商；这些情况每天如何变化。

首版包含手动采集、可选择启用的每日定时采集、任务恢复、每日趋势、门店排行、四类交叉分层、淘汰/考核品剔除视角、仓库/商品类目/供货商切面、商品明细和独立Excel导出。默认按需使用；进入页面只读取所需汇总，不自动开始采集。分析不依赖当天是否计算补货、是否签发、是否产生采购单；也不生成补货数量、签发单、采购单或收货记录。

这里衡量的是**每日观测时点的门店有销商品缺货率**。每天采一次不能证明全天缺货时长，也不能恢复开始采集之前的历史库存。

## 3. 指标口径

### 3.1 统计单位与公式

基础记录为 **分析日期 × 门店编码 × 商品编码 × 日快照修订**。同一修订中一店一商品只出现一次；同一个商品在两家独立门店算两个店品，一店两仓不能重复算两次。门店以已核验的翱象仓店编码为准，名称仅展示；一份平台仓店数据不能复制给多个别名门店后重复累计。

对某日、某筛选范围，设：

- `M`：翱象原表“月销”。沿用原字段，不擅自改成自然月销售额或自行重算销量窗口。
- `K`：翱象原表“可用库存”，表示门店可用库存；不是聚水潭大仓库存。
- `B = {有效店品 | M > 0}`：有月销基数。
- `O = {店品 ∈ B | K = 0}`：缺货集合。
- `缺货率 = |O| / |B| × 100%`，保留两位百分比用于展示，计算及汇总不先四舍五入。

示例，仅用于解释口径：100款有月销商品中8款可用库存为0，缺货率为8%；另外20款零库存且月销为0的商品不进入分子，也不进入分母。

### 3.2 边界处理

| 情况 | 主指标处理 |
| --- | --- |
| 月销>0、可用库存=0 | 计入基数和缺货数 |
| 月销>0、可用库存>0 | 只计入基数 |
| 月销=0，包括零库存新品 | 不进入本指标；仍保留原始记录及排除说明 |
| 月销>0、可用库存=0、在途>0 | 仍算缺货；可在“缺货且有在途”切面查看 |
| 月销>0、可用库存为负、空白或非法值 | 计入已知有销基数，但库存判定待核；受影响范围不发布正式缺货率，不把负库存改成0或当成有货 |
| 月销缺失、非法或负数 | 基数资格待核，不当作无月销；受影响门店正式指标显示待核，已确认款数可查看 |
| 月销明确为0、库存字段异常 | 本行明确不在主指标基数内，保留异常，但不凭此改变主指标分母 |
| 分母=0且来源完整 | 显示“—／无有销商品”，不显示0%或100% |
| 价格、箱规或在途缺失 | 不因此阻断有效M/K的基础缺货率；只影响对应扩展字段/切面 |
| 停采、禁用、备用、拒收、资质受限 | 只要M>0仍进入全量总体；剔除视角仅按所选淘汰/考核标记筛除，不连带套用补货执行排除规则 |
| 淘汰品、考核品 | 全量视角保留；选择相应剔除视角时同步从分子和分母移除，规则见第4.4节 |
| 重复/冲突商品、无效身份、表头或原件完整性异常 | 不猜测、不一对多连接；阻止受影响门店发布完整日结果，保留原因及原件 |
| 采集失败、未采、文件缺失 | 显示未取得，不能记为零缺货或零基数 |

来源/必采/类目/供应商等**维度缺失**与M/K、身份等**指标依据缺失**分开。有效M/K仍可计算总率，维度未知进入明确的待核分组；不能因为供应商为空而从总分母删除商品。若仓资料采集失败，可展示独立验证通过的门店缺货总览，分层明确不可用，不发布假完整分层。

### 3.3 多店、多日与筛选

1. 多店总缺货率使用 `Σ缺货店品数 ÷ Σ有销店品数`，不平均各店百分比。示例：10/100与180/900合计为190/1000=19%，不是15%。
2. 按7天、30天汇总时命名为“期间缺货率（店品日加权）”，使用每日分子分母之和。单日趋势仍逐日显示；不能把多日累计店品数叫去重商品款数。
3. 同一切面的分子分母必须在同一日期、门店、供货类型、必采、仓库、类目、供货商及淘汰/考核剔除视角内。分组率不能相加。
4. 多店总览另列“采集完成门店数／所选门店数”。只取得部分门店时，显示“已完成X店范围结果”，不能冒充所选全部门店结果。
5. 明细的“只看缺货商品”只筛下钻表，不改变上方缺货率分母；否则点一下就变成100%，失去意义。
6. 环比用百分点，例如10%到12%为上升2个百分点。默认同时展示分子、分母变化；门店范围变化时提供“共同门店”比较，且仍提示有销商品集合会变化。
7. 连续缺货只按连续、有效的每日观测判断，缺采日打断连续性；这是连续观测缺货，不是已证实连续全天无货。该衍生指标可放第二阶段，不挤占首版。

## 4. 分层与切面

### 4.1 必采与非必采

“必采”使用分析明确采用的必卖清单，按商品编码精确匹配，并冻结清单内容及版本。首次可只读采用原补货清单，后续不自动追随其更新，见第7.1节。不是“本次建议补货数量>0”，也不是“本月实际买过”。未取得明确有效清单时为“必采属性待核”，不能默认全部非必采。明示采用内置清单时必须显示其来源版本，不在后台偷偷修改日常清单。

必采属性独立于供货来源。因此首页四类均可存在：

| 重点分层 | 分母 | 分子 |
| --- | --- | --- |
| 中心仓·必采 | 该组M>0店品数 | 该组M>0且K=0店品数 |
| 中心仓·非必采 | 同上，限定该组 | 同上，限定该组 |
| 地采·必采 | 同上，限定该组 | 同上，限定该组 |
| 地采·非必采 | 同上，限定该组 | 同上，限定该组 |

底层还保留供货来源待核、必采属性待核，采用互斥完整分组；首页展示四类及“分层待核”汇总。来源和必采同时未知的同一店品只进入待核汇总一次，不能把两个异常计数相加。已知四类加待核应还原总分子、总分母。

### 4.2 中心仓与地采

采用0.46.5供货范围规则，冻结分析已经采用的每店主从仓设置及本批仓资料；设置的独立采用方式见第7.1节：

- 山东单仓：山东有资料归山东中心仓；山东无该编码归本次地采，不因河北有资料而待核。
- 河北单仓：对称处理。
- 双仓：保持现有主从仓判断，包括主仓库存未知保留主仓、主仓有资料而从仓缺条目时保留主仓等规则。
- 整份所需仓资料缺失、路线未配置、编码冲突时，不用“没匹配上”冒充地采，进入归属待核。
- 有商品条目但仓库存为0或禁用，不因这个原因变为地采。

供货仓是本次规则下的归属，不代表门店现货历史上一定从该仓购买。每日仓库存变化可能使双仓归属变化；历史按当日冻结版本展示，不事后重分组。

### 4.3 首版切面清单

| 维度 | 设计与来源 |
| --- | --- |
| 日期、门店 | 单日/区间、单店/多店，展示采集覆盖与实际观测时间 |
| 中心仓/地采/归属待核 | 同批冻结构成，沿用上述规则 |
| 必采/非必采/属性待核 | 当批冻结必卖清单 |
| 山东/河北供货仓 | 只对中心仓适用；地采显示“不适用”，不借另一仓身份 |
| 商品类目（商品资料“分类”） | 中心仓取归属仓同批原件的“分类”；支持筛选、汇总、排行、下钻以及类目×门店交叉查看。首版一层原类目；地采只有翱象原表具备已核实类目才赋值，否则“类目未提供” |
| 仓库上游供货商 | 从归属仓同批原件“供应商名称”按SKU精确匹配；缺编码时用“仓库＋供应商原名称”，不跨仓猜测合并。支持供货商×门店、供货商×类目。地采不套用另一大仓供应商，显示“不适用／地采供应商未提供” |
| 淘汰/考核品视角 | 全量、剔除淘汰品、剔除考核品、两者都剔除；各自重新计算同范围门店缺货率 |
| 商品状态、补货状态 | 仓商品启用/备用/禁用与翱象正常/停采分开；状态缺失明确显示，不能互相替代 |
| 在途情况 | 缺货且有在途／无在途／在途待核；在途不抵扣缺货数，也不能据此承诺到货时间 |
| 商品编码/名称 | 查某商品哪些店缺货，显示有销门店数、缺货门店数、具体门店列表 |

同维度多选为“或”，不同维度之间为“且”。供货商、类目、门店和必采等可以组合筛选，如“山东仓＋必采＋饮品＋某供货商＋剔除淘汰及考核品”。类目缺失仍计入“类目未提供”，不能隐藏地采后声称是全店类目分析。

商品原类目与快销/日百等计算分类组不是同一个维度。首版以原商品类目为主；地理区域、运营人员、商品品牌、多级类目等没有可靠映射时不推断，作为后续资料扩展。

供货商切面表示“该供货商资料所对应商品在所选门店的缺货情况”，不能直接判定缺货由该供货商履约造成。大仓可用库存为0可作同时出现的现象辅助查看，不自动给出责任归因。

界面及导出的指标名称必须保留“门店”：例如“山东仓供货商品的门店缺货率”“某供货商商品的门店缺货率”“饮品类目门店缺货率”。每组分母是该组中有月销的门店商品，分子是其中门店可用库存为0的商品；不能改用仓库有销商品数、仓库零库存数或仓库SKU总数。

### 4.4 淘汰品、考核品的可切换剔除视角

默认保留全量口径，提供四种明确视角：

| 视角 | 从基数及缺货数中移除的商品 |
| --- | --- |
| 全量 | 不因淘汰/考核标记移除 |
| 剔除淘汰品 | 已识别“标杆淘汰”系列 |
| 剔除考核品 | 已识别“淘便考核” |
| 剔除淘汰品和考核品 | 上述两类的并集，双重命中只剔除一次 |

用户已确认两类都取**聚水潭原生商品资料的“虚拟分类”列**。不使用名称猜测，也不把商品状态、商品等级、商品类目或另一列“商品标签”当作同一字段。

- 淘汰品沿用当前已核实的精确标签：`标杆淘汰`，以及 `标杆淘汰（箱规废弃）`、`标杆淘汰（厂家停产）`、`标杆淘汰（夏季）`、`标杆淘汰（冬季）`、`标杆淘汰（拉回下单）`、`标杆淘汰（样品/赠品）`、`标杆淘汰（质量问题）`、`标杆淘汰（节庆商品）`、`标杆淘汰（召回退供）`、`标杆淘汰（河北仓专属）`。明确的新子标签可补入版本化映射。
- 考核品精确识别 `淘便考核`，单独保存考核标记，不并入淘汰品。
- 多个标签按已核实的逗号、分号或换行等分隔后逐项匹配，保留原文；不能用“含淘汰”或“含考核”模糊匹配。`待淘汰`、`不淘汰`、`厂家下架`等未确认名称不自动剔除。
- 取中心仓商品**当日归属仓**的同批原件；另一仓标签不同不替代本仓。地采若本次供货资料无对应条目，标签依据为未取得，不从未选仓借标签，也不改变本次地采归属。
- 原件该列存在且为空，可确认无上述标签；缺列、未留原件、无对应商品或编码冲突不能当作“已确认正常”。
- 标签未知的商品默认保留在分子和分母，单列“标签待核”及覆盖情况；有未知时，调整后结果明确标为“剔除已识别淘汰/考核后的门店缺货率，含标签待核X款”，不声称已完全排除。全量口径不因标签缺失失效。标签待核的有销款数、其中已确认缺货款数可下钻。

计算使用同一集合：设 `X` 为当前视角选定的剔除集合，则 `B_view = B \ X`，`O_view = O ∩ B_view`，调整后门店缺货率为 `|O_view| / |B_view|`。只减少分子而保留原分母是错误口径。

例子仅用于口径核对：全量100款有销、20款缺货；淘汰品和考核品去重合计10款，其中4款缺货。剔除两者后为16/90≈17.78%，不能算16/100。若全部有销商品被剔除，显示“—／当前视角无有销商品”。剔除后比率也可能上升，不预设必须改善。

每个视角保留：原始有销/缺货款数、剔除有销/缺货款数、调整后有销/缺货款数、双标去重及标签待核数量。主页面、四类分层、门店排行、日趋势、类目、供货商、下钻和Excel必须统一采用所选视角；全量与调整后可并列对比。

**剔除只是分析筛选，不删除原始商品或改写日快照，不改变必采身份和供货归属，不修改现有补货及五段漏斗规则。** 首版可以复用旧漏斗的精确淘汰枚举，但不能调用其整体 `inclusion()` 过滤，否则会同时排除停采/禁用等用户没有在此视角选定的范围。

## 5. 每日采集和历史快照

```mermaid
flowchart LR
    A[手动采集 或 已启用计划到时] --> B[等待原业务空闲并取得共享租约]
    B --> C[冻结分析已采用设置及本次仓资料]
    C --> D[逐店获取翱象全部商品补货建议]
    D --> E[身份 范围 行数 原件及字段校验]
    E --> F[独立分析快照与日汇总]
    F --> G[门店缺货率 全量及剔除视角 切面 Excel]
```

### 5.1 当日流程

1. 首次进入时才初始化分析资料目录及配置。新板块独立保存所选门店、已采用供货设置、必卖清单版本和计划。复用已核验连接与门店身份，不复制登录态，不重新要求配置另一套浏览器。
2. 默认点“采集今日”才取数。每日计划默认关闭；若用户单独启用，建议时间08:00、北京时间，可调整。启用时明确提示“未打开分析页面也会采集今日快照，运行时会占用浏览器、内存和硬盘”；本轮不创建或启用任何计划。
3. 单日任务开始时冻结**分析已经采用的**门店范围、每店供货路线、必卖清单，而非再次自动采用补货侧最新设置。首次可只读导入补货侧已保存版本；后续更新须在分析内明确采用，规则见第7.1节。所需仓按并集获取，每仓一份，不按门店重复下载仓资料。
4. 手动采集或已启用的每日计划，默认取本次分析用途的聚水潭资料快照，并取得所选门店翱象全部商品。资料只落分析目录，不发布为日常默认仓资料。若明确选择复用已有仓快照，先核验并存为分析自有的不可变副本，显示真实采集时间及版本，不能把旧资料标成本日刷新。
5. 翱象获取完整商品范围，再在本地按月销筛基数；不能在导出前只保留建议补货、必采或可售商品。
6. 每店完成后立即校验并分块存入分析暂存区，保留原生文件、任务号、查询范围、行数及哈希。完成集合可预览；日报正式修订引用确定的一组快照，不混用正在写入的半份数据。
7. 同一任务重试继续原命令，只补未完成门店。成功文件及仓资料依据不重复取；结果未知时先查原任务，不盲目重新导出。
8. 完成后一次发布新日报修订，工作进程正常退出并释放租约。离开页面时的默认行为是安全暂停手动任务、释放查询资源；用户明确选择“本次继续后台采集”，或该任务由已启用的每日计划触发时，采集可继续，规则见第7.2节。仅打开每日计划开关不等于授权所有手动任务后台继续。关闭页面不等于强杀正在提交的动作。

### 5.2 同日重采、失败和跨天

- 默认一个计划时点对应一份日结果。普通刷新读取该日快照，不自动重新发起全部平台导出；“重新采集”明确产生候选修订，验证后采用，保留前一版追溯。
- 一个日报修订使用固定的一套仓资料、供货设置和必卖清单。只补失败门店时不偷偷换依据；若更新这些依据，重新生成完整修订，不把两种口径拼在一起。
- 个别门店失败不清空其他门店成功数据；部分结果有明显覆盖提示。总览、趋势、下钻和导出绑定同一日报修订及成功门店集合。
- 采集开始、结束、每店查询观测时间、平台原生数据时间（如提供）、分析日期分别保存。多店串行取得的是一个观测窗口，不能声称同一秒的全店库存。
- 软件关闭、电脑休眠或未登录时不能保证每日采集。同日恢复可补采并显示“晚于计划”；跨天漏采不能拿今日库存补昨天。
- 跨午夜取得的原件不能凭旧任务业务日期标为前一天库存；依据可信观测时间分日，前一天未取得的门店保留缺采。
- 历史补入只能使用具有可信当时观察日期及来源的完整原件。当前接口未证明支持任意历史日期库存回查，首版不承诺自动补历史。
- 月销窗口会每日移动，商品进入/退出有销基数；看趋势时同时显示分母，避免把商品集合变化误认为缺货改善。

### 5.3 每日记录与不使用时的资源边界

| 使用方式 | 未进入分析页面时 | 历史数据的结果 |
| --- | --- | --- |
| 按需使用，默认 | 不打开分析库、不启动分析任务；进入后仍须主动采集 | 仅保留实际采过的日期，缺采日留空，日后不能补出当时库存 |
| 启用每日采集 | 只保留小型计划触发器；到时才启动一次采集工作，结束后释放；不创建分析页面或扫描历史 | 积累实际成功取得的每日快照；关机、休眠、未登录或资源繁忙仍可能缺采 |
| 本次离开后继续采集 | 仅本次已明确授权的任务继续；完成后退出，不自动变成每日计划 | 增加本次观测结果，不补其他日期 |

定时关闭与本次任务停止分别显示，关闭未来计划不能静默丢弃已受理任务。界面提供“停用每日采集”及“安全暂停本次采集”；暂停保留原任务号和成功文件，恢复先查原任务。应用重启时，计划关闭的未完成任务不自行复活，进入板块后再由用户继续；计划开启时也不得绕过未完成任务另发同范围导出。跨日未知任务先核对历史状态，新取的数据按真实观测日期保存。

**完全不在后台取数与连续每天留存库存快照不能同时保证。** 首版保留这两种明确选择，不以“每日分析”为由默认开启后台工作，也不把未采日期显示为0或用今日数据补填。

## 6. 页面方案

顶级“门店缺货率分析”内建议四个页签，避免把新任务挤进补货出单步骤。页头固定显示淘汰/考核剔除视角，默认全量，切换后所有汇总和下钻同步：

| 页签 | 内容 |
| --- | --- |
| 总览与趋势 | 全量及当前视角门店缺货率、分子分母、剔除款数、标签覆盖及采集完成数；四类交叉卡片；每日趋势及门店排行 |
| 切面分析 | 选择按仓、商品类目（分类）、上游供货商、必采或门店分组；支持供货商×类目、供货商×门店、类目×门店交叉表，仅生成实际有记录组合 |
| 缺货商品 | 商品/门店明细、在途、归属、必采、月销、门店可用库存；虚拟分类原文、淘汰/考核命中依据及本视角是否剔除；已剔除商品可另行查看 |
| 采集与快照 | 当日任务、逐店状态、继续原任务、补采失败项、历史修订、分析已采用的资料版本、手动采集、默认关闭的每日计划与独立清理 |

每个率同时显示 `缺货数 / 有销基数`。门店、供应商和类目排行既能按缺货率也能按缺货款数排序，小基数直接显示，不另造一个未经业务确认的评分。

日趋势默认展示每天的比率、分子分母及覆盖门店数；缺采/待核日期断线，不能补0。部分门店日期用不同标记，默认不与完整日期混成一条无提示的趋势。

表格点击后能看到具体商品与理由，例如：

- “月销24，可用库存0：计入缺货；在途6不抵扣本指标。”
- “本次山东单仓，山东资料无该编码：归为本次地采。”
- “虚拟分类命中淘便考核：在剔除考核品视角中，本商品同时移出有销基数和缺货数。”
- “河北仓商品资料未取得：缺货总率可查看，供货分层待完成。”
- “原导出已受理，文件尚未取得：继续核对原任务，无须重新提交。”

用户修改日期或筛选后，旧结果标记待刷新；新查询取消/失败不能让旧数字挂在新标题下面。

首次进入展示“采用现有供货设置与必卖清单”和采集范围，采用仅建立分析自己的版本；之后页头常显分析资料日期及版本。首页及原补货页面只保留分析入口和必要的当前任务提示，不为显示分析数字加载数据。离开时有手动采集，提示可选择“安全暂停并离开”或“本次继续后台采集”；后者只授权该次任务，页面本身仍释放查询资源。

独立Excel建议包含“口径与覆盖”“每日趋势”“门店汇总”“四类分层”“当前切面”“商品明细（选导）”“剔除与标签待核”。各表保留分子、分母、剔除视角、剔除前后款数、标签规则版本、快照版本和来源时间，和页面同口径，不修改原签发/采购/五段漏斗导出模板。缺货明细状态筛选不改变汇总分母；淘汰/考核剔除视角则按规则同步改变分子和分母，二者不能混用。

## 7. 资料独立、按需加载与资源边界

### 7.1 资料归属与采用规则

原补货围绕当前作业取得资料，分析则每天积累全店商品历史。两边允许采用不同时间的资料，页面应分别显示“补货采用版本”和“分析采用版本”，不能用一个全局“最新资料”指针同时驱动两边。

| 对象 | 共享或独立 | 更新规则 |
| --- | --- | --- |
| 平台登录连接、企业身份、门店身份绑定 | 复用已核验的宿主能力 | 分析读取并校验身份，不复制登录态、不自行修改绑定；账号或绑定变化先停止相关采集并核对，不把不同企业/门店接到旧日快照 |
| 仓归属、必采识别等规则代码 | 共用纯规则，版本留痕 | 不复制第二套易漂移的算法；规则升级不静默重算已发布历史 |
| 门店供货设置、必卖清单 | 从原业务只读采用，分析独立保存版本 | 首次进入时可一键采用原业务已保存版本；后续在分析内点“采用补货侧新设置”才生效。首版不另造一套规则编辑器，也不反向回写原业务 |
| 聚水潭商品/库存原件，含类目、供应商、虚拟分类 | 分析独立采集或明确复制采用已有版本 | 新采集只更新分析自己的版本；补货侧更新资料不替换分析已采用版本；分析刷新也不改变补货默认仓资料 |
| 翱象每日全商品原件 | 分析拥有的快照 | 分析导出不自动进入补货待采用文件，也不替换当前补货输入 |
| 日明细、汇总、索引、缓存、导出和清理记录 | 分析独立存储及生命周期 | 只随分析任务更新；原订单删除不扫描或清理它们，分析清理不删除原订单或原业务原件 |
| 平台命令与受理台账、浏览器租约 | 共用协调基础设施 | 只记录带分析用途/拥有者的操作，不复制台账绕开原任务检测，不随分析历史清理丢掉仍需续查的命令证据 |

例如：补货正在采用上午09:00的山东仓资料，分析在下午14:00另取一份。下午资料用于分析当次结果，原补货仍使用上午资料；分析不得触发原业务重算、资料发布、文件采用或草稿保存。反向也是如此：补货之后更新资料，已发布的分析日报仍按当时冻结版本展示。

建议目录为 `<资料目录>/analysis/stockout/`，独立SQLite库存任务、日快照、明细、维度和汇总；独立保存分析设置、按哈希归档的原件、按任务隔离的暂存文件和报表。原件复制并核验后由分析拥有，不把原业务可删除路径作为唯一依据，也不使用会把原文件修改传播过来的可写硬链接。相同原件和维度版本只在分析内部去重，避免共享回收逻辑牵连旧业务。

首次采用原业务资料也只能走明确的只读接口：不触发自动建库、迁移、缺省配置写入或默认资料发布。复制期间复核来源版本/哈希，出现并发变化则放弃该候选，不采用混合版本。旧设置缺失时明示待核，不通过读取接口补写默认值。后续发现新版本的检查仅在用户进入分析或主动检查时发生，不增加后台持续监视。

每次采集开始固定分析已采用的设置版本与本次仓原件。运行中修改设置仅影响之后的新修订；原任务继续自己的冻结依据或安全暂停，不能半途中切换。界面把“查看/刷新结果”“采集分析资料”“采用补货侧新设置”分为清楚的操作，普通刷新只查现有结果。

首版不提供“分析资料自动同步到补货”的通道。原补货草稿、签发、预算、箱规、默认参数、默认资料、采购身份、收货和删除范围保持。共享台账查询按用途/拥有者过滤，原采集界面不把分析任务当成待采用补货文件，双方不能随意结束对方任务；旧无用途记录保持原解释。

### 7.2 按需加载与退出释放

主窗口只登记入口和轻量回调，不在应用启动时构造分析页面、分析仓库对象、解析器或历史查询服务。用户进入页面或已明确启用的采集任务实际开始时，才按需导入对应模块和打开分析库；不能通过首页数字、状态栏、菜单数量、启动恢复、通用维护或后台定时器间接扫描分析历史。现有定时补货管理器本轮不改，但不能直接用于新分析的启动生命周期。

| 状态 | 允许加载/运行的内容 | 必须避免的工作 |
| --- | --- | --- |
| 从未进入，且未启用计划 | 固定导航入口；最多读取一个小型启用标记 | 不建分析目录/库，不导入新分析重型依赖，不读原件/明细/仓资料，不启动分析工作进程、轮询器或浏览器请求 |
| 进入分析，仅查看 | 页面及所选日期汇总；点开切面/明细时查询当前范围 | 不自动采集、不扫描全历史原件、不一次装载全部门店全部历史 |
| 点击采集/导出/重查询 | 按需启动一个分析工作进程，传任务编号和必要版本引用 | 不向主进程传整个数据集，不把长操作放在Qt界面线程，不导入分析UI到后台进程 |
| 离开页面，当前无采集 | 关闭游标及连接、取消查询、销毁明细模型和缓存，工作进程完成清理后退出 | 不只隐藏页面却继续轮询、刷新表格或持有大对象 |
| 离开时有手动采集 | 默认请求安全暂停；用户可明确选择“本次继续后台采集” | 不因切换页面强杀提交；不把离开页面视为长期后台运行授权 |
| 每日计划已启用，尚未到时 | 轻量计划触发器读取下一次时间和少量状态 | 不开分析库等待、不预热历史索引、不启动解析进程、不加载页面 |
| 每日计划到时或明确本次后台继续 | 采集当日所需资料、必要校验、暂存和当日汇总；结束后正常退出 | 不趁机全历史重算、生成全部切面报表、扫描磁盘或预热查询缓存 |

计划启用标记、下一次时间、计划版本及必要的未完成任务引用，保存在固定结构、限制大小的小型触发文件中，和巨大分析事实库分开。应用启动只读取该小文件；标记不存在或关闭就不注册分析计时器。启用后优先用下一次到期触发，恢复休眠时复核北京时间和任务状态，不轮询全库；读取失败或文件超限时停止新触发并显示可理解的提示，不猜成启用。该文件不保存商品、历史结果或登录凭据。

采集、解析和大范围统计建议使用**按任务启动、可正常退出的独立工作进程**，释放时可回收其堆内存。主界面仅持有进度、任务编号、少量汇总和当前页数据；通信队列有界。工作进程复用宿主会话协调，通过窄接口申请平台操作，不自行启动第二套会话抢浏览器；小型宿主适配器只在任务期间运行。实际EXE入口须将后台任务参数在创建主窗口之前分流，避免启动工作进程时连带启动补货工作台。

离开分析时断开页面信号和计时器，关闭数据库读事务，丢弃过期查询回调；再次进入使用新会话标识，不能让旧结果更新已销毁页面。退出前正在提交的短事务允许正常结束，平台受理不明确时先保存命令号和未知状态，停止后续动作，后续续查原任务。主程序退出沿用安全等待，不强杀正在提交的任务；不关闭其他模块仍在使用的共享浏览器。

已经导入的少量Python代码可能留在主进程模块缓存中，不以强行卸载模块作为验收。重点验证大数据对象、数据库句柄、工作进程和后台活动被释放；未首次进入时则检查没有由新入口引入的重型模块初始化。共享依赖若原补货本来就在用，不能把它的常驻内存误算成新分析常驻量。

### 7.3 运行资源与原业务优先

新分析在运行期间仍会消耗内存、硬盘和平台导出时间，独立数据库或进程不能自动消除物理资源竞争。原补货计算、删除、资料导入、采购/收货等操作优先；分析重任务遇到原业务繁忙先排队，已运行任务在解析块、门店或明确的事务边界安全让行。原业务启动不能等整批分析完成，等待原因、已完成门店和暂停点应可见。

同一浏览器和同一平台账号资源不并行抢用，沿用现有租约和未知受理保护。分析查询、解析和导出也要服从资源协调，不能只协调浏览器却让两个大文件任务同时占满内存。首版不增加并行采集店数以换速度；分析内部大任务串行，必要的小型进度回报保持可用。

以下为首版设计值与限制，**尚未实施或实测**；实施若需调整应保留有限上限和同一口径，不能依靠跳过校验或截断商品减少负担：

| 项目 | 首版设计 |
| --- | --- |
| 重任务并发 | 最多1个分析重任务/工作进程；逐店采集解析，查询、导出与采集避免同时成为重任务 |
| 首次展示 | 最新已发布日期的汇总；趋势默认近30天；首次进入不扫全历史原件 |
| 明细与交叉表 | 默认每页200行；按筛选查询，交叉表只返回实际组合并分页；分页不改变全范围统计分母 |
| 解析与写入 | 每批最多1000行，另设字节预算；队列最多2批，避免长文本使行数上限失效；不累积全店/全月DataFrame |
| 页面结果缓存 | 按实际可控的数据体积设32MiB上限并淘汰旧项；不缓存原始工作簿，离开清空；这不是整个进程RSS保证 |
| 大范围趋势与导出 | 先按日期和维度聚合；长查询后台执行、可取消，导出流式写入；不把完整历史传到主界面 |
| 库及暂存 | 写事务仅在分析库内；原件校验/网络等待在事务外；连接的缓存和临时排序空间受预算约束 |
| 空间不足或内存压力 | 在新店/新块之前检查可用资源，不足时安全暂停并显示原因；保留已确认结果，不重复提交平台任务，不通过强杀或删历史腾空间 |

固定行数、缓存和并发上限只是控制手段，不能证明Excel解析库和SQLite的真实RSS受同样上限约束。实施阶段先测单店原件及索引的最大中间占用，再冻结分析工作进程合计内存、暂存峰值和可接受暂停延迟；需要严格内存限制时用磁盘投影/索引和进程隔离解决，不把超限当作可以不完成校验的理由。用户侧不需要配置几十个底层参数，首版默认保守，页面只展示任务状态、资料版本及空间占用。

### 7.4 数据量、保留与故障范围

每日全量数据是本功能主要新增成本。示例假设20店、每店1万条，30天就是600万条店品日原始记录，90天为1800万条；这是容量验收场景，不是已测用户规模或磁盘体积。

- 每店流式读取，分块写入自己的暂存表；完成并校验后短事务发布指针，不在原业务库持有长写锁。只保留当前任务必要的中间数据，不同时在两库保存同一整份JSON。
- 不保存完整计算结果、预算数组；仓资料、必卖清单和长文本维度按版本只存一次。全量、剔除淘汰、剔除考核、两者都剔除共用事实与标签，不复制四份日明细；常用汇总保存分子分母，其余组合按需计算。
- 原生XLSX归档与规范化事实分开；日汇总供总览、趋势使用，明细表按日期、门店、SKU和常用切面建立必要索引。增加索引要核对写入成本和占用，不预先生成所有维度的笛卡尔积。
- 原件、规范化事实、维度版本、汇总、索引、事务日志、暂存及导出分别计量。实施先用隔离样本量出每店/日增长，再估算30/90天容量和剩余可保留天数；不能直接把Excel压缩体积当成数据库体积。
- 同日相同任务/相同修订幂等，不重插事实；失败重试不重复下载已确认文件。任务完成清理自身可再生暂存，失败原件和关键日志按验收/保留规则保留，不随意擦除失败证据。
- 首版不后台自动删历史、不在启动或退出时自动全库整理。占用统计默认读取已记账大小，精确扫描仅在分析内主动执行。独立清理提供日期范围预览，说明删除原件/明细将失去哪类复算或下钻能力；仅删除分析拥有且不再被保留修订引用的内容，不扩大原订单删除范围。
- 分析库损坏、升级失败或原件缺失只让分析页面提示恢复，原补货仍可启动和使用；分析迁移/修复只在进入或已启用任务确需访问时执行，先保留恢复依据，不修改业务库。版本不匹配时暂停分析任务，不带故障反复后台重试。
- 原补货的启动恢复、默认备份/维护与删除路径不能因新增目录而隐式遍历分析全量历史。分析备份、导出和清理作为独立操作，已有业务的备份承诺和数据范围保持原定义。

### 7.5 资源验收方法

在同机、隔离目录、固定输入下，对比原版本与候选版本，分别覆盖无分析数据、30天和90天规模。未进入板块的启动与日常补货对照交替串行至少3轮；记录中位数和峰值，区分系统缓存影响。容量场景可以合成，必须标明；业务等价性保留既有真实冻结样本及既有预期，均不调用真实平台。

1. **未使用成本**：计划关闭且从未进入时，分析事实库/原件读写次数为0、分析数据库句柄为0、分析工作进程为0、分析轮询和平台请求为0；仅允许固定入口及小型启用标记开销。即使放入大历史库或损坏的分析库，原业务也不应打开它们。
2. **生命周期**：连续进入、查询、离开，核对无增长的持久连接、孤立工作进程、悬挂回调和大对象引用；离开且安全收尾后无分析活动。主进程RSS允许运行库保留部分内存，需结合对象/句柄及进程树数据说明，不只用一次RSS下降证明释放。
3. **运行成本**：测整应用进程树与新增分析工作进程的内存分别值，记录CPU、进程读写、临时文件峰值、库增长、页面响应、暂停与退出等待时间。浏览器作为共享进程单独标明；进程I/O不能表述为物理磁盘占用率。
4. **旧业务不受污染**：按第9节对原资料、默认配置、作业和订单做前后业务签名对照；同时验证计算、删除、导入等使用时分析会排队或安全暂停。计划关闭时，原业务耗时不应随分析历史规模增长；发生退化必须定位，不能用“独立进程”代替证据。
5. **资源不足及隔离失败**：模拟低可用内存、磁盘不足、分析库占用/损坏、子进程异常和跨日恢复；原业务仍可使用，分析不给出半份正式结果、不丢掉未知平台任务。没有在低配置业务电脑实测前，不声称已证明该电脑的性能。

## 8. 实现边界建议

以下均为待实施设计，不是本轮新增运行模块：

| 位置 | 职责 |
| --- | --- |
| `stockout_entry.py` | 无重型依赖的入口登记、按需页面工厂、会话标识及离开清理；不在导入时创建分析库或读取资料 |
| `stockout_trigger.py` | 默认关闭的计划标记、下一次到期触发；计划开启才驻留，不通过轮询分析库判断是否该运行 |
| `stockout_worker.py` | 按需启动的采集/解析/统计/导出工作进程，有界通信与安全退出；通过宿主适配使用共享会话，后台入口不创建主窗口 |
| `stockout_repository.py` | 独立分析库、任务意图、快照修订、日汇总、原件引用和短事务发布 |
| `stockout_acquisition.py` | 手动/已启用的每日采集编排、共享连接租约、原任务续查、补失败项；冻结分析采用设置，不计算补货、不发布默认资料 |
| `stockout_facts.py` | 原表字段投影、统计资格、异常及冻结的归属/必采/类目/供货商；虚拟分类、淘汰/考核命中与标签依据状态 |
| `stockout_metrics.py` | 门店缺货分子分母、四种剔除视角、双标去重、互斥分组、筛选、趋势和覆盖计算，不依赖Qt、不操作平台 |
| `stockout_ui.py`、`stockout_exports.py` | 独立页面和Excel，使用同一结果服务 |
| 主窗口与任务协调 | 只接轻量入口及任务期间的窄接口；按原业务忙闲安全让行，不把分析完成回调接入补货资料采用或工作区 |
| 共享采集组件 | 增加独立用途和任务拥有者；保持旧协议字段解释、回执、原生范围、锁和完整性校验 |

必须直接复用或通过薄适配复用既有纯归属规则，避免维护一套易漂移的“分析专用主从仓算法”。若为了低内存投影必须提取公共纯函数，先证明原补货全字段输出等价；不能借此修改归属规则。

新分析计算缺货率不运行 `engine.run_calculation` 或预算分配。不能用 `orderable()`、签发导出过滤、货值缺价规则去决定缺货基数。

快照至少记录：统计口径版本、应用/归属版本、计划及门店范围、供货路线版本、必卖清单版本、仓资料哈希、原件任务及文件哈希、日期/采集时间、原始行号、规范化M/K、来源与必采/类目/供货商分组、虚拟分类原文、淘汰/考核三态标记及规则版本、标签来源仓和依据状态、异常和修订状态。查询、缓存及导出标识包含剔除视角；切换视角不改原事实。历史默认按当时规则查询，不用最新资料补旧值；将来若重述历史须产生明确的新修订。

分析内部数据库可以有自己的版本及迁移，原业务的参数、作业和存储格式保持。模块依赖方向是“入口按需调用分析，分析通过窄接口读共享能力”，不让核心补货服务反向依赖分析库。以只读资料适配器、独立写入路径及验收拦截共同保证隔离；不能只依靠界面上不显示“同步”按钮。

## 9. 验收条件

| 验收场景 | 必须满足 |
| --- | --- |
| 有销缺货/有销有货/无销零库存/有在途缺货 | 与第3节公式逐行一致，分子始终是分母子集 |
| 0基数、负库存、缺月销、缺库存、非法编码、重复记录 | 不猜0、不扩行、不发布假完整率，定位到具体门店/商品/字段 |
| 缺价格/箱规/供应商/类目 | 有效基础缺货率不被无关字段阻挡；维度待核可追溯 |
| 禁用、停采、拒收且有月销 | 进入总基数，状态切面可定位，不沿用下单资格过滤 |
| 标杆淘汰系列、淘便考核及双重命中 | 四种视角分别正确，剔除同时影响分子分母，双标只减一次 |
| 待淘汰、不淘汰、厂家下架、其他非精确标签 | 不因模糊包含字词误剔除，考核品不误计为淘汰品 |
| 虚拟分类空值/缺列、地采无条目、两仓标签不同 | 空值与未取得区别明确；不借另一仓标签，不把未知当正常，剔除结果显示识别覆盖 |
| 100有销20缺货、剔除10有销4缺货 | 调整后16/90≈17.78%；全部剔除显示无基数，率可上升也可下降 |
| 商品类目、仓库供货商、组合剔除 | 每个切面仍用门店月销/库存计算；页面、排行、趋势、明细和Excel一致 |
| 单仓与双仓 | 和0.46.5归属一致；本仓无而另仓有的单仓商品归本次地采 |
| 必采×来源四类及待核 | 分子、分母完整对账，无双重计数；地采必采可单独查看 |
| 多店/多日/同商品多门店 | 比率按分子分母汇总；不重复两仓，不平均百分比 |
| 只看缺货、组合筛选、下钻、导出 | 分母不被缺货明细筛选缩没，页面与Excel及快照完全一致 |
| 全部商品完整性 | 范围、门店身份、原生任务、有效行数、键及文件哈希一致，零行未知契约不当成功 |
| 失败/中断/重启/重复点击 | 续查原任务，成功数据不重复，未知受理不重新提交；安全停止后可继续 |
| 部分门店、晚采、跨天漏采 | 覆盖清楚，晚采时间真实，不拿今日库存补昨天 |
| 同日重采、资料变更、配置变化 | 冻结原依据，新修订明确，读取期间不混合两版；历史不被当前设置改写 |
| 两边资料分别更新 | 分析刷新不改补货默认资料及当前作业；补货更新不替换分析已采用版本；主动采用新设置有版本记录，旧日报不变 |
| 复制采用与并发修改 | 只读取得稳定原件/配置，变化则放弃候选；分析保有独立原件，原业务后续清理不使分析依据失效 |
| 冷启动及长期未进入 | 计划关闭时，分析库/原件访问、工作进程、轮询及平台请求均为0；大历史库或坏库不影响原补货启动 |
| 进入、分页查询、离开后重复进入 | 按需初始化；离开释放大对象、连接和任务资源，无悬挂回调；当前页分页不改全范围缺货分母 |
| 默认计划关闭、启用、停用及本次后台继续 | 仅明确启用才后台触发；到时加载必要采集能力，结束退出；停用计划和暂停当前任务语义清楚，无隐式重启或跨日重复提交 |
| 采集/事务中离开或退出应用 | 安全边界收尾，保存平台受理证据；不强杀、不关闭其他模块会话，UI销毁后不再回调旧页面 |
| 与补货/采购/资料同步同时使用 | 原业务先行或安全交接，无抢浏览器、重复导出、原任务误结束、当前草稿替换 |
| 对原业务保护 | 隔离验收中原作业、订单、参数、默认仓资料及旧报表业务签名前后相同；共享台账仅新增本分析用途记录 |
| 30/90天容量、内存或磁盘不足、分析库损坏 | 不整库载入内存，遵守分页/队列/缓存上限；明确安全暂停，原补货仍可使用；记录整进程树峰值与新增工作进程峰值 |
| 清理与取消导出 | 只影响所选分析范围，无残缺正式报表；不扩大原订单删除范围 |
| 实际EXE及规模 | 从固定提交独立打包，测上述原生交互、低资源策略和完整回归，保留失败证据与限制 |

本轮没有运行新功能测试或性能测试；上述为后续完成门槛。

## 10. 阶段与工作量

这是独立每日数据链和分析页，工作量高于在现有漏斗上加两个切面。按当前连接可复用、原生表头保持、单层类目和仓内供货商名称口径估算，原含淘汰/考核视角方案约6.5～10人天；本次补充的按需生命周期、独立设置采用、可退出工作进程和容量隔离验证，约增加1.5～2.5人天，首版合计约 **8～12.5人天**，包含实现、验证和独立打包。这是估算，不是交付日期承诺；类目和供货商已在原首版范围，不重复计入新增工作。

| 阶段 | 交付 | 估算 |
| --- | --- | ---: |
| 1. 原件与口径 | 冻结字段契约、全部商品覆盖、类目/供应商、关键异常样本 | 0.5～1人天 |
| 2. 独立每日链与生命周期 | 独立资料采用、分析库、按需工作进程、默认关闭的每日触发、原任务恢复、资源让行和原子发布 | 2.5～4人天 |
| 3. 统计与切面 | 门店缺货率、四种淘汰/考核视角及校验、必采/来源、仓/类目/供货商、历史与质量覆盖 | 1.5～2.5人天 |
| 4. 页面与Excel | 按需进入/离开、总览、趋势、下钻、任务状态和独立报表 | 1.5～2人天 |
| 5. 回归与交付 | 两边资料隔离、冷启动/释放验证、30/90天规模、故障恢复、实际EXE、独立包 | 2～3人天 |
| 合计 | 首版完整范围 | **8～12.5人天** |

建议分三个可核对的里程碑：先完成独立资料、按需入口和手动采一天，验证退出释放及旧业务不变；再完成默认关闭的每日采集、原任务恢复和资源让行；最后完成跨日趋势、30/90天容量及实际EXE验收。每一步沿用同一数据边界，不先做成常驻功能再补隔离。手动里程碑不冒充完整每日版本，尚未完成容量验收也不宣称适合低配置电脑。

后续可选：连续观测缺货天数、月销量权重视角、明确规则的提醒、可靠的地区/负责人/多级类目维度、AI只读查询、服务器无人值守。首版不做损失销售额估计、责任自动归因、自动采购、历史库存回填，也不顺带实现原五段漏斗的待办方案。

## 11. 本方案采用的默认设计

- 默认按需进入，进入只查看、不自动采集；每日计划默认关闭，明确启用后一天一次、建议08:00、北京时间，按所选门店取全部商品。
- 主口径为商品款数比例，不按销量、金额或建议订货量加权。
- 全部指标明确命名为门店缺货率，缺货判断来自翱象门店可用库存；仓和上游供货商仅作为切面。
- 默认全量，支持分别剔除淘汰、考核或两者。按已确认的“虚拟分类”精确标签识别，同步调整分子分母；缺标签证据保留并明确识别覆盖。
- 首次可只读采用原业务已保存的供货设置及必卖清单，分析独立持有版本；之后主动采用更新，两边互不自动替换。分析采集的仓资料仅用于分析。
- 本次地采沿用0.46.5单仓规则；必采对中心仓和地采都保留独立属性。
- 类目使用原商品资料“分类”，首版一层；仓库上游供货商按仓内原名称，支持与门店/类目交叉，缺字段明确展示，地采不套用大仓供应商。
- 计划关闭且未进入时，仅保留轻量入口和启用标记检查，不开分析库、不读历史、不启动分析进程。离开安全收尾并释放；本次后台继续须明确选择。
- 本机应用内定时，仅启用后保留轻量触发器；到时执行后退出，关机/休眠不能保证执行，不新建服务器或系统服务。未采日期不能事后补回当时库存。
- 逐店采集、最多1个分析重任务，明细分页、队列/缓存有界，原业务优先；不自动删历史或在启动时整理分析库。设计上限与实测峰值分开记录。
- 数据质量问题只阻挡受影响的指标/范围，未知不伪装为0；不因无关价格字段让基础率失能。
- 后续开发使用独立分支、隔离数据库与新QA目录，旧包保留，固定提交构建；未经要求不推送、不合并。

若业务希望改变以上口径，先调整本方案再实施。本轮仅交付方案，没有开启新功能或每日自动采集。
