已有分仓执行表的订单，复用`warehouse_execution`及`purchases.validate_head`的仓单校验。尚未分仓管理的旧订单，沿用原有父单校验；不为了读取而自动改造真实库。仓单删除、同号重建、原摘要变化、付款版本变化仍需被识别。

本轮检查这套身份在采购提交、收货资格、监听恢复和对比导出中的消费点，只修改已经确认的错误用法，避免扩大到计算或其他单据流程。

**三、P1 采购上传的最终依据核验**

现有问题是主程序派发前已核验，但浏览器连接和页面准备可能等待较久；组件之后的检查没有核对当前付款版本。修复不能仅在`upload()`开头再读一次，也不能在等待登录期间一直占用数据库写锁。

采用“完整业务核验生成依据凭据，最终导入请求前自动校验并一次性登记提交”的方式：

1. 主程序继续调用现有完整付款、签发、配置、准入和文件校验，并生成仅属于本仓本次采购的依据凭据。凭据包含订单身份、本仓源修订及摘要、可见性和数据代次、付款版本及摘要、付款依赖的回传和运营版本、流程分支，以及现有核验实际使用的准入和配置依据。冻结文件SHA与请求内容摘要一并关联。无关订单的变化不得使凭据失效。
2. 浏览器连接、登录、原采购查询、导入窗口准备和文件读取均在提交边界之前完成。等待时不持有主库写事务。现有组件预检查继续承担尽早报错，不能代替最后一次核验。
3. 原生导入请求到达`NativeImportGuard`时，先暂停该请求放行。验证本次请求类型、目标和文件字节，再对主库执行短事务：以该仓身份复查凭据覆盖的当前事实，条件成立才写入一次性的提交登记；校验与登记同一事务完成。组件只按明确契约核对版本事实，不另写一套数量和健康计算。凭据缺项或旧包需要补齐时，返回主程序按原校验生成新凭据，不静默降级为仅检查订单存在。
4. 登记提交事务完成的时刻定义为提交起点。在此之前已经提交的付款更改必须被看到；付款保存与提交登记由同一主库的写事务确定先后。在此之后发生的更改属于提交后的业务变更，允许保存，保留原在途采购的冻结数量，并提示依据变化。不能声称网络在途的旧请求自动变成新数量。
5. 主库短事务提交并关闭后才放行网络请求；不在数据库事务内等待浏览器、HTTP响应或平台导入完成。提交凭据只消费一次，过期或重复命令不自动放行。

组件的`SUBMITTING/uploadAttempted`不得在浏览器连接前设置。最终请求被自动核验并登记后，先持久保存组件进入提交边界的事实，再放行；组件保存失败就中止请求并保留技术登记供恢复。已知被拦在放行前的记录与放行后无回执的记录分别处理。

主库事务只保证本仓签发、付款和库内依赖的先后关系。浏览器身份、配置和外部文件继续使用现有配置占用保护、版本与摘要检查；上传字节使用已校验的内存副本。不宣称一个SQLite事务可以同时原子保护浏览器、配置文件及平台请求。

主库可新增一张仅保存采购ID、仓单身份、依据摘要、文件/请求摘要、提交状态与时间的技术登记表，由主程序正常升级路径创建；不保存第二套商品数量。组件沿用现有采购账本与回执。两库不是一次原子提交，恢复时按技术登记与原受理回执对账，不能假定跨库崩溃原子性。

| 最终结果 | 本地处理与下一步 |
| --- | --- |
| 校验不通过，导入请求尚未放行 | 中止本次请求，保存“提交前依据变化”的明确原因；允许在原入口重新生成预览，不要求确认付款以外的额外审批 |
| 有明确、持久的未放行证明 | 归类为未提交；允许安全结束旧准备并重建本单，不污染批次其他成员 |
| 请求已进入提交边界但没有唯一回执 | 保留结果待核，沿用已有核对/明确结束重建入口，不凭超时自动重传 |
| 已取得唯一受理回执 | 只查询原任务和采购单，保留原文件及数量；不再次上传 |
| 提交后付款或上游发生变化 | 原采购事实与当前付款分别保留，提示具体差异；按原有下游更正规则处理，不自动绑定到新版本 |

必须保留一种可核实的“未发出请求”证明，不能仅凭错误码把`uploadAttempted`改回假。技术登记孤立、组件崩溃和取消都要进入上述已定义结果，不形成永久占用且无恢复入口的新状态。

历史已受理任务无需补造提交凭据即可沿原任务查询；旧预览尚未上传的，在完整重核验后补齐凭据。保持现有逐单提交顺序、平台处理中任务可重叠、无本地待处理数量上限的行为。

**四、P1 收货监听与误退役恢复**

`aoxiang_receipt_scope.assess`按本仓有效执行身份读取源修订、签发摘要和付款记录。父单进入修订2、河北仓仍合法固定在源修订1时，河北仓应通过；河北仓自身变化时仍拒绝旧关联。继续检查原`oid`、删除/可见性令牌、付款版本和摘要，不按同号新单或同名门店接管旧采购。

自动监听、人工单单同步、批量同步、队列派发和正式实收保存采用相同资格口径。临时读库失败只报告本次无法核验，不把未知写成永久退役。

修复同时覆盖已经被错误设置的`retired=True`、`enabled=False`及队列跳过状态。恢复放在现有“配置收货同步/启用”和“继续原单”入口中，避免让业务手工处理SQLite：

- 先展示并重核验所选采购的原平台单号和本地依据；能验证仍有效，才清除误退役标记。
- 启用监听由用户在原入口明确执行。修复安装后不自动启用所有历史计划；原本主动停用的计划保持停用。
- 已跳过的本地同步项，可以针对所选有效订单建立继续任务，仍指向原采购ID和平台单号。已完成成员、同店另一仓及其他订单保持。
- 真删除、已作废、付款已变化、缺少可复核旧身份或已经实收完成的记录，保留对应原因和既有处理入口；不能靠清标记恢复。
- 重复恢复不重复采购、不重复形成实收版本。批量中不合格项逐项说明，合格项的范围由用户明确选择。

恢复前留存所选技术状态，记录操作后的结果；不从退役后的`enabled=False`反推用户原本是否想启用，也不重放已跳过的外部写入。

**五、P2 生命周期对比导出**

保留`purchases.validate_head`和不可变签发快照核验，移除其后重复要求`仓单revision == normal_orders.current`的判断。按正确仓单读取原签发依据，缓存键包含实际快照身份；不能把另一仓或另一修订的快照拿来复用。

覆盖订单级、门店级、仅勾选和全部筛选导出。某个选择确实失效时，列出具体仓单和原因，由用户刷新或调整选择；不静默导出有效子集。模板、字段顺序、金额口径、缺失值和批量排序保持原样。

**六、独立看板CSV的保存与升级**

按“观测日期＋供货仓＋商品编码”合并记录。新增和更正都进入持久覆盖集；重开时先加载内置基线，再用保存记录覆盖同键旧值。保留仅保存增量覆盖集的方式，避免把整份内置大数据反复写入浏览器存储。

导入先在候选数据中完成解析和合并，再保存覆盖集并读回核对，成功后才切换页面数据和显示“导入完成”。存储不可用、容量不足、读回不一致或旧记录无法解析时，保持上次成功数据，保留失败原因，不能将错误提示覆盖成成功。原字段和统计规则保持，本轮不增加猜仓或商品匹配规则。

兼容原存储键和数组格式，治理行动记录保持原身份。完整备份应包含库存更正覆盖集和治理行动；原有仅导出治理行动的功能不能充当库存备份。升级优先沿用原访问路径，原HTML另存备份；更换文件路径或浏览器时采用明确的完整备份/恢复，不承诺不同浏览器存储会自动共享。

交付修复版独立HTML并保留原件。已经关闭页面、且从未持久保存的更正不凭空恢复，需要重新导入对应更正CSV。缺货率、品类、供应商、持续缺货及治理前后对比都从同一份最终记录重算。

**七、P2 采购轻量读取**

`_comparison=False`时，在进入逐商品差额、展示名称、阶段文案、备注拼接之前走轻量分支，连只供这些展示使用的映射和集合一起避免构建。保留原件解码及摘要校验、旧回传完整性、付款完整事实、路由和依赖健康判断，保持当前返回字段与类型。

普通完整快照继续输出原有展示行。不能通过减少付款行、跳过上游健康判断或更改`Decimal`处理换取速度。本轮已确认1000 SKU轻量路径返回0展示行仍执行展示计算；提速和内存收益以后续冻结旧版/新版对照实测为准。

**八、验收与实施顺序**

先把现有离线复现固化为回归用例，再统一仓单身份校验；随后完成采购最终提交、收货误退役恢复及对比导出，单独完成HTML保存，最后优化轻量读取。两项P1和已有错误状态的恢复必须一起验收，不先交付只改判断条件的版本。

| 验收组 | 必须覆盖的场景与判定 |
| --- | --- |
| 付款竞态 | 数量7在连接、页面准备、原生请求放行前三个同步点改为2，旧文件均不得提交；不要依赖随机延时碰运气 |
| 提交先后 | 付款先提交则旧凭据拒绝；提交登记先完成则原请求保持冻结版本，后续付款可保存且差异明确；不长时间持有数据库写锁 |
| 非数量变更 | 付款摘要变化、回传/运营变化、签发变化、删除、准入及配置变化分别按原规则处理；新增无关原件但业务版本不变时不误拦截 |
| 单单与并发 | 只拒绝本单，其他独立订单按原顺序继续；已受理任务可重叠，不降低默认并发或恢复本地数量上限 |
| 上传失败恢复 | 校验拒绝、取消、登记后崩溃、请求结果未知、回执晚到、重启均有明确归类；凭据不重复消费，原任务不自动重传 |
| 分仓身份 | 山东单独重签不影响河北，反向相同；本仓真正更新仍拦旧单；覆盖旧库分支、同号重建、回收站令牌变化 |
| 监听恢复 | 单个和批量误退役可重核验恢复；主动停用不自动启用；完成、作废、真删除及失效付款不能被恢复；恢复后仍使用原平台单号 |
| 对比导出 | 单选、批量、筛选全部和门店汇总均可使用有效仓单；真正失效选择明确拒绝；字段、数量、金额及排序与原结果一致 |
| CSV持久化 | 内置日期更正、新增日期后二次更正、同键重复导入、重开、更正为0/负库存、容量不足、存储不可用、完整备份恢复 |
| 轻量等价 | 新旧付款事实、健康状态、下一步和原业务数据完全一致；完整快照的展示行也保持一致 |
| 性能与内存 | 使用新建合成数据，至少1千/5千/1万SKU，三轮交替运行旧冻结源码与新版；报告真实工作进程峰值内存、耗时及输出摘要，不预设加速比例 |
| 实际界面 | 实际打包EXE验证准备、拒绝、继续原任务、误退役恢复、导出、关闭和重开；独立HTML在隔离浏览器存储中实际导入并重开，不能只用JS模拟代替 |

真实平台调用、真实采购上传、批量恢复业务机监听、覆盖现用软件和真实资料迁移均不在实施验收范围。使用新建合成数据库、原生样式的合成模板、离线上传适配器和隔离浏览器；保留错误弹窗和真实保存路径，不能全替换成空函数后声称通过。
