# 补货助手0.52.5性能核查、修改与验收方案

日期：2026-11-13。阶段：核查、隔离诊断测量、算法原型和实施评估。**本轮未修改业务代码、版本或交付包，未操作真实业务数据、提交、推送或合并。**

## 1. 结论与建议顺序

有明确优化空间，第一轮建议集中做三件事：

1. 复用签发预览中同一份差异比较，完整差异JSON按需生成。
2. 生命周期与经营分析的SKU有序查重增加seen集合。
3. 历史及跟踪查询先按有效范围收敛，再读取必要资料；先完成不改变派生索引格式的小步改动。

随后优化签发Excel的样式处理，再评估完整快照解析、派生查询缓存和大历史删除。每个候选单独验证，避免一次改动过多而无法定位回归。

目前不能确认上一轮业务电脑空异常就是内存不足或死锁；本方案也不把0.52.5的诊断补齐当成现场根因已解决。

## 3. 本轮证据及其限度

### 3.1 实际签发预览的重复比较是第一优先

受控合成输入：11店×1000行，复制一份独立已签发合成库，将本次数量由24改为48，通过实际Session运行prepare_normal，不提交新订单。

| 指标 | 诊断结果 | 解释 |
| --- | ---: | --- |
| 父进程调用 | 约16.00秒 | 包含等待子进程，不能当CPU时间 |
| 子进程处理 | 约15.31秒 | 带cProfile及QA插桩 |
| revision_diff | 22次，累计约12.06秒 | 约占该子进程诊断时间78.7% |
| wr.dumps | 3,674,749次，累计约10.50秒 | 与上行嵌套，不能相加 |
| 返回界面 | 200行预览／总差异66,000行 | 返回少不代表准备阶段只处理少量 |
| 最大worker／owned tree RSS | 约209.4／372.2MiB | 外部采样，不是整机内存 |

源码位置：work_io_process.py:78、81，同一old/new先在order_review.build里调用revision_diff，随后构造details时再调用一次。work_io_process.py:84提前生成整批漂亮格式JSON；delivery_probe同样提前生成review_text。用户不导出完整JSON时，这份完整字符串也会留在会话中。

这不是业务原单复现。cProfile有开销，上述秒数用于确定热点，不是无插桩基线；不能据此承诺正式全链节省12秒或提速一倍。首次签发无旧明细、完全未变重导、少量改动与整批改量的收益会不同。

### 3.2 保存、读回与IPC仍有内存压力，当前不能只归咎于IPC

同一11店×1000行合成资料，带诊断的单次测量：

| 入口／阶段 | 观测 |
| --- | --- |
| 直接headers-only签发 | 约2.81秒，操作阶段worker峰约135.9MiB |
| 首签发导出 | prepare约0.96秒、execute约22.88秒，操作峰约156.4MiB |
| 全作业保存／完整读回 | 约0.43／0.56秒，读回操作峰约278.8MiB |
| 实际Session | prepare_save约1.31秒、save约0.024秒、fullread约0.967秒、copyconfig约0.0035秒 |
| Session内存 | 最大worker约242.6MiB，进程树约380.1MiB |

Session与直接API、预览与确认、工作进程与进程树的统计范围不同，不可混算成一个前后性能对照。当前传输已使用小帧、按所有权consume释放；snapshot已排除loaded.intake.frozen。不能把这些已有优化重新列为本轮成果。

storage_chunks.load仍重建完整JSON字节缓冲后解析；normal_orders.fingerprint_owned还生成完整JSON文本再编码。完整日草稿、校验缓冲和解析对象可能同时存在，是下一阶段内存优化候选，但不能通过少读数据或跳过校验解决。

### 3.3 导出热点主要在样式，部分重复工作收益较小

11店×1000行首次导出诊断中：

- styleable.__set__累计约7.19秒、serialisable.__hash__自身约3.62秒，值得拆分测量和验证样式复用。
- groups调用40次，累计约1.123秒；partitions调用20次，约0.563秒。两者嵌套，不能相加。
- explanation调用11,000次，约0.095秒、约0.42%，不列为主要收益。
- receipt.save约85次、累计约0.546秒；它承担恢复证据，不能为省小量时间直接批量延后。
- QA文件取消器、进度日志产生的nt.stat/open成本已单列，不能当成生产磁盘瓶颈。

上一轮0.52.5的无cProfile单轮对照仍仅作背景：11店×1000行首导出操作峰208.1→154.7MiB，约9.709→9.471秒；不表示稳定提速。本轮未重新测出一个“新版”全链性能提升。

### 3.5 查询与删除的结构性问题尚需对应大样本测量

- 历史Index.get(detail=False)仍读取、拼接并校验完整商品projection；冷列表为只取源SHA读取整份catalogs、格式化全商品。
- 历史／跟踪存在先构造范围外资料再分页、全库版本或活动生成单读取；部分每仓查询重复扫描版本集合。
- 经营分析日期范围payload先fetchall，全部事实长驻；导出再构造完整二维明细list。
- 门店缺货率每页请求会重复卡片／趋势／切面工作，大仓深页islice会从头跳过。高基数GROUP BY也有自身成本，换OFFSET或游标不一定解决聚合。
- 删除snapshot中的evidence摘要及linked集合有计算后未使用迹象，相关历史版本被重复解析；但这些动作可能同时触发数据合法性校验，不能未经证明直接删除。

以上为当前源码确认的工作形态，不是0.52.5新测出的耗时或百分比收益。历史版本的37秒删除结果不能当成本版当前基线；独立0.49.4删除性能分支也不能直接套入或整体合并。

人日为熟悉该项目的一位开发者估计，非排期承诺，不含取得业务机资料和长时间现场验收。建议第一轮只做A1、A2和A3中不改缓存结构的部分，约2–3人日实现＋2–3人日验证；B/C按实测收益再选，不一次全部上线。

### A1需要具体保留的行为

完整差异仍必须能导出全部明细，预览截断不能截断证据。旧修订、完整草稿覆盖范围、参数/来源变化、200行预览和总条数保持。按需JSON绑定同一个冻结会话，不能在用户点击导出后改用最新结果；下一次准备必须使旧差异状态失效。

### A3与B3不能混为一次简单SQL改动

日期、门店纯头筛选可以前移；商品关键词搜索仍需真正的商品搜索资料。总卡片、下拉候选、当前页、全部匹配、固定范围和跨页勾选各自保留原口径。不能仅对当前页计总数，也不能因分页把同店两仓或其他生命周期版本漏掉。

缓存内容要分别校验，不能为薄读取而取消旧projection校验；派生缓存换版时保留失败证据、允许重建，主库记录始终是授权导出和删除的依据。

## 5. 必须保持的边界

1. 不改模型、销量/库存/在途口径、断货保底、必卖最低持有、日配/禁采/禁用排除、预算、箱规、仓归属、默认参数和生命周期规则。
2. 保留缺失、异常和未知状态；不能把未读、未采或待核变成0。SKU只按既有精确编码规则，不引入辅助码/条码推断归属。
3. 业务值、类型、原有顺序、单号关系、原修订、Excel样式/批注/隐藏关联页与用户修改文件保护不变。
4. 不跳完整性校验，不放宽并发CAS、删除失效屏障、防重复提交及平台受理未知保护，不改变事务原子性、回收时机或secure_delete。
5. 不等待平台才能完成本地性能测试；不在真实平台重复导出/采购。增加并发会增加CPU、进程树RSS、磁盘与浏览器冲突，不能当通用优化开关。
6. 缺货率与补货资料保持独立。未进入缺货率时不加载分析事实/原件/重型业务库，少量明确启用的计划metadata除外；离开页面按既有规则暂停和释放。不能为“热启动”常驻预热所有模块。
7. 原C盘资料、D盘失败搬迁副本、待迁入目录、旧版本、QA原始/失败证据均不清理；不为测试初始化真实库或清锁。
8. 涉及主库存储格式、批次提交、延迟回收、历史保留或平台写操作的改变，先另列方案及影响，不纳入本轮实施包。派生缓存格式也要明确换版与回退，不与主库改格式混称。
9. 不直接运行含超时kill的旧基准驱动来测试提交。只允许协作取消；提交中等待明确结果，不杀不明进程、其他会话或浏览器。

## 6. 测试与验收方案

### 6.1 正确性先于性能

对0.52.5冻结基线与候选使用相同隔离库/输入。先比较完整已保存业务树及类型、有序业务摘要、SKU/仓/数量/价格顺序、逐表业务签名和单号关联；不能只对合计金额或行数。允许差异仅限事先列出的非业务时钟/构建标识，不能事后扩大白名单。

签发Excel逐sheet/行/列核对值、类型、样式、字体主题、数字格式、批注、属性和隐藏系统关联页。独立首签发的随机身份要用固定合成身份或明确映射核对关系；不能因UUID不同省掉关联验证。

### 6.3 性能测量方法

- 先冻结候选源码、环境、依赖、输入、库和EXE哈希。基线/候选串行交替AB/BA/AB各3轮，新进程；冷/热缓存分别测，性能窗口不同时构建、跑回归或其他重测量。
- 分阶段记录：导入、准备、计算、签发预览、事务等待/提交、快照校验/读回、Excel写值/样式/压缩/验证、查询至UI可交互、删除准备/提交/回收。
- 同时记录worker RSS、整个应用进程树RSS、GUI最长无响应间隔、进程CPU/读写字节、SQLite调用数、块读取/解压次数、缓存/临时文件峰值。Windows进程I/O不等于物理磁盘利用率；采样峰值不等于瞬时绝对峰值。
