# 补货助手订单迁移提速执行技术方案

一期针对现有「合并导入」和「完整替换」减少重复读取和磁盘写入。先完成逐单等价及中断恢复，再用固定迁移包对比新旧 Windows EXE。按日或所选订单导出属于二期，单独交付和验收。

## 基线和目标

| 项目 | 执行依据 |
| --- | --- |
| 源码基线 | `codex/order-migration-progress-05416` 的 `4034aa936f23c2f369d904fbf80ebbe72ea5ee72`，对应 `0.54.16 rc36`。开工时核对实际交付与源码标识，并保留该基线及工作区已有改动。 |
| 历史耗时 | `补货助手_轻量性能日志_20261123_211055_238448.zip` 中两次完整替换预检为 1,089.860 和 1,417.609 秒。日志归入读取解码的时间为 959.049 和 1,308.052 秒，约占 88% 和 92%。这组数字只覆盖完整替换预检。 |
| 性能目标 | 大包预检中位耗时降低约 30% 为试验目标。用同机、同包、同目标库的对照结果评估。导出与确认写入按各自的实测耗时评估。 |
| 业务契约 | 沿用存储格式 2、完整迁移包格式 `replenishment-orders/1` 和现有订单身份、付款采购事实及删除屏障。合并按原规则新增完整关联组，完全重复跳过，冲突保留本机。完整替换保留本机连接和独立资料，迁入任务按原规则暂停。 |

## 现行入口和提交边界

入口在「订单跟踪 → 完整订单迁移／导入与参数导出」。`order_migration_ui` 调用 `order_migration.prepare`，合并方向经 `order_merge_migration.prepare` 附加冲突预览。确认后先启动独立进度窗口并完成就绪握手。主窗口安全退出后，由 `application_exit.finish` 调用 `order_migration.apply`。

准备阶段只读源包和本机业务资料，写入本次隔离暂存目录。确认阶段用计划中留存的文件清单复核暂存文件的实际内容，结合源包摘要和本机相关记录核对预览依据。取得现有排他锁后在独立目录写入。发布仍按原迁移日志切换目录并保留完整旧库。用匹配本次 `nonce` 的正式目录回执判定已经迁入，启动恢复沿用 `order_migration.recover`。

## 一期实施顺序

### 1. 固定样本并量清阶段耗时

- 固定一个小包和一个可复现慢速的大包，以及各自用于完整替换与合并的目标库副本。记录源包 SHA-256、目标基线、订单数、修订数、商品行数、内容块数、原件数及大小。合并样本包含可新增、完全重复、冲突和同店双仓关联。全重复另设用例。
- 复用 `io_stages` 或现有诊断记录，用单调时钟标记解包验文件、SQLite 完整性、快照校验及业务摘要、合并比对、等安全退出和锁、复制、写入、最终校验、切换。导出记录冻结副本、收集原件、压缩和成包校验。移交后的计时写到资料根目录旁，跨主界面退出仍可查。记录读写次数、字节数和内存峰值，诊断只需计数和操作身份。
- 两个实际 EXE 都用相同边界量端到端时间。预检从选定包开始，到预览可操作为止。确认移交从点确认，到同一作业回执终态为止。人工停留单独记时。若旧版缺内部阶段事件，用同一源码仅加计时的构建补测阶段，并标明构建身份。

### 2. 消除只为校验创建的数据库副本

涉及 `src/order_migration.py`、`src/storage_maintenance.py` 和 `src/order_merge_migration.py`。

1. 将 `storage_maintenance.backup` 的**数据库校验**提取为可接收现有 SQLite 连接的只读操作。保留 `integrity_check`、`require_current`、快照摘要和业务绑定检查。`verify_originals` 继续按原件 BLOB 分段重算 SHA-256，可在同一一致视图中执行。
2. `prepare` 解包时校验实际写入字节数及成员摘要。对已解包、身份明确的暂存数据库用只读连接开启读事务并直接校验，替换 `.verified` 的创建、校验和删除。ZIP 条目、版本、相对路径、链接和来源包变化检查按原契约执行。主库和组件库按原角色检查。
3. 活库导出及合并前的本机副本继续用 SQLite backup 获取一致提交内容。存在 WAL 或回滚日志时沿用当前安全备份与读取规则。只有可证明自包含的暂存库，或已结束写入的独立副本，才用直接校验路径。
4. 合并写入后，对独立新库直接执行原来在 `.merge-verified` 上执行的检查。保留源包暂存 `verify_stage`、写前 `expected_report` 核对和发布前校验。第一轮保持当前磁盘安全余量，同时记录实测暂存峰值。

### 3. 共用快照读取结果和合并查找索引

涉及 `src/storage_chunks.py`、`src/storage_maintenance.py` 和 `src/order_merge.py`。

1. 利用 `storage_chunks.Reader` 现有的 `read` 和 `emit`，全量遍历时累计原清单字节数和 SHA-256。对 `normal_revisions` 在本次遍历中解析 `result` 和 `new_focus`，把解析结果交给 `normal_orders.fingerprint_owned`。保留原业务摘要口径、`binding`、字段类型和顺序。其他只需核对摘要的记录沿用流式校验。按顺序处理一条记录，随后释放明细对象。
2. 只在同一数据库的一致读事务内复用核验过的块。首次读取校验库中实际内容、解压长度和哈希，每次引用再核对其声明长度。按字节限制缓存，可沿用维护读取器的 8 MiB 上限起测。缓存未命中使用原块读取。对已支持但无法走合并读取的快照布局，使用原完整校验路径。缺块、损坏和业务指纹错误沿原错误路径处理。
3. `Graph._read` 从已完整校验的原对象取出 `work_revision`，按数据库、表和记录身份暂存。后续关联校验从该记录核对工作修订，省去 `normal_revisions` 和 `warehouse_execution_revisions` 的第二次全单展开。保留原 `strings(decoded)`、仓关联和原件引用提取，覆盖历史快照内部的路径。
4. `_inspect` 为本机订单建立 `oid`、签发单号、`(day, store, kind)` 和 `(day, store)` 的内存索引。查询结果保留全部候选，使用原有摘要及迁入回执判定完整重复。删除、仓退役、平台单号冲突、共享分配／采购组和预览摘要沿用原判定。结果行顺序及原因与基线逐项比较。
5. 先量共用读取和索引的收益。如果同一次合并预检中，来源库的完整校验和 `Graph` 仍重复展开同一快照，则在同一读视图内共用完整校验结果。来源包的整包阻断条件、单订单冲突条件仍按原作用范围执行。确认写入前的复核及写入后的独立验证继续执行。

### 4. 合并进度写盘并保留恢复证据

涉及 `src/migration_status.py`、`src/order_merge_migration.py`、`src/order_migration_progress.py`。

- 当前 `_clone` 把 SQLite 复制及逐记录检查的回调一律写成 `COPYING`。改为在内存累计最新进度，运行中按单调时钟约每秒写一次状态。同一作业只在需要更新指向时写 `latest.json`，状态历史记录实际阶段切换，窗口依原 `nonce` 读它自己的状态文件。
- 数据库页数、已校验记录和已复制文件分别用实际的 `done`、`total`、单位显示。总量未知时显示阶段、已处理量和用时。阶段切换、取消、正式完成和首个失败原因即时原子写入。进程是否退出仍用当前观察原进程的机制判断。
- 沿用主窗退出前的独立窗口就绪检查、实例租约、浏览器和数据库占用检查。预览取消时保留源包、原库和已记录结果。确认后出错时通过阶段日志和回执区分原库仍有效、已回滚和已迁入但清理待处理。结果不明时先恢复或核对原回执，再决定是否重新预览。

### 5. 按实测减少导出重扫和大文件搬运

- `order_migration.export` 在冻结副本上调用校验后再用 `referenced_files` 扫描快照。让整包原件引用提取复用同一次已校验的块读取。保留原先遍历的表、嵌套字段及原件映射范围，对其余原引用走原扫描。对照两版文件清单、BLOB 和外部文件摘要及缺失提示。压缩级别根据实际压缩和跨机传输耗时评估。
- `order_migration._apply` 目前把校验后的暂存成员复制到新目录。如果实测复制占主要时间，先验证已核验、发布前无需改写的 `migration-assets` 原件能否走同盘接管。接管记录归本次计划，覆盖中断恢复、原包重开和重试。数据库及需改写的文件遵循原副本路径。跨卷和无法安全接管的文件继续走流式复制。

## 正确性验收

| 用例 | 必须查到的证据 |
| --- | --- |
| 正常整库恢复与升级 | 旧包在新 EXE 正常打开。逐仓单比较原单、全部修订、SKU 顺序和字段、数量、金额、付款、采购及实收版本。比较本机连接、参数采用规则、原件映射和文件摘要。旧库备份可打开。 |
| 合并和重复 | 同店双仓、签发单号撞号、同日同店撞键、平台单号撞号、删除标记、共享组冲突。比较预览四类行及原因、实际新增范围、迁入前后关联摘要。相同包再跑一次的新增为 0。 |
| 文件与块校验 | 比较 ZIP 改变、暂存同长度篡改、缺块、不同引用声明长度、`binding` 不符、原件损坏及读期间目标变化的结果。即使缓存已命中，也校验每个引用的独立身份和长度。 |
| WAL、长路径和占用 | 用带已提交 WAL 页的源库导出和合并。用 Windows 长路径提取、校验及迁入原件。验证正在写入的本机库和预检后重新开启专用浏览器时的现有拦截和诊断。 |
| 恢复和状态 | 覆盖预览取消、后台退出失败、首个目录换名后中断、第二次换名后应答丢失。核对备份、源包、原 `nonce` 和实际回执。重复恢复后只存在一份正式迁入结果，进度仍可观察。 |
| 业务事实 | 原线上单和内部单号、原采购号、占用记录、付款及实收版本均按原仓单关联。迁入中和重开后用测试替身统计下单及采购提交为 0。 |

先用现有回归及新增的上述差异用例验收。一项逐单差异就先根据原仓单及修订定位，再进入速度对照。数据库业务内容、原件和关联决定等价，允许 ZIP 创建时间、机器路径映射及迁入记录时间等预期元数据变化。

## 复跑命令与速度交付

在项目根目录使用仓库锁定的 Python 环境。为每次验收指定新的隔离输出路径，保留每轮原件、目标库种子、回执和日志。以下命令沿用当前构建器和 smoke 入口。

```powershell
$migrationPython = '.\.venv\Scripts\python.exe'
$env:PYTHONUTF8 = '1'
$env:PYTHONPATH = (Resolve-Path '.\src').Path
& $migrationPython -m unittest discover -s tests -v
& $migrationPython tools/build_from_commit.py --commit $migrationCandidateCommit --build-id $migrationBuildId --output-root $migrationDeliveryRoot
& $migrationPython tools/verify_migration_shutdown.py --exe $migrationCandidateExe --out $migrationShutdownEvidence
& $migrationPython tools/verify_order_merge.py --exe $migrationCandidateExe --out $migrationMergeEvidence
Get-FileHash -LiteralPath $migrationCandidateExe -Algorithm SHA256
```

`$migrationCandidateCommit` 为通过源码回归的冻结提交。`$migrationBuildId` 和 `$migrationDeliveryRoot` 使用该次新构建的实际编号和目录。将候选 ZIP 解压到空目录，`$migrationCandidateExe` 指向解压出的 EXE，并核对它的散列与构建产物相同。两个 `Evidence` 变量指定互不相同且尚未创建的隔离目录。现有 smoke 自建小样本，用于功能和故障验收。大包速度测试从实际 EXE 的工作台进入，用已冻结的迁移包及独立资料目录。

在同一台 Windows、同一磁盘交替运行新旧 EXE，完整替换、合并各做三轮配对。每一轮从相同目标库种子开始，记录应用和组件构建号、CPU、内存、存储介质、阶段用时、读写量、峰值内存、暂存峰值和逐单对账结果。按模式计算新旧阶段及总耗时的中位数，保留所有原始结果。仅在有实包对照时报告业务大包的节省时间，隔离合成包的结果按样本标注。

交付从固定提交构建的独立 EXE 和完整 ZIP，列出完整路径、构建标识及两者 SHA-256。附逐仓单等价表、每轮计时、中断回执和复跑输入位置，保留原候选包及原验收证据。

## 二期按日或所选订单导出

在一期稳定后另设导出入口。以所选订单为起点复用合并关系图，计算同店双仓、共享分配批次和采购关联的完整范围。预览显示用户选中的单、被关联带入的单及原因。确认后冻结范围及修订，生成带独立格式标识的包，携带该范围的全部签发、付款、采购、实收、原件和防重事实。

小包仅进入合并入口。旧完整恢复入口按格式识别并引导使用完整包。验收覆盖跨日共享依赖、源单签发修订变化、同一包二次导入、当地已有采购或删除事实、原件哈希及库内闭合关系。比较同一批交接订单的包大小、导出耗时和接收耗时。
