# 五段漏斗上游供应商与商品类目切面方案

日期：2026-11-07，状态更新：2026-11-11。**0.51.2已实施历史供应商/类目属性与SKU×门店×供应商×类目组合导出；页面自定义筛选、独立切面看板等其余规划仍待实施。** 用户已明确“大仓供应商”指山东仓、河北仓各商品对应的上游供货商。实际交付范围见`../0.51.2经营分析组合明细补全.md`，下文仍保留完整规划，不代表全部已交付。

核对基线：应用 0.46.3，提交 `d12bf52e99fddd1705d57a35d7aa5d91d19e8c97`；模型 `0.3.4-rules`、仓归属 `0.5.1`。本次仅编写方案及入口文档，不升级应用版本、不打包、不执行平台操作。后续实施前重新核对实际 HEAD 和工作区。

## 1. 要解决的问题

现有五段漏斗能看门店、仓库和订单，但不能直接回答：

1. 哪些上游供应商的商品从模型建议到实际下单、实际收货减少最多？减少涉及哪些门店和商品？
2. 哪些商品类目的建议被门店保留、增加或削减？差异集中在哪个环节？
3. 同一供应商下，不同类目、门店、必采属性的执行情况如何？

在既有“模型建议 → 签发 → 门店确认 → 实际下单 → 实际收货”上增加两个可以组合的维度：**大仓上游供应商、商品类目**。页面、Excel 和 AI 使用同一份分析结果。

本功能观察的是这些商品在门店补货链路中的变化，不是对上游供应商的采购履约考核。现有资料不能直接证明减量由供应商缺货、门店选择或其他原因造成；只能定位变化，再查看原业务依据。

- 山东仓：`090f8a672ffb320d7fe9f27c0c80970b3b849272b779a472aa7881473cba1ab1`。

## 4. 属性取值与历史口径

### 4.1 供应商

- 业务名称使用“大仓上游供应商”；取已签发订单所属仓当时商品原件中的“供应商名称”。
- 通过“作业修订 → 所属仓资料 → 原件 SHA-256 与工作表 → 商品编码”精确关联；同名商品、条码近似或目录中的最新文件不能代替该链路。
- 不使用补货建议 C 列的供应商编码，也不使用翱象两仓供应商配置；这些是门店与中心仓的供货关系，不能代替中心仓的上游供应商。
- 分组键为“所属仓＋原供应商名称”。名称仅去除首尾空白，保留原值供核对；不自动统一简称、全半角、括号或大小写，不按分隔符拆为多个供应商。
- 山东仓与河北仓同名供应商分别显示。同一 SKU 在两仓按各仓冻结资料分别归属。
- 没有供应商编码，无法完全排除同仓同名不同主体；页面说明这是“按资料供应商名称分组”。将来有可靠编码后再升级身份键，不静默重算旧结果。
- 这里的供应商是当时商品资料归属，不等同于某次采购入库的实际供货商。若需要实际批次供货来源，另立需求接入采购、入库批次及分摊依据。

### 4.2 商品类目与计算分类组

| 属性 | 来源和含义 | 处理方式 |
| --- | --- | --- |
| 商品类目 | 签发结果的 `_category` / `_meta.category`，必要时使用同轮所属仓冻结“分类”或归档原件 | 新增切面；保留当时原值，不借用当前映射表 |
| 计算分类组 | 现有结果行 `U`，如快销、日百 | 原筛选与模型含义保持；界面明确名称 |
| 虚拟分类 | 原商品资料中的标签及淘汰依据 | 保留现有纳入/排除规则，不当作本次商品类目 |

原商品类目的多个冻结来源均存在时须一致；冲突显示“类目待核”并给出来源，不静默选择某个值。来源只缺少字段时才使用同一历史版本的下一来源。原件校验失败属于完整性错误，不能靠另一个来源掩盖。

同一 SKU 跨仓、跨日期可以出现不同类目：每条订单商品事实按自己当时的归属分析。首期类目概览允许把两仓完全同名的类目合计，仍能按仓拆开；没有统一类目编码，不能声称完成全局分类标准化。

### 4.3 缺失、歧义与完整性错误

| 情况 | 显示及统计规则 |
| --- | --- |
| 供应商列不存在、单元格为空、原件未留存、SKU 未匹配 | 进入“供应商待核”，分别保留原因 |
| 类目各来源均缺失 | 进入“类目待核”，保留原因 |
| 原件商品编码重复、业务表头重复或来源冲突 | 对受影响属性标记“待核”；不随意选首条、不扩成多条重复累计 |
| 原件哈希、内容块或归属证据校验失败 | 阻断本次结果发布，保留具体错误，不降级成普通待核后继续使用 |
| 商品已有五段资料待核或被原规则排除 | 保持原状态；属性是否齐全不改变原纳入规则 |

**属性待核与五段业务资料待核分开。** 某商品五段数量有效但供应商缺失，仍计入原有总体，并计入“供应商待核”分组；不能因为新增维度缺失而减少原漏斗金额。

生命周期后续追加的商品，只有在原订单所属仓的同轮冻结资料中能精确定位时才赋予相应属性，否则待核；不从当前目录补齐。

### 4.4 归属跨期变化

同一 SKU 上期归供应商甲、本期归乙，按各期冻结事实分别出现。提供按 SKU 查看历史归属的明细，不据此认定发生了销售、减单或供应商履约变化。切面趋势和前后期对比须提示归属变化可能影响可比范围；首期不增加迁移贡献拆解。

## 5. 指标与合计规则

### 5.1 五段保持同一商品归属

一条事实的身份仍为“业务日期、门店、所属仓、订单、SKU”。供应商与类目各确定一次，五段共用；不得到付款或收货阶段改查最新资料，以免同一商品在不同环节换组。

对某个切面内符合原纳入条件的事实集合，复用现有算法：

| 指标 | 口径 |
| --- | --- |
| 商品款数 | 本阶段数量大于 0 的去重 SKU 数；沿用原编码口径 |
| 执行数量 | 本阶段有效数量合计；混合库存单位时明确标注，不能解释成同质物量 |
| 商品货值 | 有效数量 × 签发时 V 列价格，汇总已计价部分；缺价数量单列 |
| 相邻环节及首尾比值 | 两环节共同有效的商品集合内，后值 ÷ 前值；货值比值还要求相同商品具备签发价 |
| 增量、减量与净差额 | 在同一共同集合中逐商品计算，再分别合计；定位到实际变化的商品 |
| 实际付款金额 | 有效付款商品行的实际金额，按币种分列；不把整张付款单总额重复挂到每个供应商或类目 |
| 预计可售天数 | 复用现有制单预测、签发价加权、共同有效范围、最新业务日及跨仓去重规则 |

未取得的阶段保持空白/未取得，明确有效的 0 保持 0。分母为 0 的比值不填 0，不强行限制比值在 100% 以下。切面上的预计可售天数表示这些商品的覆盖情况，不是供应商库存周转。

天数按各组最新有效业务日期展示并标明日期；不同组日期不同须可见。天数与比值必须从分子、分母重新计算，不能求和或平均已有汇总值。

### 5.2 对账与重复计数

- 每条事实在“供应商”这一单独维度中只落入一个已知或待核分组；在“商品类目”这一维度同样只落入一个分组。
- 同一过滤范围、同一有效状态和同一计价口径下，已知分组加待核分组的已计价货值应等于该范围总体。排除、业务待核、未计价部分分别对账，不混为一列。
- 款数、订单数、门店数属于去重指标：一个商品、订单或门店可跨多个类目/供应商，不允许把分组个数直接相加冒充总体。
- “供应商汇总”“类目汇总”“供应商×类目”是同一批事实的不同视角，不能把三张表相加。
- “全部”与必采、非必采、属性待核是总计与分组关系，不重复累计。
- 不同供应商组可能因跨仓、跨期归属而共享同一需求商品，预计可售天数的分母各自在组内计算；跨组不得相加。

## 6. 页面交互

保留现有经营分析入口。基础筛选仍为日期、门店、仓库、必采属性；新增“大仓上游供应商”“商品类目”可搜索多选控件，原“分类组”明确为“计算分类组”。

筛选规则：同一控件多个选项为“或”，不同控件之间为“且”；全部包含待核，只有用户明确选已知值时才筛去待核。待核选项使用独立状态键，不能与真实名称恰好叫“待核”的供应商混淆。

筛选候选只来自当前日期、门店、订单及仓范围中的历史事实，不扫描当前供应商大全。仓范围变化后清理不适用选择并明确提示；加载候选期间保留原显示，取得完整结果后一次更新。

| 页面区域 | 设计 |
| --- | --- |
| 范围说明 | 显示日期、仓、供应商、类目、纳入商品与资料截至时间；点击即可看完整条件 |
| 原五段概览 | 应用当前组合筛选后的五段结果，并显示资料覆盖范围 |
| 供应商汇总 | 每行一个仓内供应商；包括货值、款数、执行量、阶段有效范围、变化及待核数量 |
| 类目汇总 | 每行一个商品类目；可按仓拆分，支持同样的指标切换 |
| 交叉查看 | 在新增汇总区域切换“供应商×类目”；只生成实际有事实的组合，不展示巨大空矩阵 |
| 查看商品 | 选中汇总行后查看门店、订单和 SKU；保留返回上层入口及当前条件 |
| 资料提示 | 显示供应商待核、类目待核；展开后给出“原件未留存”“名称为空”等具体原因 |
| 导出 | “导出供应商与类目分析”；全量明细需明确选择，先显示范围和预计行数 |

普通查询保留现有路径；进入新切面或展开新筛选候选时，在后台补充属性并汇总。补充阶段允许取消，不展示未完成的局部总数，不阻塞 GUI。只有完整且通过校验的切面结果才能导出。

查询条件改变后旧结果标记需刷新，防止用新标题解释旧数据；下钻、勾选、分页和常用视图都绑定完整筛选条件及快照。旧常用视图的 `category` 继续解释为计算分类组，不能自动换成商品类目。

## 7. Excel 与 AI

### 7.1 独立 Excel 报表

原经营分析导出的 37＋5 列及既有工作表保持。新增独立报表入口，不把供应商、类目硬插入旧列，也不修改既有商品明细导出的字段顺序。

| 新报表工作表 | 主要内容 |
| --- | --- |
| 供应商五段漏斗 | 仓库、供应商、属性状态、日期范围、五段指标、共同范围变化、缺失数量 |
| 类目五段漏斗 | 商品类目、仓范围及同口径指标；可选分仓明细 |
| 供应商类目交叉 | 仓库、供应商、类目及同口径指标；按当前选择输出 |
| 切面商品明细（选导） | 日期、门店、仓、订单、SKU、供应商、商品类目、计算分类组、必采属性及五段数据 |
| 切面资料待核 | 属性缺失/歧义及业务资料待核分别列示；保留订单、SKU 和具体原因 |

在各表顶部记录查询范围、业务日期口径、生成时间及“按签发时资料”；同一快照、同一选择必须与页面一致。来源修订、文件摘要和源行号放在明细的追溯列，不复制原始业务文件。

输出到新的文件名，采用现有流式写出和发布前校验。取消、失败和并发资料变更不得留下一个看似完整的正式报表。

### 7.2 AI 接口扩展建议

继续使用 `query_order_funnel`、`order_funnel_results`、`export_order_funnel`；不增加业务写入权限。

- 查询新增可选 `include_dimensions`、`supplier_filters`、`product_category_filters`；旧 `category` 参数语义保持。无新参数的旧调用保持原行为。
- 供应商选择必须携带所属仓、名称或明确的未知状态；类目选择携带类目值或未知状态。接口校验不接受仅凭相似名称猜测匹配。
- 结果增加 `supplier`、`product_category`、`supplier_category` 层级及可分页的筛选候选，提供资料覆盖、指标定义、缺失原因和下钻键。保留已有分页上限及 `next_offset` 规则。
- 导出增加独立的切面报表类型，接受快照标识和明确范围；原生与 AI 调用同一导出服务。
- 扩展结果携带属性版本、来源摘要和切面摘要；旧结果中已有字段的意义不变。
- AI 可以解释差异发生在哪个环节，不能把漏斗减量直接解释为上游供应商缺货，也不能把“未取得收货”说成“收货为 0”。

接口名称属于实现建议；开发时与现有协议版本策略一并落定，不把本方案当作已上线 API。

## 8. 实现路径与性能控制

### 8.1 首选实现

采用“**原五段事实＋只读属性投影＋统一分组服务**”。新增属性附在分析结果的扩展部分，不重写历史业务快照，不升级数据库或作业存储格式，也不改变供应商相关的采购配置。

1. 从当前查询已经确定的订单、所属仓和作业修订建立精确来源映射。
2. 原商品类目优先读取签发时已冻结字段；供应商从对应归档原件读取。
3. 复用现有原件校验和解析过程，按所需列提取供应商、类目及来源；原纳入规则不改。
4. 将属性状态与原 `scope` 分开存放，形成供应商、类目、交叉分组及筛选候选。
5. 使用原聚合、共同集合和天数算法生成切面指标，页面、Excel、AI 共享结果。

首期不在每次导入时增加新的业务快照字段，不建立需要跟随订单删除回收的持久属性缓存。若实测证明无持久缓存无法满足性能要求，再单独说明缓存位置、失效与删除策略后决定，不在实现中悄悄增加。

### 8.2 性能约束

- 按当前日期、门店、仓和订单范围读取，避免为筛选下拉框扫描全部历史。
- 同一查询按原件 SHA-256 与工作表合并属性读取需求；每份原件原则上只增加一次属性提取，不为每个门店、SKU、切面或导出重复解析。与原纳入依据共用读取，不能再叠加一套全文件扫描。
- 流式读取原件，只保留被当前查询使用的 SKU 属性；已存在的完整性校验继续执行。每次只持有一份正在解析的原件，不同时解压多份历史 Excel。
- 内存缓存以来源、属性版本和精确查询范围为键，设容量上限；分组保存行引用或累计值，避免为每个切面复制整份大文本和完整明细。
- 汇总先呈现，商品明细分页；交叉表按实际组合生成，避免供应商×类目×门店×全部日期的笛卡尔积。
- 所有读取、聚合和导出在已有后台任务框架执行，保留取消检查；压缩或不可中断操作安全结束后再响应取消。
- 业务发生签发修订、履约更新或删除时沿用失效机制；切面摘要包含来源与解析版本，导出和 AI 不能返回已删除订单的旧结果。
- 不为增加筛选而改删除事务、延后回收、放宽原件哈希校验，或把旧数据批量迁移一遍。

## 9. 验收标准

### 9.1 数据与业务语义

| 场景 | 必须达到的结果 |
| --- | --- |
| 同一 SKU 在两仓分别对应不同供应商 | 分别归属，不串仓；五段一直使用同一归属 |
| 两仓同名供应商、同仓名称相似 | 两仓不合并；相似名称不模糊合并 |
| 供应商为空、缺列、原件未留存 | 显示具体原因；原总体有效金额不减少 |
| 供应商原名称恰好为“待核” | 与未知状态选项分开，不误分类 |
| 商品编码、表头重复或类目来源冲突 | 待核且不重复累计；保留原完整性校验 |
| 原件哈希/内容块不符 | 拒绝发布完整结果，不偷偷用当前资料替代 |
| 商品类目与快销/日百分组不同 | 两套筛选分别正确，旧查询和旧常用视图保持含义 |
| 同一 SKU 历史改供应商/改类目 | 按当时版本分组，不覆盖旧归属 |
| 付款或实收阶段追加 SKU | 按同轮来源定位；缺来源待核，不猜 0 或猜供应商 |
| 未导入、有效 0、缺价、零分母 | 与原五段语义一致，缺失不转为 0 |
| 供应商、类目、交叉表总计 | 各自与同范围总体对账；去重款数/订单数不直接相加 |
| 实际付款金额 | 按商品行和币种归集，不能把整单金额复制给多组 |
| 预计可售天数 | 固定预测、正确分母、最新业务日可见；跨仓冲突不强算 |
| 筛选、下钻、选导、空结果 | 范围一致，旧数据不顶替新空结果 |
| 新签发、履约变化及订单删除 | 页面、AI、导出旧快照失效，未选业务记录保持 |
| 取消、失败、重新查询 | 不写业务库，不发布部分总数或残缺正式文件，可安全重试 |

保留原五段全量字段对照：在未选择新增筛选时，原指标、纳入/排除/待核、排序、数量金额及旧 Excel 字段值/类型/顺序均应零差异。历史、并发和失败样本不得通过降低预期来通过测试。

### 9.2 页面、Excel 和 AI

使用同一固定输入对三者逐字段比较；检查分页读完后的记录总数、缺失状态、币种、下钻范围、日期及快照标识。实际 EXE 验收覆盖多选、跨仓、待核选项、返回上层、常用视图、导出、取消及重新打开。

回归复用 `tests/test_order_analytics.py`、`tests/test_order_analytics_ui.py`、`tests/test_funnel_compact.py`、`tests/test_funnel_monitor.py`、`tests/test_coverage_metrics.py`、`tests/test_automation_analytics.py`，新增切面专项。先读现有工具的参数和写入位置，再决定复用或新增验证入口。

### 9.3 性能及证据

选择已有小样本、可获得的真实冻结历史样本，以及明确标注的合成多店多轮样本。分别记录普通查询、切面首次加载、缓存复查、交叉汇总、下钻、Excel 导出和取消。

- 同机、同输入，新旧交替串行至少各 3 次；性能测试期间不并行跑构建或全量回归。
- 普通旧查询对比总耗时、进程采样峰值 RSS、进程读写量；切面新增路径报告实际增加的耗时与资源开销。
- 覆盖较少/较多历史原件、较少/较多供应商、类目缺失与旧原件缺失，不仅测内存已热的情况。
- 保留每次原始记录、中位数和范围，进程 I/O 不称为物理磁盘占用率，进程峰值内存不称为整机内存。
- 普通旧查询若出现持续超出同机波动的退化，实施时必须定位并披露，修复无关全库扫描或重复解析后再交付；不在缺少实测时承诺具体秒数或固定提升幅度。
- 每轮使用独立 QA 目录；隔离数据库、离线平台响应，保留失败证据。低配置业务机没有实测时明确列为限制。

本方案只安排这些检查，尚未执行新增功能回归、性能测量或 EXE 验收。

## 10. 阶段与工作量

按单人开发、现有一层商品类目及资料供应商名称口径估算，完整版本 **3～5 人天**，包括编码、必要验证和独立打包；这是工作量估算，不是已经承诺的交付日期。

| 阶段 | 交付内容 | 估算 |
| --- | --- | ---: |
| 1. 取值与聚合 | 冻结来源、缺失/歧义、历史映射、组合筛选和汇总纯逻辑 | 0.75～1.25 人天 |
| 2. 原生页面 | 多选筛选、汇总切换、下钻、待核说明、常用视图兼容 | 0.75～1.25 人天 |
| 3. Excel 与 AI | 独立报表、可选接口扩展、分页与统一结果 | 0.5～1 人天 |
| 4. 验证与交付 | 原业务零差异、三端一致、性能、实际 EXE、说明及独立包 | 1～1.5 人天 |
| 合计 | 首期完整范围 | **3～5 人天** |

若只先交付 Excel 切面汇总和明细，可收缩到约 1～2 人天；不包含完整页面、AI 及全部交互验收。此为可选范围，本方案默认按完整版本设计，不把缩小版当作全部完成。

可能增加工作量的情况：需要补供应商编码或实际采购批次来源、需要类目多级树、旧历史原件覆盖不足且要求补齐、性能实测证明必须引入新的持久索引。发现这些情况时先给出范围及影响，不自行扩大实现。
