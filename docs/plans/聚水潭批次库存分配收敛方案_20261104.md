# 聚水潭批次库存分配：收敛方案

日期：2026-11-04。状态：方案已按最新业务口径收敛，尚未修改应用代码。

本方案替代此前核查报告中关于跨批次预留、每轮强制刷新和全仓重分配的实施建议。原报告保留为0.32.2提交`3a06151`的现状证据，其测试结果不代表本方案已经实现。

## 1. 唯一主干

**业务选定本批次的订单和商品资料 → 各仓冻结一份库存 → 按门店顺序分配 → 核对、导出 → 确认已下单。**

每个分配批次独立使用自己的库存。本地预留只用于本批次内防止重复分配，不承担跨批次库存台账的职责。

示例：批次A库存100，门店甲分40，门店乙最多分60。批次B选用新资料库存80，就从80开始分配，不再扣批次A的40或其他占用，无论A是否锁单。资料是否足够新、是否已反映平台实际下单，由业务判断。

## 2. 批次边界

- 一次明确选定的订单列表，加每仓一份选用的商品资料，组成一个分配批次。
- 原有“日批次”继续作为按天查看业务进度的入口；一天内可以有多个分配批次，不把“同一天”自动当作同一库存池。
- 本批次开始分配后，成员、顺序和库存依据固定。后续确认的回传单进入待分配列表，由下一批处理，不中途插队。
- 单店重试、重复预览、导出、软件重启继续，都不创建新批次，不重置本批库存。
- 新批次采用新选定的商品资料；允许业务明确再次选用同一份文件。软件不凭哈希、修改时间或文件名判断新旧。
- 一张订单同时最多保留一个当前有效生成结果。已生成或已锁订单不自动带入新批次重复分配。未下单订单需要换批处理时，业务先明确撤销原分配，再明确加入新批；不自动重新入队。现有付款、收货保护继续有效。
- 切换到新批时，旧批未完成任务暂停并保留；业务明确“继续原批次”才恢复。恢复绑定旧批库存和原进度，不能读当前默认库存重新起算。

批次编号由系统维护，不要求业务填表，也不改变补货单号和订单生命周期。

## 3. 库存和占用规则

按“批次＋仓库＋商品编码”计算：

> 本批可继续分配量 = 本批冻结库存 − 本批当前有效生成单占用。

库存不足时继续沿用现有分配算法和箱规规则，不能因批次改造增加可分配数量。不同仓、不同批次各自独立。

| 动作 | 本批库存处理 | 历史及其他批次 |
| --- | --- | --- |
| 预览 | 只试算，不保存占用 | 不改变 |
| 保存生成单 | 记录本批有效占用 | 不扣其他批库存 |
| 重试同一任务 | 已完成步骤复用，不再次扣减 | 不改变 |
| 重复导出 | 原样导出已保存结果，不扣减 | 不改变 |
| 确认已下单并锁定 | 保留本批占用，保护已生成数量 | 不推断付款，不给后续批次追加扣减 |
| 暂停/关闭 | 保留已经保存的占用和进度 | 不改变 |
| 撤销未下单生成单 | 释放本批该单占用，同时停止对应任务 | 留存原生成记录和原因，不释放其他批库存 |
| 重新分配 | 只替换本批所选未锁订单的占用；本批未选订单及锁单仍占用 | 不要求选齐其他批次，不改其他批结果 |
| 新建批次 | 从该批选用的库存起算 | 旧批占用不带入，旧批记录不删除 |

锁单不加回本批库存，否则同一批后续门店会重复分到已经用于下单的货。新批不继承旧批占用，也不需要维护“新库存包含了哪些旧锁单”的推断清单。

## 4. 库存准备保持简单

沿用手动导入、选用已有资料、主动在线刷新入口。**本次不新增强制在线刷新，也不逐店自动刷新。**

- 在回传确认后、分配前，业务为本批选好相关仓资料；模型计算阶段不加库存刷新动作。
- 在线获取按本批涉及仓执行，每仓采用一份成功结果。失败时暂停准备，业务选择重试，或明确选用已有资料；不默默替业务决定。
- 本批一旦开始分配，不在中途更换库存。单项重跑和恢复继续使用冻结依据；更换资料供下一批使用。
- “继续原批”沿用其剩余库存；“新建批并选用已有资料”从新批选定的原始库存起算。界面区分这两个动作。
- 保留读取期间文件变化、资料内容完整性、提交冲突等检查。这些用于保证同一次操作依据一致，不判断库存新鲜度。
- 更新默认资料或建立下一批库存，不单凭全局库存编号变化使旧批导出失效。导出校验绑定订单、回传依据、本批生成结果及撤销状态；被替换的历史结果仍走明确的历史重导入口。
- 当前资质、黑名单、禁采禁用等准入复核继续沿用现有规则，不因冻结库存而绕过现行准入。

## 5. 界面只保留必要动作

入口仍放在回传处理和聚水潭导入单工作页，不增加生命周期阶段。

1. **准备本批**：选门店订单、确认顺序，为山东仓/河北仓选资料。默认顺序继续使用回传确认时间及现有同时间决胜规则，业务可明确调整。
2. **分配并核对**：先看门店级金额、满足量、削减量和受影响SKU，必要时展开商品。
3. **导出所选生成单**：可重复导出，不改变占用。
4. **确认已下单**：保护所选结果，不自动确认付款。

辅助操作清楚区分：继续原批、重试失败门店、暂停、撤销未下单分配、新建批次。新建批次不删除旧批，暂停不释放占用，撤销必须停止自动再生成。

同仓前序任务失败时暂停后续同仓任务，重试仍在原位置，避免后店抢先用掉库存。两仓库存独立；结果展示及文件输出仍按本批确认的顺序，不按任务完成先后重新排列。

## 6. 最小开发范围和顺序

### 阶段一：批次隔离与队列正确性

- 保存批次成员、门店顺序和分仓库存快照引用。继续复用现有分配与提交服务，不复制一套算法。
- 任务、生成单、预留明确绑定分配批次；恢复和重试从批次读取依据。
- 预留查询限定本批，不再汇总全仓全部历史有效单。
- 修复撤销联动队列：释放与取消同事务完成，已在内存的任务提交前也复核取消状态。已完成步骤幂等复用。
- 保证同仓前序失败不越过；本批局部重分配原子替换所选旧占用。

### 阶段二：入口与导出衔接

- 区分“继续原批”和“新建批次”，展示本批门店、仓资料及处理进度。
- 手动与自动任务统一绑定明确批次，不把每个门店的prepare调用当作新批。
- 导出有效性从“全局当前库存”调整为“本批依据和当前有效生成结果”；所有普通导出入口使用同一检查。
- 复用现有资料获取入口，不扩展浏览器自动化，不增加文件年龄判定。

### 阶段三：兼容和验收

- 新增批次元数据及关联，不重写已有签发、回传、付款、收货和历史生成快照。
- 老记录按已有事实查看、导出，不凭日期或相似文件推断它们属于一个新批。老待执行任务进入明确核对后再继续，不悄悄混入新批。
- 完成服务、事务、恢复、导出及实际EXE验证后交付；保留旧版本。

预计主要涉及`jst_tasks.py`、`jst_orders.py`、`jst_results.py`、相关界面及少量批次元数据。不是只给预留查询加一个条件：任务恢复、当前有效生成引用和导出校验必须一起绑定批次，防止只改扣减却留下串批入口。

## 7. 必须通过的验收

以下是后续开发的目标验收，尚未执行，不能用原核查报告的通过数代替。

| 场景 | 目标结果 |
| --- | --- |
| A库存100，第一店40，第二店要80 | 依次40/60，余额0 |
| A已占40，B选库存80 | B从80开始；A锁或未锁都不额外扣40 |
| A占40，B选库存60 | B可分60，不扣成20 |
| 同一文件明确用于新批 | 可建立新批，不因哈希相同合并或拒绝 |
| A生成40后重复导出、重复提交 | A只占40，数量金额不变 |
| A生成40后撤销，原自动任务尚排队 | A释放40，后台及重启后均不得复活；B不受影响 |
| A部分重新分配并重复提交 | 旧占用只替换一次；A未选及已锁单不动，B不动 |
| A暂停，B导入新资料，随后恢复A | A使用自己的原库存和进度，不采用B资料 |
| 第一店失败，重试后继续第二店 | 仍按原顺序分40/60，不变成20/80 |
| 两仓含相同SKU | 按批次及仓独立计算，不能混扣 |
| B建立新库存后重导A当前有效结果 | 原数量、金额、列顺序不变，不因B库存更新自动改量或失效 |
| 回传、准入或当前有效结果确实改变 | 沿用对应保护；不能借批次隔离绕过核对、锁定或撤销 |

## 8. 本次收敛后的边界

不做跨批次预留结转、库存新旧自动判断、锁单与平台扣减推断、全仓跨批重分配、强制自动刷新或新增生命周期。

模型计算、预算、箱规、单价取值方式、准入规则和付款实收口径保持原规则。变化仅在库存分配作用域、任务状态衔接和导出依据绑定。

业务原则已经明确，本方案没有新增待业务决策项。开发前需要落实的是技术兼容与状态绑定，不再扩大为库存管理系统。
