# 运营签发生命周期与全流程经营分析方案

在门店回传之后、聚水潭库存分配之前，增加“运营签发”环节。**业务上就是现有回传的同一套逻辑换一个环节名称**：页面、样式、认单、整单核对、数量处理、保存、更正和导入导出都复用回传实现，不另造审批流程。只区分环节名称、独立保存的数据及上下游位置。经营分析按完整过程展示数量、转化、耗时和缺货率趋势，导出遵循“业务数据在前、订单关联在后”的阅读顺序。

这是实施方案，本轮仅新增本文，不修改业务代码、数据库、EXE或已有交付，不提交、推送或合并。

## 一、已经确认的业务要求

1. 新环节位置：**门店回传 → 运营签发 → 聚水潭分配 → 付款下单 → 实际收货**。
2. 运营签发与门店回传**逻辑和样式均一致**，不只是模板相同；可见表头、列顺序、填量、核对、保存和更正规则全部复用，不增加业务必填字段或审核条件。
3. 运营签发支持单个导入、批量导入、从已确认回传一键生成，以及单个导出、批量导出、一键衔接付款。
4. 一键流转在本机传递已确认数据，不要求导出Excel再导回来。
5. 经营报表先放门店、仓、日期和业务数据，签发单号、聚水潭内部订单号、翱象采购单号统一后置。数量、款数、货值分视图，不同时铺成很宽的主表。
6. 要能观察各环节随时间上升、下降的情况，并联看门店和大仓缺货率的变化。
7. **原五段生命周期的漏斗率值必须有独立时间趋势看板**，不能只展示节点数量、完成单数或当前时点漏斗；增加运营和分配后继续保留原五段比率的定义，并增加新环节的分段比率。
8. **防止逻辑死锁和过严审批是实施与交付条件**。正常改量、正常价差、资料暂缺或单个旧任务异常不能演变成全流程无法继续；必要校验必须有明确影响范围和可操作的恢复路径。

本稿将“从运营签发自然导出到付款”解释为保留一个直达入口，但中间完成既有聚水潭分配：按钮为“分配并准备付款”。付款准备以实际分配结果为准。真实外部付款文件仍可独立导入，不要求补造本机不存在的分配记录。

## 三、业务如何操作

### 3.0 复用回传逻辑，仅替换环节配置

采用同一套生命周期实现，通过环节配置区分“门店回传”和“运营签发”，不复制并维护两套分叉的业务代码。

| 完全复用回传的部分 | 运营环节仅需要不同的部分 |
| --- | --- |
| 页面布局、表格、模板及可见字段 | 环节名称显示为运营签发。 |
| 单张/批量认单、整单范围与行处理 | 数据保存到独立运营环节，不覆盖回传。 |
| 明确0、空白、缺行、清单外商品和数量差异处理 | 上游输入由原补货签发改为已确认门店回传。 |
| 核对、保存、留存待核、更正、取消、重试 | 运营确认后的下游是聚水潭分配。 |
| 单张/批量导入导出、关联身份及文件留存 | 隐藏元信息记录所属环节和来源版本。 |

回传允许的正常业务操作，运营签发同样允许；回传没有的审批条件，不因为环节叫“签发”而额外增加。完整性和并发保护也使用同一套公共能力，不为运营另设更严的审核分支。

### 3.1 运营签发页面

订单跟踪增加“待运营签发”状态及入口，列表继续显示门店名称、门店编码、供货仓、业务日期和本次数量。进入运营环节时沿用回传页面的布局与表格组件，避免出现第二套操作习惯。

常用动作放在主表附近：导入运营签发、导出运营签发、采用回传并运营签发、进入聚水潭分配、分配并准备付款。单张与批量沿用同一套动作：勾选一单即单张，勾选多单即批量，按钮显示实际订单数。

主表只展示本环节业务内容；回传与运营的增减量、调整记录在可展开对比区查看。表格获得主要高度，说明和历史记录默认折叠；不在上方堆多行按钮挤压商品明细。

### 3.2 导入和导出能力

| 方式 | 业务操作 | 系统处理 |
| --- | --- | --- |
| 单张导入 | 在运营环节拖入或选择一张文件 | 自动认单，读取为本次运营数量，核对后保存运营版本。 |
| 批量导入 | 一次拖入多个文件或合并工作簿 | 按原仓单身份拆分，列出将新增、更正、不变和需处理的订单；只保存明确选择的范围。 |
| 自然导入 | 回传页面点击“采用回传并运营签发” | 直接采用已确认回传的数量和对应版本，记录来源为一键采用；不生成中间Excel。 |
| 单张导出 | 勾选一单导出 | 按当前有效运营版本输出与回传相同样式的文件。 |
| 批量导出 | 勾选多单导出 | 沿用现有逐单文件及合并工作簿方式，保留各单隐藏身份。 |
| 自然导出 | 运营页面点击“分配并准备付款” | 使用运营签发量进入原聚水潭分配流程；有效分配结果直接生成付款核对草稿，无须绕回跟踪页搬文件。 |

“采用回传并运营签发”本身是明确的保存动作：将已确认回传作为运营输入，复用现有回传的核对/保存能力，无变化时一次点击完成并进入运营页面，不另加一次运营审批。需要修改时复用现有编辑、留存待核和确认保存方式，不新增“审批中”“终审”等状态。未确认的数据不会提前进入分配。

批量动作严格限定勾选身份，不因为同店同名或分页切换扩大范围。无变化的重复点击复用原结果，不增加版本或重复库存占用。取消只停止未提交部分，已完成订单在结果列表明确保留。

### 3.3 与门店回传完全相同的文件样式

- 复用同一模板和写表组件，不复制出一套独立、容易漂移的格式代码。
- 可见表头、列次、宽度、配色、数量栏、备注栏、填写说明和整单范围处理规则保持一致。数量列沿用回传的既有表头，由运营导入入口解释为运营环节数量；不会把它保存回门店确认数量。
- 导出文件名可标明运营签发，业务表内不新增“运营审批号”“操作者账号”等必填列。
- 隐藏关联信息扩展为：环节类型、原签发仓单身份、回传版本、运营版本及摘要。隐藏信息用于防止关联错单，不被当作账号认证。
- 从明确的运营入口导入无环节标识的回传同样式文件，按运营环节读取。混合环节批量导入优先使用有效隐藏标识；两种文件完全同样式且没有环节信息时，不凭外观猜环节，转到明确的环节入口处理即可，无需改文件或填写新字段。
- 运营入口采用回传文件属于明确的环节转换，保留原文件身份及转换来源；不能在后台静默覆盖回传记录。

自动关联继续依据有效签发身份、保存的关联、门店及整单资料。不能凭单个SKU、辅助码、条码或历史仓归属推断付款单属于哪个仓，也不恢复此前已撤销的相关拦截。

## 四、新环节保存什么，后续如何跟随

### 4.1 运营签发是独立事实

运营签发保存完整商品数量、原文件、来源方式、上游回传版本、操作者可取得的信息、签发时间、版本和摘要。不覆盖原补货签发，不修改门店回传，也不调用补货模型重算。

页面用“补货签发”和“运营签发”区分两次动作。原签发单号继续作为整条订单链的主关联号；运营版本作为内部子版本，不要求业务再维护一个新单号。款数、数量增减与备注均可回查到同一仓单。

运营按回传相同的规则确认、减少或增加数量；与上游不同的数量是本环节正常事实，不能因为“不完全匹配”直接阻止保存。单位、数值合法性、重复行冲突及目标单身份继续使用回传通用校验；清单外商品按同一规则明确展示，不按商品编码猜仓。运营数量不意味着库存已分配，也不意味着已付款。

### 4.2 下游依据

新流程的依赖顺序为：

已确认回传版本 → 运营签发版本 → 聚水潭分配版本 → 付款版本 → 收货版本。

每一步冻结来源版本和摘要。保存或提交时复核原仓单仍有效、版本未变、目标范围未被删除。一个订单的新版本不影响其他订单，不按数组位置回写批次。

“分配并准备付款”使用持久步骤记录：先运营依据校验，再原分配预览/确认，再分配提交，再付款草稿准备。各步使用稳定操作身份，重试只补未完成步骤，不重复分配、不重复扣减库存。过程中断后明确显示“已分配，付款草稿待准备”等实际状态，不把多步动作假装成一个跨库原子事务。

分配必须遵守当前库存、箱规、顺序、未选订单占用和锁单保护。运营签发量不直接替代分配量。正数量缺价时，已确认的运营和分配数量保留，付款显示缺价原因，不填0元。

付款草稿准备完成后展示核对页面。只有用户明确确认付款来源并保存，才产生付款事实；本机付款保存不代表真实扣款，不会因此自动上传采购单或向真实平台下单。真实外部付款表仍独立记录实付金额和实际数量，不能要求它必须与运营或分配完全一致。

### 4.3 更正和旧订单

| 情况 | 处理 |
| --- | --- |
| 新回传尚未运营签发 | 状态为待运营签发，可一键采用或导入。 |
| 运营草稿未确认 | 保留草稿，不能用它开始正式分配。 |
| 运营签发后尚未分配 | 可保存新的运营版本，按新版本进入分配。 |
| 已分配后更正回传或运营数量 | 原分配标为依据已更新；从原批更正重分配，保留未选订单及原库存占用。 |
| 已付款、未收货后更正 | 保留原付款事实，经过运营重新确认和既有原批更正流程；新结果要求重新核对付款，不强制清空旧付款。 |
| 已锁单或已有收货事实 | 沿用既有更正保护，不自动解除锁单、不覆盖已经发生的收货。 |
| 删除订单后旧任务回写 | 同步失效新环节、草稿、分析缓存及步骤记录；晚到回调不能重建订单。 |
| 运营确认整单0 | 明确记录为已确认0，与缺资料区分；沿用现有无要货结束规则，不造付款或收货量。 |

引入订单流程版本。升级前订单按原流程继续处理，已付款或已收货订单不会统一退回待运营签发。历史运营量显示“启用前未留存”，不自动把回传量复制成历史运营事实。

新建订单按新流程执行；旧未完成订单可以通过明确的“采用回传并运营签发”接入新流程，届时展示会失效的下游依据。数据迁移采用增量兼容，不为新增环节重写全部历史快照。旧版回退时不得静默写入含有新运营依据的订单；升级前备份和旧版交付继续保留。

### 4.4 防止状态锁死与过严审批

本节是共享生命周期实现的可用性与验收要求，**不是运营签发新增的一套业务审核规则**。运营直接沿用回传能力，不增加审批人配置、重复勾选、逐行必填调整原因或必须与上游完全一致的条件。数量增减、率值超过100%、实际付款价差属于业务事实，应展示差异并允许按本环节规则处理。

**业务差异不等于关联错单。** 导入目标身份明确后，不因SKU清单、数量或金额与上游不同，就禁止绑定或留存；不能用辅助码、条码或SKU历史仓归属另设拦截。身份冲突、数值无法解释等问题要指向具体行和解决动作，原件仍可先留存为草稿或待核，不让用户反复导入同一文件。

运营提交沿用回传的公共条件，不另加门槛：目标仓单仍存在且身份明确，必要数量/单位合法，依赖版本仍有效，真实付款/收货和库存占用未被错误覆盖。付款继续使用付款环节自己的规则；缺价不阻止与回传相同的运营数量保存，分析标签或资料状态不成为运营审批条件。

后续实现必须满足以下约束：

1. **依赖保持单向。** 回传确认不依赖运营签发，运营签发不依赖分配完成，分配不依赖付款完成；不能出现两个环节互相等待对方先完成。上游更正只标记相关下游需要重新核对，不删除旧事实或要求用户重新从头做单。
2. **锁定精确对象。** 任务占用绑定仓单身份、版本和操作；只限制确实共享该资源的写入。其他日期、门店、仓单不能因无关旧任务被整体阻塞。库存分配保留真实共享库存资源的串行保护，但本地草稿、历史查看和导出不等待平台登录或任务结果。
3. **每个非终态都有出口。** 等待、失败、取消、依据过期、部分完成、回执未知分别提供继续、重新核对、取消未开始部分、结束本地步骤或更正入口；不能只留下“待核，不自动重试”而没有下一步。结束本地步骤不冒充外部任务已撤销。
4. **未运行与正在提交分开。** 禁止仅凭旧busy标志、旧批次未完成或界面按钮灰掉认定任务还活着。记录实际工作进程、操作身份和存活状态；失效执行者按已有提交回执恢复。超时不能直接清除正在提交的任务，也不强杀、强行解锁或盲目重复外部请求。
5. **写事务短且可恢复。** 网络、浏览器等待、文件读取和报表生成放在写事务外；仅在提交时复核相关版本。数据库繁忙采用有界等待并显示实际占用或可取得的诊断，结束后释放资源，不无限等待，不把“重启电脑”作为业务恢复步骤。
6. **重试接续已完成部分。** 保存了运营版本就不重复签发，分配已提交就不再次扣库存，付款草稿已准备就打开原草稿。部分失败逐单说明已保存、未保存和待处理部分；未选订单不受影响，同一批其他订单不被失败项改写。
7. **按钮状态必须回收。** 成功、异常、安全取消、窗口关闭、子进程退出、重启恢复均检查任务结果并回收busy状态。仍有异常时保留查看原因和恢复入口，不能把全部操作永久禁用。重复点击只复用相同操作，不生成并发重复提交。
8. **无变化不重复核对。** 已确认范围及依赖未变时，导出、切换页面、重开窗口不撤销确认；仅相关上游内容或实际范围变化时重新核对。不能因为其他订单进度或不相关全局版本变化，使本单确认反复失效。
9. **拦截必须可解释。** 每次未完成提示明确是哪张单、哪个环节、什么数据/版本发生变化、当前是否已保存以及可点击的下一步。校验失败不能只写在表格底部，不能出现按钮点击后没有可见反馈；可直接定位具体商品或冲突信息。

实施时对每条拦截登记“保护什么、拦哪一步、作用范围、恢复入口、对应测试”。没有明确业务或完整性目的的拦截不新增；存在拦截却没有恢复动作的状态不得作为验收完成。

## 五、全流程经营指标

### 5.1 展示七个观察节点

原五段加入运营签发形成六段经营事实，聚水潭分配作为额外执行节点一起展示。前端统一称“全流程经营分析”，按顺序展示：

**模型建议 → 补货签发 → 门店回传 → 运营签发 → 聚水潭分配 → 付款下单 → 实际收货。**

这样可以区分运营改量、仓库分配不足、实际下单更正和最终实收变化。七个节点分别取各自已经留存的有效版本，不用前一环节数量填充缺失节点。

每个节点支持数量、款数、货值三个独立视图。数量沿用库存单位执行统计，混合单位注明且可按单位筛选；款数取有效正数量去重SKU，跨店或跨仓不能直接相加为全局款数；可比货值统一采用冻结签发价，真实付款金额单列，不混入同价漏斗。

### 5.2 主要过程指标

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 各节点数量及增减量 | 同一有效商品集合：下节点数量减上节点数量；同时保留增加量和减少量 | 看改量发生在哪个环节，避免增减相抵后看不出问题。 |
| 运营确认比 | 运营签发量 ÷ 门店回传量 | 看运营采用和调整情况，可超过100%。 |
| 仓库分配满足率 | 分配量 ÷ 运营签发量 | 看仓库供应约束。 |
| 下单执行率 | 实际下单量 ÷ 分配量 | 看分配后真实执行变化；无分配依据则不计算。 |
| 已记录样本实收率 | 已有有效实收资料的相同样本，实收量 ÷ 实际下单量 | 不把未收货当0，旁边展示收货资料覆盖率。 |
| 环节耗时和待办 | 已完成节点间的实际事件时间差；未完成单独展示等待时长和数量 | 区分已完成效率与尚未完成的积压。 |

保留模型到补货签发、签发到门店回传及首尾转化指标，放在漏斗总览和展开指标，不要求默认主表同时展开全部比值。分母0、缺资料或依据失效留空并显示原因；整体比率使用同样本汇总分子除分母，不能平均各门店比率。

各节点之间允许正常加单或减量，比例超过100%不直接当异常；数量上升也不自动判定经营改善。时长按真实事件顺序记录，不把业务日期补成签发时分秒。

### 5.3 随时间如何看

默认日视图，可切周、月，并提供两种明确的时间口径：

1. **按补货业务日期看一批订单。** 同一批仓单在同一个数据截止时间下，比较各节点的量、转化率、缺口和覆盖。更正版本不被当成新的补货轮次重复计入。
2. **按实际办理时间看作业。** 展示每天运营签发、分配、付款、收货完成单数及耗时。新办、更正、撤销分别计数，不与业务日期的订单规模混为同一指标。

趋势图展示节点数量或货值折线、各段转化率、增减量和待办变化；点击某天或某段可下钻到门店、仓单和差异SKU。默认曲线控制在当前选择的少量指标，其余通过选择展开，保持可读性。

周/月按完整自然周期比较；正在进行的周期标为累计。金额或数量环比为本期÷上期－1，上期0不计算；比例变化使用百分点。没有业务或没有采集的日期保留空档，不补0，不用未完成周期冒充完整周期改善。

默认展示当前有效版本，允许选择“截至某时点回看”；办理时间趋势保留历史动作。需要记录阶段确认、更正、撤销、重新核对的版本和时间，旧资料没有的事件不反推、不补造。

### 5.4 五段漏斗率时间趋势看板

新增明确的“漏斗率趋势”页签，作为经营分析的常用看板，与数量趋势、作业耗时、缺货率趋势分区。即使尚未接入新运营流程，也可以查看原五段漏斗率的日、周、月变化。

原五段需要独立观察以下五项，不因新增运营环节改变原指标含义：

| 看板短名 | 原五段定义 |
| --- | --- |
| 补货签发率 | 补货签发 ÷ 模型建议 |
| 门店确认率 | 门店回传 ÷ 补货签发 |
| 回传下单率 | 实际下单 ÷ 门店回传 |
| 下单实收率 | 实际收货 ÷ 实际下单 |
| 全程实收率 | 实际收货 ÷ 模型建议 |

每项均可切换数量、款数、货值口径；同屏比较时必须使用同一口径。数量为库存单位执行统计，允许按单位筛选；货值沿用冻结签发价。用户可按大盘、山东仓、河北仓、门店、必采属性、供应商、类目筛选或对比，查询条件与导出保持一致。

新流程另外提供运营确认比、仓库分配满足率、下单执行率三项趋势。原“回传下单率”继续反映从门店回传到实际下单的总体执行，新三项用于拆解其中的运营调整与分配变化，不能把新指标替换到原指标名下。历史没有运营或分配事实时，新三项留空，原有有效五段指标仍可查看。

看板布局保持简洁：

1. 顶部放日期范围、日/周/月、数量/款数/货值、环节比率和维度筛选。
2. 中部放五项漏斗率概览，每项显示本期值、上期值、变化百分点及小趋势；点击其中一项，在主图展开该率值曲线。
3. 主图横轴为补货业务日期或完整周/月，纵轴为实际百分比。可选少量环节或门店/仓进行对比，不把数量和百分比画在同一刻度。超过100%的有效值如实显示，不封顶。
4. 图旁或下方同步显示每个点的分子、分母、有效仓单数、可比SKU数及资料覆盖；实收指标额外显示实收覆盖，便于识别“率提高但样本减少”。
5. 点击曲线点下钻到该周期的门店/仓单，再查看造成变化的商品及版本。单号留在明细末尾，不挤占主图和主要业务列。

各点按该周期内两个环节共同有效的仓单及商品集合重新汇总分子分母，周/月比率不能平均每天比率，整体比率不能平均门店比率；款数按本组SKU去重，不能累加每日去重款数充当周期去重款数。全程实收率直接按模型与实收的共同有效样本计算，不能将相邻段比率连乘，因为各段资料覆盖可能不同。

率值变化以百分点为主：本期率减上期率；与数量增减率明确区分。默认同时展示真实业务覆盖和“同完成条件对比”入口：两期各自选择前后环节均有效的仓单，再按共同门店、供货仓及商品范围汇总，各期使用自己的仓单，不要求不同业务周期存在同一仓单。不能把未付款、未收货、分母0或无数据日期补成0%，曲线在无有效比率处断开。

趋势默认按相同查询截止时间计算各业务日期的当前有效率值；历史回看使用当时已保存的版本和截止时间。较新的业务日期尚在等待下游时提示覆盖不足，不能将未成熟批次直接解释为执行变差。按实际办理时间的完成量和耗时继续放在作业趋势，不能混作漏斗率的日期口径。

支持导出“漏斗率趋势”工作表和对应图表。趋势数据行包含周期、所选维度、环节、指标口径、分子、分母、率值、上期率、变化百分点和覆盖情况，订单关联放在下钻明细末尾。Excel百分比保持数值类型，导出图与页面使用同一查询快照、筛选及截止时间。

## 六、缺货率趋势如何接入

缺货率读取现有独立“缺货率”板块的有效日报，经营分析只读关联，不改采集资料、补货默认参数或库存事实。打开经营分析不自动发起平台采集；需要补采时进入已有缺货率入口，沿用其单跑、一起跑和每日计划能力。

| 指标 | 继续采用的口径 |
| --- | --- |
| 门店缺货率 | 同一筛选范围有月销商品中，可用库存≤0的缺货数÷有销基数。负库存按0统计；停采/禁采、供货仓禁用及淘汰视角沿用现有选择，虚拟分类精确“淘便考核”固定剔除。 |
| 大仓缺货率 | 同一仓有效商品范围内，可用库存≤0的缺货数÷有效基数。不要求月销；继续剔除淘汰、禁用、商品标签精确日配和虚拟分类精确淘便考核。 |
| 缺货率变化 | 本期缺货率减上期缺货率，以百分点展示；同时列出两期缺货数、基数和已覆盖门店/仓数。 |

同屏分区展示过程转化趋势和缺货率趋势，支持门店、供货仓、供应商、类目、必采属性等共有维度联动。两套资料的维度依据不同或某项不可用时明示，不能把未匹配的记录消失掉，或强行按名称拼接。

需要区分“整体结构变化”和“相同样本变化”：常规视图保留各日真实基数，另提供两期均有有效观测、同口径的可比店品/仓品范围。切换口径后重新汇总分子分母，不平均日百分比。必采清单、标签剔除、供货关系、资料版本变化应能追到对应依据。

业务日期和缺货观测日期各自显示。给某张订单关联日报时优先使用明确的同日有效快照，并列出采集时间；没有对应观测就显示未采集。不能自动借其他日期填满过程，也不能把订单数量增加推算成库存缺货已经改善。只有真实后续观测能形成缺货率变化；缺货率下降不直接归因于本批订单。

新日报更正保留修订；旧报告按自己的数据截止时间和版本可追查。删除原订单或分析资料时同步使关联结果失效，不留下能恢复已删业务内容的隐藏明细。资料缺失不借另一业务当前资料回填历史。

## 七、经营分析导出样式

以用户提供的门店补货订单漏斗样式作为阅读参考，采用“先总览、后轮次、再切面和追溯”的顺序。

| 工作表 | 展示内容 |
| --- | --- |
| 漏斗汇总 | 指标纵向排列，大盘、山东仓、河北仓横向对比；分段展示完整过程、转化和实收覆盖。 |
| 门店轮次明细 | 默认一行一个门店×仓×补货轮次；业务身份和数量在前，关联号在最后。按当前选择的必采视角导出，不把“全部”和子分组重复堆叠后误加。 |
| 过程趋势 | 日、周、月的节点数量、比率、覆盖及变化，可追到所用时间口径。 |
| 漏斗率趋势 | 原五段五项率值及新增运营/分配比率的日周月曲线、分子分母、百分点变化与覆盖，可下钻明细。 |
| 缺货趋势 | 门店/大仓缺货数、基数、比例、百分点变化、观测日期及覆盖。 |
| 类目与供应商切面 | 继续保留现有日期、仓、必采、门店、SKU等切面，按本次选择输出，数量、款数和货值分视图。 |
| 单号关联明细 | 一对多外部号、签发身份、当前状态和各版本对应关系，保持末尾。 |
| 统计口径 | 简短业务定义、空白与0、实收覆盖、历史运营缺失和周期说明。 |

门店轮次主表字段分组：

1. 业务身份：业务日期、门店名称、门店编码、供货仓、必采视角、库存单位。
2. 过程数量：模型建议、补货签发、门店回传、运营签发、聚水潭分配、付款下单、实际收货。
3. 关键结果：运营确认比、分配满足率、下单执行率、实收率。
4. 当前状态：流程进度、实收记录状态、数据截止时间。
5. 关联追溯：签发单号、聚水潭内部订单号、翱象采购单号。

以上主表预计23列，数量、款数、货值用相同布局的独立视图替换，不把三套指标挤到同一行。表头用“运营签发数量”“分配满足率”等明确短名；冻结身份列和表头，允许筛选，编码保持文本，数量、金额和百分比保持可计算类型。

供应商资料状态、类目资料状态、五段资料覆盖、维度资料依据这四个此前明确移除的字段不重新加入业务导出。必要缺失原因保留在简洁提示和口径中，详细追溯通过明细入口查看。

前端图表、表格和导出使用同一个已冻结查询结果、范围和截止时间，导出包括全部筛选结果，不限于当前页。不增加需要人工搬运的“数据录入”流程，原件自动提取为业务明细。

## 八、实施顺序与改动范围

### 第一步：运营环节及兼容

在 `lifecycle_io.py`、`order_lifecycle.py`、`lifecycle_rules.py` 的现有公共能力中增加运营环节配置、独立保存、上游依赖、流程版本和旧单兼容；同步状态总览、单张/批量导入导出、混合文件识别、隐藏关联信息及操作日志。页面、模板、认单、核对保存和更正均复用回传实现，不另写运营审批引擎。

### 第二步：分配与付款衔接

扩展 `jst_orders.py`、`jst_batches.py`、`jst_results.py`、`jst_payment.py` 及对应页面。把新单分配依据切换为运营签发；补上运营更正后的原批重分配；一键准备付款复用现有精确生成结果。先完成依赖校验和重试保护，再开放按钮。

同步数据维护、订单/参数资料迁移、完整订单导出、失败回滚与删除清理，避免运营数据遗漏。索引和缓存按新格式失效更新，不能继续显示旧的“下一步”。

### 第三步：全流程分析和清爽报表

扩展 `order_analytics.py`、生命周期对比、数量/款数/货值投影、切面导出及UI，纳入运营和分配节点；增加独立漏斗率时间趋势看板、事件时间趋势、只读缺货日报关联和统一查询快照。保留原五段字段的含义，对扩展响应增加显式指标版本和节点顺序；MCP/AI导出与原生页面同步，不让旧客户端把列位置读错。

经营分析按需启动查询与绘图进程；不进入且没有明确分析任务时，不加载全量历史明细。缺货率仍独立保存，不改为启动时常驻加载。过程事件增量索引，不在每次打开页面时重扫全部原始Excel。

### 第四步：验收和教程

更新以业务为导向的图文手册：回传怎么直接运营签发、运营如何调整、如何分配并转付款、更正后为何需要重新核对、如何看过程趋势与缺货率。通过隔离回归后再独立打包，旧版保留；推送合并另按用户后续指令执行。

按“运营直接复用回传”的收窄范围，整体初估约10～15人日：环节配置及兼容2～3，分配/付款衔接2～3，分析/导出3～5，回归/EXE/教程3～4。主要工作在上下游衔接、旧单兼容、趋势看板和验收，运营本身不按新审批系统开发。此为工程量估算，不是完成承诺；不含新增真实平台接口或不存在的历史缺货资料补采。

## 九、必须通过的验收

1. 运营模板与回传模板的可见字段、样式、填量方式一致；仅隐藏环节元数据不同；单张、批量、合并文件均可正确识别。
2. 从已确认回传一键运营签发不产生中间Excel，运营数量正确，回传数量不变；重复点击不产生重复版本。
3. 运营增量、减量、明确0、空白、缺行、清单外商品按同一套整单规则展示与保存；不因正常数量差异认定错单。
4. 运营数量不同于回传时，聚水潭只用已确认运营版本分配；运营草稿不可成为正式依据。
5. 一键分配转付款使用真实分配结果；分配中断、付款准备失败后续跑不重复扣库存，也不自动确认真实付款或调用平台下单。
6. 回传或运营在预览后发生变化时拒绝提交旧依据；同时更正同店两仓、多单批次和未选订单时不串单、不扩范围。
7. 已付款后更正可以按原批流程重新分配，旧付款留存、重新核对指引明确；已锁单、已收货保护不被绕过。
8. 升级前已付款/已收货订单继续可查可用，不统一变成待运营；历史运营为空，不伪造签发动作；旧单显式接入新流程可追查。
9. 删除、取消、迁移、重启恢复、并发回写均覆盖运营及新步骤；删除后晚到回调不能复活订单。
10. 用隔离独立预期逐项校验七节点、各阶段共同样本、分母0、超100%、明确0、缺失、缺价、重复SKU和混合单位；不是只比较两个共用公式的页面。
11. 业务日和办理日趋势不重复计算更正版本；周月完整周期、未采日期、实收覆盖变化及新增/退出门店均有明确表现。
12. 门店和大仓缺货率与本板块同范围结果一致，剔除规则一致；缺资料不补0，不从订单量推算库存。供应商/类目缺失、归属变更和资料版本冲突可追查。
13. 前端和Excel的筛选范围、分子分母、值、类型、单号关系一致；主表业务数据前置、关联号后置，四个已移除字段不回流。
14. 真实EXE在常规、放大字体和小屏下验证核心业务表可读；完整回归、取消、失败回滚与低资源响应检查通过。只用隔离数据库和模拟平台，不删除真实业务数据、不调用真实平台。
15. 漏斗率看板逐项覆盖原五段五项比率及新增运营/分配比率，日周月数据、百分点变化、分子分母和覆盖均与独立计算一致；验证周月不能平均日比率、款数不能简单相加、全程不能连乘分段率。
16. 覆盖不足、未成熟批次、无数据、分母0、超100%、跨仓对比及版本更正时，曲线、提示、下钻和导出保持一致；旧订单不因缺运营事实丢失原五段趋势。
17. 检查回传、运营、分配、付款的依赖不存在循环；所有等待、失败、取消、过期、部分完成和回执未知状态都有明确恢复动作。旧任务残留不锁死无关日期、门店或仓单，也不妨碍本地查看与草稿留存。
18. 用正常增减量、超过100%、付款价差、缺价、清单变化、标签待核验证不会增加无关审批；身份明确的单据不因上下游数值不一致拒绝绑定。不能恢复SKU猜仓、辅助码、条码拦截。
19. 模拟界面异常、执行者退出、重启、数据库繁忙及各步提交前后中断，验证busy释放、按钮恢复、有界等待和已提交步骤的幂等续跑。每单结果明确，不强杀提交、不重复分配或付款保存。
20. 每个有意拦截都能直接看到具体原因及恢复入口；核对范围未变时不反复审批，点击无反馈、全页永久失能或需要重启电脑才能恢复均判定验收失败。
21. 对回传和运营输入相同结构的隔离数据，比较认单、整单核对、明确0、空白、缺行、增减量、重复导入、更正、取消和导出结果。除环节身份、上游版本与保存位置外，行为必须一致，运营不得出现回传没有的审批或阻塞条件。
