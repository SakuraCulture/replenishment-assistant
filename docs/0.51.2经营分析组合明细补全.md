# 0.51.2 门店经营分析组合明细补全

原“经营分析 → 门店经营分析”只导出门店、分仓和订单汇总，没有SKU与上游供应商、原商品类目组合明细；分析事实也没有读取上游供应商。这是导出链路未补齐，不是业务没有这些数据。

本版在“门店经营分析”和“订单经营分析”导出中增加 **门店SKU供应商类目** 工作表；“当前商品明细”同步增加属性列。既有三张汇总的列位置和数值口径保留，既有单号关联明细继续保留。

## 每行是什么

一行是同一“门店编码＋供货仓＋SKU＋大仓上游供应商＋商品类目＋计算分类组＋库存单位＋必采属性＋纳入状态”的组合，附门店名称和商品名称。同组合跨日期汇总，显示业务开始/结束日期和去重签发仓单数；供应商、类目、单位或仓不同则拆行，不把两仓同名供应商混在一起。

五段均包含正数量去重SKU数、执行数量和按签发价计算的货值，并保留相邻阶段及首尾比值、五段新增可售天数、天数依据业务日、资料覆盖和维度依据。比值重新按共同有效商品集合计算，不平均其他汇总行；可售天数沿用固定预测、最新业务日和签发价加权规则。

签发单号、聚水潭内部订单号、翱象采购单号在行末逐单对应。多单用换行对应，完整逐单关系见“单号关联明细”。只勾选部分订单导出时，新表同步限定到所选订单。

## 供应商和类目从哪里来

- 大仓上游供应商：签发作业修订 → 本仓冻结资料 → 已归档原件SHA256及工作表 → 商品编码 → “供应商名称”。不使用补货建议C列的中心仓编码，不读当前默认仓资料，不做名称别称合并或多供应商拆分。
- 商品类目：签发`_category`/`_meta.category`、同轮冻结仓资料“分类”及归档原件“分类”。多个留存来源均有值时须一致，冲突标记类目待核。
- 计算分类组：保留原结果`U`，例如快销、日百，与原商品类目分别展示。
- 生命周期追加商品也只使用原订单本仓的历史依据，不从其他仓或最新资料猜归属。

缺列、空值、商品编码不唯一或来源冲突保留具体待核原因；原件哈希损坏仍阻断发布，不当作普通缺失继续导出。供应商/类目待核不改变五段原纳入规则：原本纳入的商品继续计入，未知属性落在待核组合；原本排除/业务待核的行仍列出，比较指标留空，不能当0。

## 如何使用

1. 在“订单跟踪 → 经营分析”查询日期、门店及仓范围；需要时沿用必采、计算分类组、搜索和订单勾选。
2. 导出选择“门店经营分析（含商品切面与天数）”，或按所选订单导出。
3. 打开 **门店SKU供应商类目**，使用Excel表头筛选门店、SKU、供应商、原类目、仓及纳入状态。数量、金额与比率的口径在表头批注中。
4. 出现供应商待核/类目待核时查看“维度与纳入提示”和归档依据。历史资料缺失不能凭当前商品资料自动补写。

本轮只补历史属性和导出，未实现方案中的页面自定义供应商/类目切面筛选；不把剩余规划声称为已交付。计算模型、预算、箱规、默认参数、仓归属、采购和删除流程未改。

验收入口：`tests/test_funnel_dimensions.py`、既有五段/单号/AI导出/预计天数回归，以及`tools/verify_analytics_identifiers.py --out <qa下全新目录> [--exe <本版EXE>]`。全部使用隔离资料，不调用真实平台。固定交付和证据见`releases/0.51.2/rc1/交付报告.md`。
