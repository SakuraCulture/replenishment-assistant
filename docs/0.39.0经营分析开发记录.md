## 阶段 1：统一五段与原生看板

新增 `order_analytics.py`、`order_analytics_exports.py`、`order_analytics_ui.py`。
入口：订单跟踪 → 经营分析；首页也有独立入口。没有当前计算任务或 AI 连接也可使用。

模型建议包含原启用的一箱例外、位于总预算和人工安排之前。纳入模型有量但最终签发为 0 的商品；门店、仓、订单和商品原顺序保持。必采/非必采按当时必卖依据，未留存清单单列属性待核。五段统一排除门店禁采、对应仓禁用和淘汰品。未导入与确认零值分开。

按门店、分仓、订单、商品下钻；分页每页100条，导出包含全部筛选页。支持固定/滚动日期常用视图、查询取消和安全关闭。导出复核确切查询快照，写入临时文件后发布，取消/变更不留下完整名半成品。看板查询只读业务库；常用视图属于本机显示偏好。

源代码验证：新增 16 项纯逻辑测试、3 项 Qt 隔离界面测试通过。新功能尚不能据此宣称实际 EXE 验收通过。一次缓存测试初始把同内容两仓误期望为读两次，实际按相同 SHA 只解析一次；改为核对不同原件哈希数，保留首次失败日志。

## 阶段 2：AI 查询与导出

MCP 和 CLI 共用协议新增 `query_order_funnel`、`order_funnel_results`、`export_order_funnel`。查询和导出后台执行、操作键幂等、结果分页最多100条，绑定查询快照，最多保留3次分析结果。原生页面可复制包含精确日期/范围的 AI 指令，不自行发送。

隔离 Qt 网关验证：查询幂等、跨页、数据变化拒绝旧结果、工具权限、AI/原生 Excel 值/类型/样式/工作表/行列顺序一致。精确动态差异白名单仅“统计口径”的生成时间。

## 阶段 3：多轮证据复盘

新增 `history_diagnostics.py`、看板“多轮复盘”页、同名报表工作表和 `store_history_review` 只读接口。查询可选择1至30轮，默认8轮，提供近90天快捷范围。先复盘签发减量、门店少要、下单减少和实收短少，不把未知到货时间当成准时，也不拿滚动月销差额冒充期间销量。

6项证据归因测试通过；经营分析/API/Qt组合22项通过。多轮复盘仍不是连续库存回测，也不承诺判断出真实因果。

## 阶段 4：冻结试算、采用与撤回

新增 `stock_diagnosis.py`（原计算编排的调用与确定性指标）、`stock_diagnosis_adoption.py`（本次作业原子采用/撤回）、`stock_diagnosis_ui.py` 及 AI 薄适配。

从“核对与签发”或经营分析的“诊断本次工作台”进入。选门店、分类组和上下小档，基线加最多两候选。仅 `profile_parameters.<分类组>.probability` 变化，完整重做整店预算；全部结果完整且固定字段一致才允许比较。显示模型/执行/必采资金、箱规与单件覆盖、保护期缺口、到货前现货风险。覆盖分母固定为基线预测日均，不能通过改分母美化结果。

默认不选候选、确认默认取消；原因必填。关键待核不能采用，增加软风险需明确确认。采用只改本次门店参数与整店结果，永久默认不变；有后续编辑、保存、签发后不能撤回覆盖。采用失败恢复原对象和参数。审计在 `stock_diagnosis_audit` 中保留参数变化、风险、确认原因、结果摘要哈希和本机用户名（明确不是认证审批人）。作业保存与签发沿用原快照机制，不回写历史。

MCP/CLI 增加 `start_stock_diagnosis`、`stock_diagnosis_results`、`adopt_stock_diagnosis`、`undo_stock_diagnosis`；工具说明、CLI 指引同步更新。一次只保留一个完整诊断，与普通试算缓存分离。摘要不具备采用资格，任务受理不代表完成。

## 已知边界与后续

- 经营看板当前以有效签发为订单范围；未签发作业仍在原核对页查看自动建议及通过诊断试算，不伪造订单纳入历史漏斗。
- 多轮默认8轮，可选1～30轮和日期；离散观察不等于期间缺货率，不支持连续库存因果回测。历史缺原件、虚拟分类或必采依据明确待核，不回填。
- 原有人工改量/新品安排的门店暂拦截本次概率试算采用链路；先回原页核对。没有自动搜索最优参数或按SKU调概率。
- 常用筛选、计划门店范围、分类组、必采分组及下钻已支持；复盘目前为表格证据，没有新增趋势图或连续销售轨迹。
- 查询后台执行、原件按SHA限量复用；一次查询仍持有全范围事实。大量历史建议按日期分段；未承诺无限数据量下的固定性能。
- 看板每30秒后台检查索引，有更新提示重新查询，旧快照不静默替换；导出前后再次严格复核。少量同日期其他门店更新也会保守提示刷新。
- 实际 EXE 验证、构建提交与哈希以 `releases/0.39.0` 的最终交付记录为准；源码通过不代替 EXE 或外部 AI 客户端自然语言验收。
